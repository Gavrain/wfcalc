# core v2 架构设计（草案，待需求方评审）

> 状态：**草案**。评审通过前不写生产代码。
> 依据：需求方 2026-11-16 的 7 条意见（见 §9「设计输入」）。
> 分支：`design/core-v2`。1.0 收尾在 `release/1.0`，两者分开。

## 1. 目标与边界

| 项 | 结论 |
|---|---|
| 做什么 | **纯输出能力计算器**：给定武器 + 配装 + 选项，算出它自己能打出多少伤害 |
| 不做什么 | 敌人克制、护甲减免、削甲、护盾/超宏、部位倍率（需求方 2026-11-16：「衡量武器单纯输出能力」） |
| 保留什么 | 派系**歧视 Mod**（它是配装的一部分，不是敌人属性） |
| 数据层 / 界面层 | **不动**。core 的公开 API 必须兼容数据层与界面已用的名字 |
| 旧内核 | 只在 1.0 收尾分支上修，作为重写的**对照标准** |

## 2. 总流水线

```
 武器 + 模式           配装（Mod/赋能/裂罅/玄骸/选项）
        │                        │
        └──────────┬─────────────┘
                   ▼
          ┌─────────────────┐
          │ ① 分解 collect   │  把"这个模式要算哪些场景"拆成若干 Scenario
          └────────┬────────┘
                   ▼
          ┌─────────────────┐
          │ ② 素材 Buckets   │  每个 Scenario 一份素材池：键 → 值数组（保留来源）
          └────────┬────────┘
                   ▼
          ┌─────────────────┐
          │ ③ 规则 hooks     │  派生键、条件复制、写回"针对本场景/本段"的加成
          └────────┬────────┘
                   ▼
          ┌─────────────────┐
          │ ④ 口径 calibers  │  从素材里按口径取用（只读，不合并素材）
          └────────┬────────┘
                   ▼
          ┌─────────────────┐
          │ ⑤ 汇总 output    │  各口径的最终值 + 拆解树
          └─────────────────┘
```

一句话：**桶只负责提供素材，口径只负责取用素材**。桶里永远不出现"合并后的最终值"。

## 3. 场景（Scenario）：内核真正被分解的一层

这是 v2 与 v1 最大的结构差别：**前面按"阶段"拆，v2 按"场景"拆。**

```
Scenario = 一次完整的、自洽的战斗场景
  ├─ 武器的一个模式 + 一个面板变体（直接命中 / 爆炸）
  ├─ 一组上下文（派系、玄骸、爆头开关、镀层叠层、窗口秒数…）
  └─ 该场景自己的素材池（本段的面板、本段的加成）
```

例：巴什穆一个模式里有「电击段 + 火焰段」两个伤害段 → 两个 Scenario；
伯斯顿灵化「命中 + 爆炸」两个变体 → 两个 Scenario；
一个包含多段的普通模式 → 一个 Scenario 覆盖全部段（段间互不影响，见 §6）。

**为什么这么拆**：
- 每个 Scenario 的输入、输出都完整自洽，可以单独渲染、单独断言、单独替换；
- 主计算与"界面备选卡的涨幅"用**同一个** `evaluate(scenario)`，不必再写第二套；
- 以前"某段缺了哪个乘区"这类 bug 只会在某几个场景里发生，现在能逐场景对照。

## 4. 素材桶（Buckets）：键 → 值数组

### 4.1 结构

```ts
type BucketKey = string;              // 例如 'baseDamage'、'elemental:heat'、'co'
interface BucketEntry {
  value: number;                      // 百分比口径（基伤 165 = +165%）
  form: 'pct' | 'flat' | 'mul';       // 面板 / 绝对值 / 乘算
  from: EntryFrom;                    // 必填：这条素材从哪来（§4.3）
}
type Bucket = {
  key: BucketKey;
  entries: BucketEntry[];             // 不合并，按加入顺序保留
};
function push(b: Bucket, e: BucketEntry): void;   // 同键只追加，永不同键覆盖
```

**核心约束（需求方 2026-11-16）**：
- 每个键都是**数组**，基伤 Mod 与镀层基伤 Mod **不合并成一个值**；
- 桶只提供素材；**取哪几条、怎么合，是口径的事**；
- 同一场景里同一个来源贡献两次是**两条素材**（例如重击 ×2 复制出的那条），不覆盖原条目。

### 4.2 桶的目录（初步）

| 类别 | 键（示例） | 说明 |
|---|---|---|
| 面板 | `panel.baseDamage[type]`、`panel.critChance`、`panel.multishot`… | 数值型面板，**不是数组**（面板本身是单一事实） |
| Mod 加成 | `baseDamage`、`multishot`、`critChance`、`critMultiplier`、`statusChance`、`statusDamage`、`fireRate`、`magazine`、`reloadSpeed`、`ammoEfficiency`、`headshotDamage`、`targetSlot`… | 每种属性一个键 |
| 条件基伤 | `co`（镀层/异况：每层值）、`coFreeze`（只认冰冻层数） | 值存"每层值"，层数来自场景上下文 |
| 元素 / 物理 | `elemental:heat` …、`physical:slash` … | 每类型一个键 |
| 派系 | `faction:grineer` … | 按目标派系分键 |
| 独立乘区 | `finisherDamage`、`slamDamage`、`bodyshotDamage`、`bladeShadow`、`weakpointCritChance` | 与现有口径一致 |
| 派生 | `critChance#derived`（弱点暴击率 → 暴击率）、`baseDamage#passive`（被动基伤）… | 由 hook 写入，带 `from.derived` 标记 |

### 4.3 每条素材的来源

```ts
type EntryFrom =
  | { kind: 'mod';     id: string; slot: number }     // Mod / 裂罅词条
  | { kind: 'arcane';  id: string }
  | { kind: 'riven';   id: string; entry: number }
  | { kind: 'weapon' }                                 // 武器自带
  | { kind: 'kuva' }                                   // 玄骸
  | { kind: 'option';  id: string }                    // 选项（叠层数、连击倍率…）
  | { kind: 'derived'; rule: string; from: EntryFrom } // 规则写出的派生素材
  | { kind: 'computed';caliber: string };              // 口径算出的结果（不进素材池，只给展示）
```

`derived` 递归带上原来源，所以界面上"这条暴击率是哪来的"能一路追到 Mod。
**素材带上来源之后，"这个数怎么算出来的"就只是渲染素材池，不用重算。**

### 4.4 每个场景各有一份素材池

同一套配装，命中段和爆炸段的素材池**分开**，互不干扰，因为：
- 爆炸段不吃镀层、不吃冷颤（已有口径）；
- 被动基伤按**每段自己的面板分布**平摊；
- 元素合成按段各自进行。

## 5. 规则（hooks）：派生键与条件复制

### 5.1 建议：**不引入通用钩子/插件，只做一张规则表**

需求方问"根据属性加另一个属性的被动，一般怎么实现，用钩子吗"。我的答案是：**不用钩子，用声明式规则 + 按场景应用**。理由有三条：

1. **钩子是"调用方在任意时刻把逻辑插进来"**，写多了不会比现在的分阶段代码更清楚，反而会退回"哪里都能改数字"；
2. 这类被动的语义都能归纳成同一件事：**「当某条件下，把键 A 的素材复制/换算成键 B 的素材」**，一句声明就够；
3. 规则在**场景构造完之后、口径取用之前**统一跑一遍，所以"哪些规则生效"是被数据决定、可枚举、可测试的。

### 5.2 规则的形式

规则的对象本身也存在素材池里（它也是"素材"），规则表对每个场景**应用一次**：

```ts
type RuleOp =
  | { op: 'copy';    from: BucketKey; to: BucketKey; scale?: number; when?: Condition }
  | { op: 'scale';   from: BucketKey; scale: number; when?: Condition }            // 原地复制一条放大版
  | { op: 'redirect';from: BucketKey; to: BucketKey; when?: Condition }

interface Rule {
  id: string;           // 稳定 id，拆解里要显示
  from: BucketKey;      // 本条规则从哪个键（或哪个 Mod 产出）来
  op: RuleOp;
  when: Condition;      // 必须显式，缺省不允许
}

type Condition =
  | { kind: 'headshot' }                  // 只在开爆头时
  | { kind: 'heavy'; attack: true }       // 只在重击系攻击上
  | { kind: 'modeFlag'; flag: string }    // _slam / _heavy
  | { kind: 'segmentProp'; prop: string; value?: unknown };
```

**规则把新素材写进桶，不直接改任何口径的中间结果。** 所以「面板上显示的数 = 结算用的数」不是靠额外保证，而是结构上就只有这一份。

### 5.3 现有被动逐条落到规则表

以下全部来自现有代码与测试，重写必须逐条还原：

| 被动 | 现有表现 | v2 规则 |
|---|---|---|
| **弱点暴击率**（敏锐主武 / 敏锐手枪） | `weakpointCritChance` 在开爆头时**复制**成 `critChance`（source 加 `#weak`） | `{ from: 'weakpointCritChance', op: copy, to: 'critChance', when: headshot }` |
| **重击 ×2 暴率**（斩铁 / 镀层斩铁 / 牺牲斩铁 / Amalgam Ripkas / 裂罅暴击词条） | 带 `heavyX2` 的暴率贡献在重击模式下**再复制一份** | `{ from: 'critChance[heavyX2]', op: copy, to: 'critChance', when: heavy }`；规则需要区分"哪几条素材带 heavyX2"，所以素材本身带属性（见 §5.4） |
| **被动基伤 +N**（灵化被动） | 武器级被动，按**每段自己**的原始面板分布平摊，单独一路，只吃 Σ基伤% | `{ from: 'weapon.passiveBaseDamageFlat', op: derive, to: 'baseDamage#passive', dist: 'segmentPanel' }`，分布式派生（§5.5） |
| **弱点击伤害 → 爆头伤害** | 数据层 `weakpointDamage` 直接落到 `headshotDamage` 键（D-180） | **不是内核规则**：adapter 已经映射好，内核只看到一个键 |

### 5.4 素材自带的属性

重击 ×2 这类规则需要**筛选素材**，所以素材除了数值和来源，还允许带标记：

```ts
interface BucketEntry {
  value: number;
  form: 'pct' | 'flat' | 'mul';
  from: EntryFrom;
  flags?: { heavyX2?: true };   // 只有少数素材需要，其余不写
}
```

**为什么不用 `when` 去猜"这个 Mod 是斩铁"**：猜 Mod 名字就是上一轮反复犯的错。`heavyX2` 是数据层给出的**结构化事实**，内核读它、不读名字。

### 5.5 分布型派生（被动基伤）

被动基伤是一个**伤害分布**（按面板各类型占比平摊），不是标量。这类派生单独一种 op：

```ts
{ op: 'deriveDistribution'; to: 'baseDamage#passive'; rule: 'spreadByPanel' }
```

它产出的素材条目是"某类型 + 数值"，并且带 `derived` 来源。以后再有同类（例如"按面板分布附加固定元素伤害"）直接复用这条 op。

## 6. 口径（calibers）：从素材里取用

口径 = "一个可展示的最终数值 + 它的取用方式"。初步清单：

| 口径 | 取用哪些素材 | 备注 |
|---|---|---|
| 单弹头 / 单次射击 | 基伤 + 多重 + 元素合成 + 暴击 + 爆头 + 派系 | 现有 |
| 连发秒伤 / 续航秒伤 | 上者 × 射速 / 装填 | 现有 |
| 逐秒异常曲线 / N 秒异常总伤 | 触发率 × 元素占比 × 多重 × 每跳 | 现有 |
| 各元素 DoT（新增，需求方 2026-11-16 批准方向） | 每种有伤害型 DoT 的元素：命中基础 × (1+该元素%) × 系数，**求和**；存在性判据取元素合成后的槽位结果 | 与元素种类无关的合并数 |
| 稳态秒伤 / N 秒总伤 | 现有 | |

口径代码里**只读桶**，不写桶（唯一例外：规则在口径之前跑完，口径看到的是终态素材池）。

## 7. 实时展示"所有桶里键"的验证页

需求方需要一页能**实时看到每个桶的每个键**，方便逐条验证 core。

- 新页面 `packages/demo/public/core-inspector.html` + `core-inspector.js`（零依赖，沿用现有 demo 服务）；
- 数据来源：**内核直接导出素材池快照**（`evaluate()` 的返回值里带 `buckets`），页面不自己重算；
- 每行显示：键名 / 类型（pct·flat·mul）/ 值 / 来源（Mod 名、槽位、规则 id）/ 是否来自规则；
- 按场景分组（§3），同一配装下各段的素材池并排显示；
- 页面打开即可用：选武器 → 拖 Mod → 每改一次自动刷新。

**为什么这个页面值得先做**：它把"桶里装了什么"变成可读的事实，是评审架构的最直接依据；也是重写期间唯一需要的人工验证工具。

## 8. 与旧内核的对照

| 旧（v1） | 新（v2） | 处理 |
|---|---|---|
| `Contribution[]` 扁平数组 | 场景 + 分键素材池 | 数据层的 `Contribution` 仍原样产出，由 `collect()` 分键 |
| 数值型乘区 `bucketDetail()` | 口径内的取用函数 | 名字与行为保持：`bucket(panel, key, bucket)` 仍是同一个公式 |
| `weapon-state` 快照 | 场景素材池快照 | 界面读快照改成读素材池，字段名尽量不变 |
| 界面层 30+ 个"去掉重算"函数 | 统一 `evaluate()` + `withSourceRemoved()` | 按需求方 2026-11-16「两遍计算法」思路统一 |

1. 保留数据与 UI 层，重写计算 core；发布 1.0 之后按分支开发。
2. 先推送。
3. 写一份架构设计。
4. 整理 doc 中核心的确定事实，其余删掉；代码注释同样处理。
5. 在现有基础上重写 core。
6. 需要实时展示所有桶中键的页面，方便验证 core。
7. 每个键都应该是数组（基伤 Mod 与镀层基伤 Mod 不合并成一个值；桶只负责提供素材）。

## 10. 待评审 / 待确认（每条都想听你的判断，不默认通过）

1. **场景（Scenario）的粒度**：我按"模式的一个面板变体"切。一个模式内多段是算一个场景还是多个？§3 暂定一个。
2. **"用户选项"在素材里怎么表示**：叠层数 `y`、连击倍率、窗口秒数，是场景上下文（§3），还是也是素材、有来源？我倾向上下文。
3. **素材带 `flags`**（§5.4）：是否接受"内核读数据给的结构化标记、绝不读名字"这条原则作为硬约束。
4. **规则表的位置**：放在数据层（`manual/rules.ts`）还是内核的常量表？我倾向数据层——它们是"某个 Mod/武器的效果的翻译"，属于数据。
5. **`weakpointDamage → headshotDamage` 的映射留在适配层**：内核只认 `headshotDamage`。是否同意"内核不认识弱点这两个字"。
6. **口径里"合并素材"的边界**：素材池不合并，但口径内部肯定要 Σ。我需要你确认这条计数规则：**口径里按"来源 × 条件"分组求和，组内相加、组间相乘**——这样你说的"基伤 Mod 与镀层基伤不合并"在口径里也成立（不同来源组）。
7. **各元素 DoT 合并数**：它是否作为**第 9 个输出口径**进入 demo 左栏，还是先只在内核导出、页面上放。
