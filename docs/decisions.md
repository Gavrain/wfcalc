### D-005 计算内核的规格形态：伪代码 vs TypeScript（状态：已确认）

- **日期**：2026-11-05
- **类别**：结构变化
- **背景**：
  需求方问"要不要把乘区表建模转换成伪代码形式防止歧义"。我已把乘区表第 0~8 节全部转成
  `docs/伤害公式.md`（函数级伪代码 + 乘区表原文→代码的映射对照 + 三个校验例）。
  问题是这份伪代码停在"文档"层，还是继续做成可执行的 TypeScript。
- **我的建议**：
  1. `伤害公式.md` 作为实现依据，**每个函数都有唯一名字**（`applyElements` / `mergePairwise` /
     `critAverage` / `critTiers` / `dotTick` / `resolve` / `blastPerSecond` …）；
  2. `packages/core` 按同名函数实现，**测试名与文档小节号一一对应**（如 `4.1 校验例 1`）；
  3. 表里没写死的（本文 A-xx 标记）**确认一条实现一条**，未确认的先不写代码。
- **理由与证据**：
  伪代码已经当场抓出 13 处歧义（见 A-01~A-13 与本文第 10 节对照表），其中至少 4 处
  （元素合成优先级、玄骸两份数值、面板多重取哪个量、射线怎么认）会直接改变数值结果。
  这说明"只读中文表就实现"确实会跑偏——伪代码这一步是必要的，但不能只停在文档。
- **备选方案**：
  - A. 只写文档，代码另起：文档与代码会分叉，后续改动没人保证同步。
  - B. 直接写 TypeScript、不写文档：歧义会以"能跑的代码"形式固化，审阅门槛更高。
  - C. 先文档、确认后按同名函数实现（**本方案**）。
- **风险 / 不这么改的后果**：伪代码本身不会算错（不执行），但它会把"未决口径"固化成默认值，
  以后被当成"已经定好的"用。
- **结论**：需求方 2026-11-05 选择「伪代码为依据，确认后按同名函数实现」。
  → `伤害公式.md` 的函数名即为 `core` 的公开 API 名；测试名带文档小节号；未确认项不写代码、显式报"口径未定"。

### D-006 元素合成的配对优先级（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径（表 4.1 与 4.3 互相冲突）
- **背景**：
  表 4.1 写「元素 %Mod **先加总**；各元素加量按该元素归属」；
  表 4.3 写「按 Mod 槽位顺序，从前往后**两两合并**；后放的元素与已存在的单元素配对」。
  两句在"元素数量 > 2"时给出不同结果，例：

  ```
  例 A（两张元素 Mod，武器无自带元素）：面板 10 冲，槽 1 = +90% 火，槽 2 = +90% 毒
  ── 先加总 vs 按槽位：两者都是"火 180 + 毒 180"，**无复合**（没有第二个火/毒可配对）
  例 B（面板自带火）：面板 10 火，槽 1 = +90% 毒，槽 2 = +90% 火
  ── 先加总：面板火 10 + 火Mod 180 = 190 与 毒 180 配 → **毒气 370**
  ── 按槽位：毒(槽1) 与 面板火 10 配 → 毒气 190；火Mod 180 落单 → **毒气 190 + 火 180**
  例 C（三组，问题最直白）：面板 10 火，槽 1 = +90% 火，槽 2 = +90% 毒
  ── 先加总：火 190 与 毒 180 配 → **毒气 370**
  ── 按槽位：面板火 10 与 槽1 火 180 合成"火 190"，槽2 毒无配对 → **火 190 + 毒 180（无复合）**
  → 同一套配置，两种理解给出完全不同的复合结果。
  ```

  另有几条同源问题：
  1. **面板单元素与 Mod 单元素谁先配对**：表 4.4 校验例 2 里是"毒(Mod) + 火(面板)"，说明**不是**严格按槽位序；
  2. **两个相同的 Mod 元素**（两张火卡）是合并成一个槽位，还是两个槽位各自找配对；
  3. **元素加量的载体**（`伤害公式.md` A-14）：同一元素两张卡合计 180% 时，是"新总伤 × 1.8"还是"每张卡各自 × 0.9 再相加"；底座里已有同类型面板伤害时，加量是**加到该类型上**还是**覆盖**。本文取"新总伤 × 总量、加到该类型上"（与校验例 1 的结果一致）；
  4. **镀层类（`co`）的实际层数**："每个异常状态 +X% 伤害"按目标身上已有的层数算，还是按本发期望叠上的层数算。
- **我的建议**：
  §5 的 `applyElements` 按"**面板元素先入槽**（顺序固定为物理之外的面板顺序）、
  **面板元素与 Mod 元素同池按槽位序合并**、**同类型 Mod 元素先合并成一个槽位**"实现。
  —— 这套做法与校验例 2 一致（毒 Mod 与火面板能配上），但需要需求方给一个**反例式的确认**：
  "面板 10 火 + 槽位1 火 + 槽位2 毒"（三组）期望的最终分布是什么？
- **理由与证据**：见上面三组对比算式。表 4.1 与 4.3 各自自洽，只有"两者同时成立时"才有冲突。
- **备选方案**：
  - A. 严格按槽位序合并（含面板元素占一个槽位、位置按武器自带顺序）——可能与"先加总"冲突。
  - B. 先按类型加总再合并（**本方案**）——与 4.1 一致，与校验例 2 一致。
  - C. 引入"面板元素优先级最高、其次是槽位 1 的 Mod"——需要需求方给规则。
- **风险 / 不这么改的后果**：复合元素与实际偏差 → 触发占比（0.3②）、DoT 系数、对目标抗性
  全部跟着错。这是**会算错数字**的一条。
- **结论**：需求方 2026-11-05 选择「**毒气 370**」（即先按类型加总、再两两合成）。
  用例「面板 10 火 + 槽位1 +90% 火 + 槽位2 +90% 毒」已写进 `伤害公式.md` §5.4 与校验例 4；
  剩余两个细问（面板单元素与 Mod 单元素的配对序、跨类型 Mod 卡配对序）沿用"面板元素先入槽 + 槽位序"的默认做法，发现反例再单列。

### D-007 玄骸自身那一份是否参与复合合成（状态：已并入 D-017）

- **日期**：2026-11-05
- **类别**：改动已确认的口径
- **背景**：
  表 4.4 校验例 2 明确说「毒素 64 与面板火 10 复合，形成 74 毒气；磁力**保持 24 不变**」，
  → 玄骸那份磁力**不参与**复合合成。
  但同一节的另一条又说「**【参与组合】**：视为位于槽位 9~12，与已有元素按两两合并逻辑合成」。
  两条在一起就是"磁力不参与、但玄骸元素参与合成"——这只有在"磁力是复合元素、不参与配对，
  但仍占一个槽位"时才能同时成立。若玄骸选的是**基础元素**（火/冰/电/毒），它是否参与配对就没写。
- **我的建议**：
  玄骸那份一律按"**复合元素/独立变量**"处理：不参与配对，只并入同类型变量（冲击例外，已定）。
  这条与校验例 2 严格一致；基础元素玄骸（如 60% 火）也就不会和毒复合。
- **理由与证据**：校验例 2 是表里给出的**唯一可复算样例**，以它为准最稳。
- **备选方案**：
  - A. 玄骸那份一律独立（**本方案**）。
  - B. 玄骸为基础元素（火冰电毒）时参与配对、玄骸为复合元素时不参与——需要需求方给"玄骸火 + 毒素"的期望结果。
- **风险 / 不这么改的后果**：玄骸基础元素武器的复合分布不对，触发占比跟着错。
- **结论**：需求方 2026-11-05 在回答 D-006 时一并裁定了玄骸的整体位置：
  「玄骸应该在基伤之前，玄骸加成体现在武器面板基伤内」→ 升级为 **D-017** 单独记录（它同时修正了表 4.4 的"不再被乘一次"）。
  本条"不参与复合合成"的结论与 D-017 兼容：玄骸是复合元素时天然不参与配对；若是基础元素，仍按"先加总成独立槽位"处理。

### D-008 DoT 基础值是否剔除玄骸加成；爆头落在哪一步（状态：已确认：部分与建议相反）

- **日期**：2026-11-05
- **类别**：改动已确认的口径
- **背景**：
  表 6.2 说 DoT 基础值 = 命中伤害中**剔除元素/物理 Mod 加量**后的值。
  **玄骸加成不是 Mod，是武器固有属性**，表里没说剔不剔。
  同源问题：表 3.2 说「爆头对 DoT **适用**」，但 6.2 的四个步骤里没有爆头这一步；
  若落进①（基础命中伤），会被③的派系加成再放大一次（相当于爆头也"两次"）；若作独立乘区则不会。
  另外 6.4 的爆炸「基础伤害 × 30%」到底取哪一版基础伤害（含不含元素加量）也没写。
- **我的建议**：
  1. 玄骸那份**剔除**（与"剔除元素/物理加量"同一精神：DoT 基础值只看武器的"裸"面板 + 基伤 + 多重 + 暴击）；
  2. 爆头作为 **6.2 ④ 之后的独立乘区**（不进①，避免被派系二次放大）；
  3. 爆炸的"基础伤害"取与 DoT 同一版基础值（即同样剔除元素/物理加量）。
- **理由与证据**：需求方在 DoT 口径上反复强调"保留基伤%、多重%、暴击，剔除元素/物理加量"——
  这句话本身就在排除"含 Mod 加量的命中伤"。爆头"两次"没有任何文档依据。
- **备选方案**：
  - A. 玄骸剔除、爆头独立、爆炸同 DoT（**本方案**）。
  - B. 玄骸保留（玄骸是武器固有，等价于面板）、爆头进①。
  - C. 三种组合分别实现为开关：增加实现量，但能对比。
- **风险 / 不这么改的后果**：玄骸武器、爆头（默认 3×）两条线的 DoT 数值偏差。
- **结论**：需求方 2026-11-05 裁定（与我的建议部分相反）：
  1. **玄骸**：「玄骸是固有的」→ **保留在 DoT 基础值里**（不剔除，与 D-017 一致）；
  2. **爆头**：「爆头是开关」→ 作为独立乘区，由用户勾选，**不进①**，因此不会被派系加成二次放大；
  3. **爆炸**：「爆炸是异常状态跟这个不是一个类型」→ 爆炸**单列结算**，不并入 DoT 汇总，也不再强行套用 DoT 基础值。

### D-009 "面板多重"取 multishot 还是 bullets（状态：已确认）

- **日期**：2026-11-05
- **类别**：归类判定 / 数据取舍
- **背景**：
  数据层 `modes[]` 里同时有：
  - `multishot`：= 导出**顶层** `multishot`（`emit.ts` 第 62 行 `multishot: m.baseMultishot`）
  - `bullets`：= 该 behaviour 的 `fireIterations`

  `research/01` 第 3 节第 3 条实测：两者**经常不等**（Strun Vandal 顶层 10 / behaviour 10；
  Soma 第二个 behaviour `fireIterations: 8` 却是"特殊状态"不是"8 连发"）。
  表 2.2 只说"面板多重就是基础值"，没说取哪个量、`bullets` 是否也要乘进单次射击伤害。
- **我的建议**：以 `modes[].multishot`（顶层）作为"面板多重"，`bullets` **不参与**伤害计算，
  只做数据溯源；对 `bullets > 1` 且确为多弹丸的武器（霰弹），以需求方人工确认为准。
- **理由与证据**：顶层 `multishot` 才是游戏面板显示的那个数；`fireIterations` 在同一字段位
  既承载"霰弹弹丸数"又承载"特殊状态段"，语义不纯。
- **备选方案**：
  - A. 只用 `modes[].multishot`（**本方案**）。
  - B. 用 `max(multishot, bullets)`：可能把特殊段算进伤害。
  - C. 两者都乘：会重复计算（霰弹枪顶层 multishot 已经含弹丸）。
- **风险 / 不这么改的后果**：霰弹类与多段武器单次伤害量级偏差，DPS 全部跟着偏。
- **结论**：需求方 2026-11-05 选择「只用 `modes[].multishot`」，`bullets` 不参与伤害计算（仅做数据溯源）。

- **结论**：需求方 2026-11-05 选择「**建表，加入 todo 后面人工确认**」。
  → 新建 `packages/data/src/manual/beam-weapons.ts`（我先按真射线清单起草，每条标 `_manual` 与待核），
  → `data-todo/README.md` 增加一节"射线武器人工核对"，**未确认前一律按非射线算并在 UI 标注**。

### D-011 core 类型与数据层字段名不一致（状态：已确认）

- **类别**：结构变化
- **背景**：

### D-012 爆头 × 暴击：整体 ×2 还是总爆伤翻倍（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径
- **背景**：
  表 3.2 原文：「爆头时若产生暴击，最终伤害直接 ×2（等效于总爆伤翻倍，再按 3.1 公式算）」。
  这两句话在 `cd ≠ 2` 时**不等价**：
  ```
  整体 ×2      ：期望倍率 = [cc(cd−1)+1] × 2
  总爆伤翻倍   ：期望倍率 = cc(2cd−1)+1
  例 cc=100%, cd=4 → 整体 ×2 = 2×3 = 6；翻倍 = 1×7+1 = 8
  ```
- **我的建议**：按「**总爆伤翻倍**」实现（表里"等效于"是等价声明，视为口径说明而非补充）。
- **理由与证据**：若按"整体 ×2"，则代码里要**区分是否暴击**（表明确说"若产生暴击"），
  而 2.4 又说"不做随机模拟"——无法在期望值里表达"有概率不暴击"。总爆伤翻倍的写法
  可以写成 `cc(2cd−1)+1`，无随机数、纯期望，与 2.4 自洽。
- **备选方案**：
  - A. 总爆伤翻倍（**本方案**）。
  - B. 整体 ×2（且仅在 `cc ≥ 1` 时乘一次）。
  - C. 按分档展示两版（实现成本翻倍）。
- **风险 / 不这么改的后果**：爆头暴击的期望值偏小（在上例差 33%）。
- **结论**：需求方 2026-11-05 裁定「**爆头倍率跟这个不是一个事情，爆头有自己的倍率，爆头且暴击的时候需要乘爆头倍率乘暴击倍率再乘 2**」。
  → 公式：`命中伤害 = 基础 × 爆头倍率（勾选爆头时）× 暴击倍率 × (暴击时是否再 ×2)`。
  → 这推翻了表 3.2 的"等效于总爆伤翻倍"说法（两者在 cd≠2 时不等），差异记入 `口径裁定一览.md`。
  → 待补确认一项：分档上下限（k 级）里"×2"是只用于平均伤害，还是分档也 ×2。

### D-017 玄骸加成在基伤之前（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径（同时修正 `乘区归属表.md` 表 4.4 的一句）
- **背景**：
  需求方在回答 D-006 时补充裁定：**「玄骸应该在基伤之前，玄骸加成体现在武器面板基伤内」**。
  这与表 4.4 现有两条写法不一致，必须显式修正，否则内核会在错误的位置乘玄骸：

  | 表 4.4 原文 | 与新裁定的关系 |
  |---|---|
  | 玄骸加成 = **独立乘区**，作用于面板伤害，形成"新面板" | 方向正确（玄骸确实在面板侧），但"独立乘区"容易被实现成"在元素之后单独乘一个括号" |
  | **「玄骸加成自身不会被再乘一次」**（数值固定为 `面板总伤 × 比例`） | **被推翻**。既然玄骸在面板基伤内，它就必须吃 `(1+Σ基伤Mod%+镀层%)` |
  | 校验例 2：面板 40，60% 磁力 → 磁力 **24**，新总伤 64 | **保留**。见下方"两种读法都算 24 的原因" |

  关键推导（为什么"吃基伤"与"24"能同时成立）：
  ```
  设面板总额 T0 = 40，玄骸比例 r = 60%，基伤加成 G（例中 G = 0）

  读法甲（玄骸金额按面板总额算）：玄骸 = T0 × r × G = 24 × G = 24 ✅
  读法乙（玄骸与面板同乘、再减回）：玄骸 = T0×(1+r)×G − T0×G = T0×r×G = 24 ✅
  → 两种写法在代数上等价，都等于「T0 × r × 整体基伤系数」。
  真正的区别不在 24 这个数，而在于**玄骸是否进入元素 % 的基数**：
    旧口径（表 4.5）：新总伤 = T0×(1+r)，玄骸不进元素%  → 元素% 基数 64
    新口径（D-017）  ：新总伤 = T0×(1+r)×G，玄骸进面板    → 元素% 基数 64×G
  ```
- **我的建议（已采纳）**：
  1. 新增前置函数 `applyKuvaBonus`：`玄骸加量 = 面板总伤 × 比例`，并入面板（物理型并入同物理类型）；
  2. 基伤 `(1+Σ基伤Mod%+镀层%)` 随后作用于"含玄骸的面板"，玄骸因此**吃基伤加成**；
  3. 元素 % 的基数 = 基伤之后的总伤（含玄骸），**这是修正后的准确含义**：
     "玄骸不被元素 % 再乘一次"仍然成立（元素 % 只算元素槽位，玄骸金额已定死），
     但"玄骸不进元素 % 基数"**不再成立**。
  4. `乘区归属表.md` 不直接改（已定稿文档走确认流程），差异记录在本条与 `伤害公式.md` §5。
- **理由与证据**：
  - 需求方原话："玄骸应该在基伤之前，玄骸加成体现在武器面板基伤内"；
  - 数值自洽性：若玄骸既在面板内、又"不被再乘一次"，就必须判定它是否在基伤括号内；
    需求方已明确在**基伤括号内**，因此它吃基伤加成。
- **备选方案**：
  - A. 玄骸前置并吃基伤（**本方案**，与需求方原话一致）。
  - B. 玄骸前置但不吃基伤（把"不再被乘一次"理解为"连基伤也不吃"）——与"体现在面板基伤内"矛盾。
  - C. 玄骸留在元素之后（旧写法）——需求方已否决。
- **风险 / 不这么改的后果**：
  - 玄骸武器（Kuva / Tenet / Coda 系，含冲击型）的基伤 Mod 收益与元素分布会偏；
  - 例 2 的 24 不会变（两种读法同值），所以**只靠例 2 无法发现这个错误**，必须用带基伤 Mod 的用例。
  - 待补一条校验：面板 40、60% 磁力、+165% 基伤 ⇒ 玄骸 = 24 × 2.65 = 63.6，新总伤 = (40+24)×2.65 = 169.6。
- **结论**：需求方 2026-11-05 确认。`伤害公式.md` §3 / §5 已按此顺序重排，`core` 侧的 `spreadTotalAfterMods` 注释需同步修正。
