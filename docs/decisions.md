### D-105 `app.js` 的分层方案（状态：**待确认 → 已确认，选 B**）

- **日期**：2026-11-06
- **类别**：结构变化（前端文件组织）
- **背景**：需求方问「app 那边需不需要拆成多个模块，数据层、计算层、UI 也独立出来？」
- **现状（实测，见下表「行数」列）**：`app.js` 2284 行 / 84 个函数，其中
  - **数据层**：8 个函数 138 行——把 `generated/` + `mods.json` 读进来、挑出可装 Mod、把 Mod/赋能转成 `Contribution`；
  - **计算层**：5 个函数 77 行——组装 `compute()` 的选项、跑一次计算、算「相对不上这张的提升」；
  - **UI 层**：其余 71 个函数 1959 行（渲染 352 / 拖拽 295 / 备选卡 243 / 控件 257 / 编辑器 354 / 选单 225 / 工具 152 / boot 81）。
- **我的建议**：**分三段、但不拆成十几个文件、更不切成独立进程**。理由：
  1. **计算层已经在 `packages/core` 了**，`app.js` 里的 77 行只是「把 UI 状态翻译成 `compute()` 的参数」，
     拆出去只会多一层跳转，**不建议单独成模块**；
  2. 真正值得独立的是**数据层 138 行**（`app-data.js`）：它对外只有「读数据 → 返回武器/Mod/赋能/贡献」，
     UI 完全不关心 JSON 长什么样；
  3. UI 里的**编辑器 354 行**和**武器选单 225 行**可以各自成文件（`ui-editor.js` / `ui-picker.js`），
     前提是先把跨文件共享的 `state` / `DATA` / `modSlots` 收敛成一个显式的 `store` 对象
     （现在 `state.` 出现 46 次、`modSlots` 31 次、`exilusModId` 19 次、`dragPayload` 16 次，
     直接拆文件会变成隐式全局，反而更乱）。

  建议的目标结构（每步都可单独回滚）：

  ```
  public/
    app.js          入口：boot + 主渲染编排（约 1600 行）
    app-store.js    跨模块共享状态（state / DATA / modSlots / dragPayload …）
    app-data.js     数据层：读 generated/ + 模组池 + 贡献转换（约 138 行）
    app-compute.js  计算层薄壳：选项组装 + runCompute + 边际提升（约 77 行）
    ui-editor.js    编辑器（约 354 行）
    weapon-picker.js 已验证存在
    weapon-override.js 已有
  ```

  - **分几步**：① 抽 `app-store` + `app-data`（行为不变，靠现有 78 项 `interact` 校对兜底）→
    ② 抽 `app-compute` → ③ 抽 `ui-editor`。每步跑 `demo:check` + `demo:editor-check` + `http-crawl`；
  - **不建议**：把 UI 拆成「样式 / 模板 / 事件」三层、或引入构建器——现在的零构建 + 服务器剥类型
    是刻意设计，拆成很多 `.js` 后首次加载会变成 10+ 个请求（本机无所谓，但上静态站要注意）。
- **备选方案**：
  - A. 只抽 `app-data.js`（138 行），其余不动——收益集中、风险最小；
  - B. 按上面 5 个文件拆（**本建议**）；
  - C. 一行不动——2284 行确实还能读，但要找「某个数字怎么变的」时仍旧要整份翻。
- **风险 / 不这么改的后果**：`app.js` 里 UI 与数据/计算混在一起，改口径展示时容易顺手改到数据层逻辑；
  改数据字段时要整读 2284 行。
- **结论**：需求方 2026-11-06 选 **B**（5 个文件拆法），实施记录见下一节。

#### 1. D-022 元素 Mod 的加成，是按哪个数算的？

- **现在实际在做**：元素 Mod（比如"火焰 +90%"）加的伤害 = **整把枪面板总伤 × 90%**，
  而这个"面板总伤"是**已经加过玄骸加成之后**的数。
- **例子**：面板 100，玄骸 +60% → 新面板 160；再来一张"火焰 +90%" → 加 160 × 0.9 = 144，
  不是 100 × 0.9 = 90。
- **当时为什么没定**：这条牵涉"玄骸加成到底算在哪一步"，问过两轮才理清。
- **我建议**：维持现在的做法（追认）。

#### 2. D-057 六秒异常状态总伤怎么算的？

- **现在实际在做**：

  - **爆炸不算进"每层秒伤"**，但算进"六秒总伤"。

#### 3. D-084 弹药效率怎么折算成弹匣？

- **现在实际在做**：显示的弹匣 = 面板弹匣 ÷ (1 − 弹药效率)。
  - 弹药效率 50% → 弹匣翻倍（×2）；
  - 弹药效率 60% → 弹匣 ×2.5。
- **为什么会有疑问**：你当时写的是"提升 a/(1−x)"。照字面理解，会变成"在原来的量上再加一份"，
  也就是 60% 时 ×3.5。但游戏里 50% 弹药效率就是弹匣翻倍，所以我按 1/(1−x) 做了。
- **我建议**：追认现在的算法。如果你要的是字面那个，改一个函数就行，很好改。

#### 4. D-074 武器自带的元素，什么时候并进元素 Mod 里？

- **现在实际在做**：武器自带的元素（比如某把枪面板自带火焰）**先单独放着**，
  等做"元素两两合成"那一步，才和 Mod 的同类元素合并。
- **唯一的争议点**：合并时用哪种算法。
  - 现在用的是 **A + B**（毒素 23.5 + 电 5 → 腐蚀 28.5）；
  - 另一种理解是"取小的那个当复合元素，剩下的留成单元素"（腐蚀 5 + 毒素 18.5）。
- **为什么倾向相加**：docs/乘区归属表.md 里的核对例子（"毒素 64 + 面板火 10 → 74 毒气"）

### D-107 元素 Mod 后移：DoT 每跳基础值改用「命中基础分布」（状态：**已确认，需求方 2026-11-06**）

- **日期**：2026-11-06
- **类别**：改动已确认的口径（DoT 基础值 + 元素 % 的作用范围）
- **背景**：需求方对 Q6 的补充把真正的问题指了出来，原话：
  > 「暴击后不加元素的命中基础值，但是元素 mod 的作用不对，火加毒确实是会合成毒气，
  > 但是他仍然是火焰加成，不会对毒气 dot 加成。只有真正的原生毒气百分比加成，
  > 例如 lavos 的效价炼成，或者裂隙 mod 上的 +xxx 毒气% 才会增加毒气 dot。
  > 所以我才一定要把元素后移，火冰毒电这种 dot 是不会出现这个问题的，
  > 然后爆炸目前的设定也是不享受爆炸 mod 加成，所以只有毒气有这个问题。」

- **改了什么**
  1. DoT 基础值 = 命中分布**剔除元素/物理 Mod 加量**后的样子（玄骸自带元素保留），
     暴击按期望倍率施加 —— 与原来一致；
  2. **元素 % 不再整体乘在每跳上**，而是只作用于「它自己的类型确实出现在命中分布里」的那一份；
  3. 由此：**火焰 % 不给毒气 DoT 加成**（命中里没有 gas 这一项）；毒气只吃基础值那 50%；
  4. 触发占比 / 叠层仍看**命中分布**（元素 Mod 撑出来的份也算触发池）；
     DoT 加权分母里，合成元素（毒气/爆炸…）按**来源元素之和**计。

- **证据（赤毒·卡拉克，玄骸火 60%）**

| 配装 | 命中Σ | DoT基础Σ | 火焰每跳 | 毒气每跳 | 切割每跳 |
|---|---|---|---|---|---|
| 玄骸火 + 无 Mod | 36.80 | 46.11 | 23.06 | 23.06 | 16.14 |
| 玄骸火 + 火焰+90% | 69.92 | 46.11 | 30.84 | 30.84 | 21.59 |
| 玄骸火 + 火焰90 + 毒素90 | 103.04 | 46.11 | 30.84 | 30.84 | 21.59 |
| 玄骸火 + 暴击+150% | 36.80 | 60.08 | 30.04 | 30.04 | 21.03 |

  火焰 +90% 只把毒气从 23.06 抬到 30.84（毒气里火占 37.5%，正是「火焰加成只作用于火焰那一份」），
  而不是旧口径那样直接乘 1.9。

- **影响面**：所有依赖 DoT 的配装数值都会变；暴击/爆头类 Mod 对 DoT 的影响不变。
- **回归**：单元测试 419/419；页面校对 8 个脚本 242 项全绿（interact 新增 2 条毒气断言）。

### D-109 异常状态"存不存在"的判据（状态：**已确认 / 已修**，需求方 2026-11-06）

- **日期**：2026-11-06
- **类别**：修 bug + 明确判据
- **反馈原话**：「现在有火或者毒的时候，异常状态那边多出来了毒气，他是 0 层为什么会显示呢，居然还有每层伤害」
- **根因**：`output.ts` 判断"合成元素在不在"时用"来源元素之和 > 0"兜底，
  于是只有火 Mod（甚至只有玄骸火）时毒气也被当成存在 —— 层数 0、每层伤害却有值。
- **需求方给的判据**：
  > 「是否有这个异常应该看当前面板复合后有没有这个元素，而不是看他分解的，
  > 否则会出现电毒火复合成腐蚀火但是你也加上了毒气。而且玄骸这个参与复合没有问题，
  > 因为元素会复合其实是 mod 顺序的问题，跟数值没有关系。」

  实测确认（槽位顺序决定配对）：
  | 槽位顺序 | 命中分布 |
  |---|---|
  | 火(0) 电(1) 毒(2) | 辐射 + 毒 |
  | 电(0) 毒(1) 火(2) | 腐蚀 + 火 |

- **改法**：`elementPresent(t) = 合成后的命中分布里真的有这个类型`；
  `dotShareOf` 只负责分份、不再兼职判存在。加权分母也只统计存在的类型。

### D-112 镀层加成框始终显示（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **日期**：2026-11-06
- **类别**：展示层（未装备时的可见性）——**不改口径、不改数字**
- **需求方原话 ①**：「镀层mod的提示框始终显示，即使没有上镀层基伤mod」
- **需求方原话 ②（同一天补充）**：「未装备也允许修改叠加层数，且默认是最大值，

**背景**

`renderCoControls()`（`packages/demo/public/app.js`）原来的第一行是
`if (!co.active && !fc.active) return;`，即「没装 `co` / `coFreeze` 词条的 Mod 就整块不渲染」。

**① 散射正义为什么显示 +203%（需求方问的那条）**

数据里每张集团卡（散射正义 / 致命数列 / 破碎正义 … 共 13 张）都带一个 `syndRadial` 词条
（描述里的「+X Justice / +X Truth」），值层级 `[0, 0.3333, 0.6667, 1]`。
`data-build/src/mods/stat-map.ts` 把它映射成 `baseDamage`（`bucket: null`，`kind: special`），
而 `toContribStat` 认不出时没有拦 → `modToContributions` 给**每一张这类卡**凭空加了 **+1% 基伤**。

```
赤毒海克 + 散射正义：  只有多重 +200%        → 指标 1220.92 → 3662.77  ⇒ +200.00%
                      多重 +200% + 误加基伤   → 指标 1220.92 → 3699.40  ⇒ +203.00%
```

需求方选择「**剔除：不算**」，与其它「= 无效果」的集团特效一致。
**实现**：`adapter.ts` 的 `toContribStat` 对 `key === 'syndRadial'` 直接返回 null（`isSyndicateEffectStat`）。
**顺带**：抵消正义的 `nullifier:90`（摧毁护罩发生器几率）、缴械纯净的 `disarm:40`（缴械几率）

### D-128 拆解跟随输出变化重算（状态：**已确认 / 已实施**，需求方 2026-11-06）

**根因：拆解根本不是"监听"，是"点一下算一次"**

`showDetail(row)` 只在卡片 `click` 时执行一次，结果直接写进 `#detail`；之后：


而且它拿的是**点击那一刻的 `row` 快照**——`row.mod` 是当时的对象引用，换枪后就失效了。

**改法：拆解挂到「渲染末尾」，只记住"拆解谁"**

| 之前 | 现在 |
|---|---|
| `showDetail(row)`：算一次，写死 DOM | `selectDetail({kind, id/key, exilus})`：只记"拆解谁" |
| — | `renderDetail()`：按**当前** `store.data` 重新取 Mod/赋能，按**当前**贡献重算 |
| — | `renderAll()` 的最后一行调用 `renderDetail()` |

`renderAll()` 已经是**所有状态变化的唯一汇合点**（异况、叠层、玄骸、派系、爆头、基准、
拖拽、换枪、编辑器保存……全部走它），把拆解挂在这里等于"输出一变就重算"，
不需要给每个控件单独挂监听（那样才会漏）。换枪后 `resolveDetailTarget()` 取不到那张卡时，

### D-129 拆解里的「等效弹匣」改成与输出口径同样的表（状态：**已确认 / 已实施**，需求方 2026-11-06）

### D-131 修复：Mod 配置区被 6 列网格挤成一坨（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「mod配置那边你改崩了，挤成一坨了」

**我上一轮（D-127）改崩了两处 CSS**

1. **`.slot` 的基础样式整块丢了**：为了加 `position: relative`（放槽名标签），
   我把原来的 `.slot { background / border / padding / min-height / display:flex … }`
   替换成了只有一行 `position: relative` —— 所有槽位（包括 8 个普通 Mod 槽）失去背景、边框、
   内边距与最小高度，内容直接贴在一起。**这是"挤成一坨"的主因**。
2. **`.slot-wrap` 改成 `repeat(6, 1fr)` 网格 + `.slot-grid { display: contents }`**：
   本意是让侧栏两张槽和 Mod 槽同宽，但 `contents` 把 8 个 Mod 槽 + 2 个侧槽全部摊进
   **同一个网格的换行流**，侧槽被挤到第二行末尾，整个区域成了一排乱格子。

**改法（恢复结构 + 保持"侧槽与 Mod 槽同宽"）**

```css
.slot {                      /* 恢复原有样式，只多一行 position: relative */
  position: relative; background: var(--panel-2); border: 1px dashed var(--line);
  border-radius: 5px; padding: 6px; min-height: 84px;
  display: flex; flex-direction: column; gap: 4px; …
}
.slot-wrap   { display: flex; gap: 8px; align-items: stretch; }
.slot-grid   { display: grid; grid-template-columns: repeat(4, 1fr); flex: 1; min-width: 0; }
.side-column { display: grid; grid-template-columns: repeat(2, minmax(0, 1fr)); flex: 1; min-width: 0; }
.arcane-slots, .side-slots { display: contents; }   /* 两张侧槽直接落进侧栏自己的 2 格 */
```

侧栏与 Mod 槽区等宽（都 `flex: 1`），侧栏里 2 格 → 每格与普通 Mod 槽同宽；
Mod 槽区仍是原来的 4 列网格。**没有用 `contents` 把 Mod 槽摊出去**。

**教训**：改"有多个 div 包裹层"的布局时，`display: contents` 会把包裹层的子元素提升到父容器的
布局流里更上层——层级一旦算错，整个区域的排布就全乱；这类改动要小步改、改完对一眼。

### D-134 赋能槽的处理方式对齐 Mod 槽 / 劣化槽（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「赋能槽有赋能的时候，其他赋能装不上去的，应该跟mod槽位还有劣化槽一个处理方式」

**为什么会装不上**：D-115 给劣化槽 / 赋能槽都写了"已占用就互换"，但 `makeDropTarget()` 的
`dropHappened` 标志是**全局单一变量**——它只能表示"最近一次 drop 处理过"。
在同一个事件循环里连发两次 `dragstart → drop` 时，第二次的 `dropHappened` 接着有效，
`dragend` 就不再触发"拖出即卸下"的兜底，于是旧的赋能留在槽里、新的没进去。

> 顺带说明：真实浏览器里 dragstart/drop/dragend 是分散在不同事件循环里的，所以手动拖一般没症状；
> 但"处理方式与 Mod 槽 / 劣化槽保持一致"是对的要求，这一轮把它改成同一套：

**改法**

1. `dropHappened` 改成**每次 dragstart 重新初始化**，并在 `drop` 处理完成后**立即复位**，
   不再依赖"下一次解析/第二次事件循环"来清掉；
2. 赋能槽补上与 Mod 相同的**可装判定**：只接受**本武器大类**的赋能
   （`arcaneSlotAccepts()` / `dropOnArcane()`，与 Mod 的 `isModAllowedOnWeapon()` 同一层意思），
   别的大类的赋能进来显示**禁止符号**、不改变槽内容（以前只看 `kind === 'arcane'`，
   会把槽里那张顶掉并换上一个不属于本武器的赋能）；
3. 赋能槽之间的互换（拖到备选区的某张赋能卡）也加了大类校验（`candidateCardAccepts`）。

**回归**：`arcane-detail.mjs` 扩到 30 项（+ 槽里已有赋能时拖入别的赋能 = 互换、被换下的回列表、
别的大类赋能不能进当前槽、拖进来不改变槽内容；另加"侧栏是单列窄栏"的结构断言）。
全量：16 个页面校对脚本全绿；单元测试 424 全绿。

### D-135 派系伤害对命中伤害生效（状态：**已修复**，需求方 2026-11-06）

- **需求方原话**：「派系伤害未对命中伤害生效，目前只对dot生效了。」

**根因**：`resolveSegment()` 里算出了 `factionPct`（`factionFor(ctx.faction, contribs)`），
但它**只传给了 `dotTick()`**；`damageLine(v, cc, cd, hitHead, hsMul)` 根本没有派系参数。
于是上「对 Grineer +30%」这类卡：DoT 每层秒伤 / 六秒总伤 ×1.3，而
单弹头 / 单次射击 / 爆发伤害 / 持续伤害**全都不变**。

**改法（\§5.2「命中结算前一次」）**

```ts
// core/src/crit.ts
export function damageLine(v, cc, cd, hitHead, headshotMul, factionMul = 1) {
  const base = (hitHead ? v * headshotMul : v) * factionMul;   // ← 只乘这一次
  const crit = base * cd * (hitHead ? 2 : 1);
  return { nonCrit: base, crit, average: (1-cc)*base + cc*crit, headshotMul: ... };
}

// core/src/segment.ts
const factionPct = factionFor(ctx.faction, contribs);
const factionMul = 1 + factionPct;
const line = damageLine(vTotal, cc, cd, ctx.headshot.enabled, hsMul, factionMul);
```

派系乘在 **v 上**（合成后总伤），之后的暴击 / 爆头照常乘——与 §5.2 的顺序一致；
**不**额外乘到 `average` 上（否则会变成平方）。DoT 端仍各自乘一次（原来是**正确的**，不改）。

**验证**（新增 `checks/faction-hit.mjs`，12 项）

```
膛线 + 对 Grineer +30%：
  单弹头 76.370 → 99.281（×1.3）
  单次射击 / 爆发 / 持续 全部 ×1.3
  DoT 每层秒伤 / 六秒总伤 ×1.3（原本就对）
  打 Corpus：全部不变（异派系不加成）
  面板总伤不随派系变化（派系只作用于命中结算）
  单弹头 = 合成总伤 × 1.3 × 暴击期望（证明只乘一次）
```

**回归**：16 个页面校对脚本 + `faction-hit` 全绿；单元测试 424 全绿；
`verify-karak` / `verify-co` / `verify-dot-per-stack` / `verify-elements` 均无失败项。
