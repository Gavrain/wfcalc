# 决策确认规范（必须遵守）

> 需求方 2026-11-05 指定：**凡是可能存在争议的修改，必须先提交建议等确认，并把理由写进文档。**
> 原因：如果不先写在文档里，需求方要在"后续思考过程中"才能看到我的理由，容易先做了再返工。
>
> **本文件是长期约定，不是一次性任务。每次会话开始、每次要改既有口径前都要读。**

## 什么算"可能有争议的修改"

以下任意一条命中，就必须先走确认流程，**不能直接改**：

| 类别 | 例子 |
|---|---|
| **改动已确认的口径** | 乘区归属、公式、结算顺序；之前已确认过的分类规则 |
| **数据取舍** | 收录/剔除某个 Mod、赋能、套装；某类数据要不要建模 |
| **归类判定** | 某把武器归到哪个类；某个属性归到哪个乘区；某条数据算不算"影响伤害" |
| **以我的判断填补缺失** | 导出里拿不到、靠推断补的值；两个来源冲突时选哪个 |
| **改变产出结构** | 字段改名/删除/语义变化，会影响下游计算内核 |
| **范围增减** | 新增/移除一整类数据源或数据层 |

以下**可以直接做**（不争议）：

- 修 bug、修笔误、补测试、补文档
- 纯格式/重构且行为不变
- 需求方已经明确说过的规则，直接落实

## 确认流程

1. **先写进文档**，不要先改代码。在 `decisions.md` 里追加一条「待确认」记录，
   写清楚：**要改什么 / 为什么想这么改 / 证据 / 备选方案 / 不这么改会怎样**。
2. **同时用提问告知需求方**（`ask_user_question` 或直接提问），把上面的要点讲清楚。
3. 需求方确认后，把那条记录状态改成「已确认」，补上确认日期与结论，再动代码。
4. 若需求方驳回，记录也要保留，状态改成「已否决」并写明理由——避免以后又提一遍同样的事。

## 向需求方提问的预设格式（必须遵守）

> 需求方 2026-11-08：「需要加入预设，防止像现在这样你直接给出 AB 两个选项，
> 但我实际并不清楚两个路径有什么差异会导致什么结果。」

需求方不是开发者。抛选项时**重点不是技术名，而是「选了之后你会看到什么变化」**。

### 模板

```markdown
**要决定的事**：<一句话人话>

| 选项 | 是什么（人话） | 选了之后会怎样（你能感知的变化） | 代价 / 风险 |
|---|---|---|---|
| A（推荐） | … | … | … |
| B | … | … | … |

**我推荐 A**，因为 <一句人话理由>。
```

### 硬性要求

1. **禁裸用内部术语**：D-编号、乘区、流水线、schema、import 路径……要么不用，
   要么先加一句人话括号解释（如「`src/manual/`（= 代码放哪的目录名，你不用管）」）。
2. **每个选项必须有一栏「选了之后会怎样」**，写需求方**作为使用者能感知到**的变化，不是代码层变化：
   - ❌ 坏例：「A 统一到 src/manual/，B 统一回顶层 data/manual/」→ 需求方完全不知道差在哪。
   - ✅ 好例：「A 把散落的几份人工数据归到一个固定位置，以后我改数据更快、更不易出错；
     B 迁回老位置、跟已归档的历史文档一致，但以后每加一份新数据都要先想该放哪，容易再乱。」
3. **必须有明确推荐 + 一句人话理由**，让需求方能「无脑选 A」。
4. **不追问**：需求方答了某个选项就照做，不要二次确认。

## 记录格式（写在 `decisions.md`）

```markdown
### D-序号 标题（状态：待确认 / 已确认 / 已否决）

- **日期**：YYYY-MM-DD
- **类别**：改动已确认口径 / 数据取舍 / 归类判定 / 填补缺失 / 结构变化 / 范围增减
- **背景**：为什么要动
- **我的建议**：具体想怎么改
- **理由与证据**：数据实测、出处、交叉校验结果
- **备选方案**：其它做法及各自代价
- **风险 / 不这么改的后果**
- **结论**：（确认后填）需求方意见 + 日期
```

## 已知容易踩的坑（从历史记录来）

这些是之前**先做了再被纠正**的事，作为反面例子，以后同类判断必须先问：

- **近战细类**：我曾按"不建架势所以不需要细类"的逻辑把近战全部归 `melee`，
  但近战专属 Mod（如尼卡纳的 Mod）实际不能装在别的近战武器上 → 已恢复区分。
  **教训**：分类能不能合并，要看"它是否影响数据可用性"，不是看"当前计算会不会用到"。
- **套装**：我曾判断"游戏里没有套装"，实际 `ExportModSet.json` 的 19 条就是套装加成。
  **教训**：数据源里有整块内容时，先核实它在游戏里的含义，再决定收不收。
- **护甲类赋能**：我曾以为"近战·苦痛"加护甲，实际是复制异常状态；真正加护甲的是"近战·坚壁"。
  **教训**：按名字猜效果不可靠，必须看渲染后的完整描述。

## 界面文案：不要自造解释性提示

> 需求方 2026-11-06：
> 「去掉本卡提升后面的提示，并在工作流里面提示不需要这种莫名其妙地提示」

**规则**：界面上只放数值本身，**不要**在数值旁边追加自己编的解释、口径说明、"请注意…"之类的文字。

- ❌ `+165.0%  相对不上这张 · 单次射击`
- ✅ `+165.0%`

判定标准：**这段文字是不是需求方要用户看的？**
如果它只是"我为了让用户理解我做了什么而写的"，就删掉。
需要解释口径时，写在文档（`docs/decisions.md` / 注释）里，不要塞进界面。

同类已踩过的坑：

- 输出区"可装 N 张"这类计数提示 —— 已删（信息噪音）
- 面板表格里重复的口径说明 —— 已删
- 卡片上的"相对不上这张 · <指标名>" —— 本次删除

**例外**：空状态的占位文案（"拖入功能 Mod"）、确有必要的一句错误提示（"劣化槽只能放入功能类 Mod"）
属于 UI 必需，不属于"解释性提示"。
