### D-006 元素合成的配对优先级（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径（表 4.1 与 4.3 互相冲突）
- **背景**：
  表 4.1 写「元素 %Mod **先加总**；各元素加量按该元素归属」；
  表 4.3 写「按 Mod 槽位顺序，从前往后**两两合并**；后放的元素与已存在的单元素配对」。
  两句在"元素数量 > 2"时给出不同结果，例：

  ```
  例 A（两张元素 Mod，武器无自带元素）：面板 10 冲，槽 1 = +90% 火，槽 2 = +90% 毒
  ── 先加总 vs 按槽位：两者都是"火 180 + 毒 180"，**无复合**（没有第二个火/毒可配对）
  例 B（面板自带火）：面板 10 火，槽 1 = +90% 毒，槽 2 = +90% 火
  ── 先加总：面板火 10 + 火Mod 180 = 190 与 毒 180 配 → **毒气 370**
  ── 按槽位：毒(槽1) 与 面板火 10 配 → 毒气 190；火Mod 180 落单 → **毒气 190 + 火 180**
  例 C（三组，问题最直白）：面板 10 火，槽 1 = +90% 火，槽 2 = +90% 毒
  ── 先加总：火 190 与 毒 180 配 → **毒气 370**
  ── 按槽位：面板火 10 与 槽1 火 180 合成"火 190"，槽2 毒无配对 → **火 190 + 毒 180（无复合）**
  → 同一套配置，两种理解给出完全不同的复合结果。
  ```

  另有几条同源问题：
  1. **面板单元素与 Mod 单元素谁先配对**：表 4.4 校验例 2 里是"毒(Mod) + 火(面板)"，说明**不是**严格按槽位序；
  2. **两个相同的 Mod 元素**（两张火卡）是合并成一个槽位，还是两个槽位各自找配对；
  3. **元素加量的载体**（`伤害公式.md` A-14）：同一元素两张卡合计 180% 时，是"新总伤 × 1.8"还是"每张卡各自 × 0.9 再相加"；底座里已有同类型面板伤害时，加量是**加到该类型上**还是**覆盖**。本文取"新总伤 × 总量、加到该类型上"（与校验例 1 的结果一致）；
  4. **镀层类（`co`）的实际层数**："每个异常状态 +X% 伤害"按目标身上已有的层数算，还是按本发期望叠上的层数算。
- **我的建议**：
  §5 的 `applyElements` 按"**面板元素先入槽**（顺序固定为物理之外的面板顺序）、
  **面板元素与 Mod 元素同池按槽位序合并**、**同类型 Mod 元素先合并成一个槽位**"实现。
  —— 这套做法与校验例 2 一致（毒 Mod 与火面板能配上），但需要需求方给一个**反例式的确认**：
  "面板 10 火 + 槽位1 火 + 槽位2 毒"（三组）期望的最终分布是什么？
- **理由与证据**：见上面三组对比算式。表 4.1 与 4.3 各自自洽，只有"两者同时成立时"才有冲突。
- **备选方案**：
  - A. 严格按槽位序合并（含面板元素占一个槽位、位置按武器自带顺序）——可能与"先加总"冲突。
  - B. 先按类型加总再合并（**本方案**）——与 4.1 一致，与校验例 2 一致。
  - C. 引入"面板元素优先级最高、其次是槽位 1 的 Mod"——需要需求方给规则。
- **风险 / 不这么改的后果**：复合元素与实际偏差 → 触发占比（0.3②）、DoT 系数、对目标抗性
  全部跟着错。这是**会算错数字**的一条。
- **结论**：需求方 2026-11-05 选择「**毒气 370**」（即先按类型加总、再两两合成）。
  用例「面板 10 火 + 槽位1 +90% 火 + 槽位2 +90% 毒」已写进 `伤害公式.md` §5.4 与校验例 4；
  剩余两个细问（面板单元素与 Mod 单元素的配对序、跨类型 Mod 卡配对序）沿用"面板元素先入槽 + 槽位序"的默认做法，发现反例再单列。

### D-008 DoT 基础值是否剔除玄骸加成；爆头落在哪一步（状态：已确认：部分与建议相反）

- **日期**：2026-11-05
- **类别**：改动已确认的口径
- **背景**：
  表 6.2 说 DoT 基础值 = 命中伤害中**剔除元素/物理 Mod 加量**后的值。
  **玄骸加成不是 Mod，是武器固有属性**，表里没说剔不剔。
  同源问题：表 3.2 说「爆头对 DoT **适用**」，但 6.2 的四个步骤里没有爆头这一步；
  若落进①（基础命中伤），会被③的派系加成再放大一次（相当于爆头也"两次"）；若作独立乘区则不会。
  另外 6.4 的爆炸「基础伤害 × 30%」到底取哪一版基础伤害（含不含元素加量）也没写。
- **我的建议**：
  1. 玄骸那份**剔除**（与"剔除元素/物理加量"同一精神：DoT 基础值只看武器的"裸"面板 + 基伤 + 多重 + 暴击）；
  2. 爆头作为 **6.2 ④ 之后的独立乘区**（不进①，避免被派系二次放大）；
  3. 爆炸的"基础伤害"取与 DoT 同一版基础值（即同样剔除元素/物理加量）。
- **理由与证据**：需求方在 DoT 口径上反复强调"保留基伤%、多重%、暴击，剔除元素/物理加量"——
  这句话本身就在排除"含 Mod 加量的命中伤"。爆头"两次"没有任何文档依据。
- **备选方案**：
  - A. 玄骸剔除、爆头独立、爆炸同 DoT（**本方案**）。
  - B. 玄骸保留（玄骸是武器固有，等价于面板）、爆头进①。
  - C. 三种组合分别实现为开关：增加实现量，但能对比。
- **风险 / 不这么改的后果**：玄骸武器、爆头（默认 3×）两条线的 DoT 数值偏差。
- **结论**：需求方 2026-11-05 裁定（与我的建议部分相反）：
  1. **玄骸**：「玄骸是固有的」→ **保留在 DoT 基础值里**（不剔除，与 D-017 一致）；
  2. **爆头**：「爆头是开关」→ 作为独立乘区，由用户勾选，**不进①**，因此不会被派系加成二次放大；
  3. **爆炸**：「爆炸是异常状态跟这个不是一个类型」→ 爆炸**单列结算**，不并入 DoT 汇总，也不再强行套用 DoT 基础值。

### D-009 "面板多重"取 multishot 还是 bullets（状态：已确认）

- **日期**：2026-11-05
- **类别**：归类判定 / 数据取舍
- **背景**：
  数据层 `modes[]` 里同时有：
  - `multishot`：= 导出**顶层** `multishot`（`emit.ts` 第 62 行 `multishot: m.baseMultishot`）
  - `bullets`：= 该 behaviour 的 `fireIterations`

  `research/01` 第 3 节第 3 条实测：两者**经常不等**（Strun Vandal 顶层 10 / behaviour 10；
  Soma 第二个 behaviour `fireIterations: 8` 却是"特殊状态"不是"8 连发"）。
  表 2.2 只说"面板多重就是基础值"，没说取哪个量、`bullets` 是否也要乘进单次射击伤害。
- **我的建议**：以 `modes[].multishot`（顶层）作为"面板多重"，`bullets` **不参与**伤害计算，
  只做数据溯源；对 `bullets > 1` 且确为多弹丸的武器（霰弹），以需求方人工确认为准。
- **理由与证据**：顶层 `multishot` 才是游戏面板显示的那个数；`fireIterations` 在同一字段位
  既承载"霰弹弹丸数"又承载"特殊状态段"，语义不纯。
- **备选方案**：
  - A. 只用 `modes[].multishot`（**本方案**）。
  - B. 用 `max(multishot, bullets)`：可能把特殊段算进伤害。
  - C. 两者都乘：会重复计算（霰弹枪顶层 multishot 已经含弹丸）。
- **风险 / 不这么改的后果**：霰弹类与多段武器单次伤害量级偏差，DPS 全部跟着偏。
- **结论**：需求方 2026-11-05 选择「只用 `modes[].multishot`」，`bullets` 不参与伤害计算（仅做数据溯源）。

### D-011 core 类型与数据层字段名不一致（状态：已确认）

- **背景**：

- **风险 / 不这么改的后果**：类型与数据"看起来能跑"，实际字段名对不上，运行期 undefined。
- **结论**：需求方 2026-11-05 确认「**类型改为与 data 输出逐字段对齐**，并补输出 `sourceKey` / `override`」。
  即：`weapon.ts` 以 `emit.ts` 的实际输出为准；计算需用而 emit 未输出的字段（`sourceKey`、`override`、灵化基伤标记）在 emit 侧补齐。

### D-012 爆头 × 暴击：整体 ×2 还是总爆伤翻倍（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径
- **背景**：
  表 3.2 原文：「爆头时若产生暴击，最终伤害直接 ×2（等效于总爆伤翻倍，再按 3.1 公式算）」。
  这两句话在 `cd ≠ 2` 时**不等价**：
  ```
  整体 ×2      ：期望倍率 = [cc(cd−1)+1] × 2
  总爆伤翻倍   ：期望倍率 = cc(2cd−1)+1
  例 cc=100%, cd=4 → 整体 ×2 = 2×3 = 6；翻倍 = 1×7+1 = 8
  ```

### D-017 玄骸加成在基伤之前（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径（同时修正 `乘区归属表.md` 表 4.4 的一句）
- **背景**：
  需求方在回答 D-006 时补充裁定：**「玄骸应该在基伤之前，玄骸加成体现在武器面板基伤内」**。
  这与表 4.4 现有两条写法不一致，必须显式修正，否则内核会在错误的位置乘玄骸：

  | 表 4.4 原文 | 与新裁定的关系 |
  |---|---|
  | 玄骸加成 = **独立乘区**，作用于面板伤害，形成"新面板" | 方向正确（玄骸确实在面板侧），但"独立乘区"容易被实现成"在元素之后单独乘一个括号" |
  | **「玄骸加成自身不会被再乘一次」**（数值固定为 `面板总伤 × 比例`） | **被推翻**。既然玄骸在面板基伤内，它就必须吃 `(1+Σ基伤Mod%+镀层%)` |
  | 校验例 2：面板 40，60% 磁力 → 磁力 **24**，新总伤 64 | **保留**。见下方"两种读法都算 24 的原因" |

  关键推导（为什么"吃基伤"与"24"能同时成立）：
  ```
  设面板总额 T0 = 40，玄骸比例 r = 60%，基伤加成 G（例中 G = 0）

  读法甲（玄骸金额按面板总额算）：玄骸 = T0 × r × G = 24 × G = 24 ✅
  读法乙（玄骸与面板同乘、再减回）：玄骸 = T0×(1+r)×G − T0×G = T0×r×G = 24 ✅
  → 两种写法在代数上等价，都等于「T0 × r × 整体基伤系数」。
  真正的区别不在 24 这个数，而在于**玄骸是否进入元素 % 的基数**：
    旧口径（表 4.5）：新总伤 = T0×(1+r)，玄骸不进元素%  → 元素% 基数 64
    新口径（D-017）  ：新总伤 = T0×(1+r)×G，玄骸进面板    → 元素% 基数 64×G
  ```
- **我的建议（已采纳）**：
  1. 新增前置函数 `applyKuvaBonus`：`玄骸加量 = 面板总伤 × 比例`，并入面板（物理型并入同物理类型）；
  2. 基伤 `(1+Σ基伤Mod%+镀层%)` 随后作用于"含玄骸的面板"，玄骸因此**吃基伤加成**；
  3. 元素 % 的基数 = 基伤之后的总伤（含玄骸），**这是修正后的准确含义**：
     "玄骸不被元素 % 再乘一次"仍然成立（元素 % 只算元素槽位，玄骸金额已定死），
     但"玄骸不进元素 % 基数"**不再成立**。
  4. `乘区归属表.md` 不直接改（已定稿文档走确认流程），差异记录在本条与 `伤害公式.md` §5。
- **理由与证据**：
  - 需求方原话："玄骸应该在基伤之前，玄骸加成体现在武器面板基伤内"；
  - 数值自洽性：若玄骸既在面板内、又"不被再乘一次"，就必须判定它是否在基伤括号内；
    需求方已明确在**基伤括号内**，因此它吃基伤加成。
- **备选方案**：
  - A. 玄骸前置并吃基伤（**本方案**，与需求方原话一致）。
  - B. 玄骸前置但不吃基伤（把"不再被乘一次"理解为"连基伤也不吃"）——与"体现在面板基伤内"矛盾。
  - C. 玄骸留在元素之后（旧写法）——需求方已否决。
- **风险 / 不这么改的后果**：
  - 玄骸武器（Kuva / Tenet / Coda 系，含冲击型）的基伤 Mod 收益与元素分布会偏；
  - 例 2 的 24 不会变（两种读法同值），所以**只靠例 2 无法发现这个错误**，必须用带基伤 Mod 的用例。
  - 待补一条校验：面板 40、60% 磁力、+165% 基伤 ⇒ 玄骸 = 24 × 2.65 = 63.6，新总伤 = (40+24)×2.65 = 169.6。
- **结论**：需求方 2026-11-05 确认。`伤害公式.md` §3 / §5 已按此顺序重排，`core` 侧的 `spreadTotalAfterMods` 注释需同步修正。

- **需求方原话（2026-11-05 第二次）**：
  > D-022 还有一点，如果玄骸加成类型是冲击，是可以享受到冲击类型 mod 加成的，
  > 所以建议统一建模逻辑，物理或元素类都是基于玄骸加成后的新面板计算。
- **为什么这次推翻了第一次结论**：第一轮我问的是「元素基数含不含物理 %Mod」，
  需求方答「不含物理 mod，物理 mod 跟元素 mod 的行为类似，只是基础值限定为对应类型面板」。
  但这留下一个**不一致**：玄骸若是冲击，它会被并入面板冲击，那它到底享不享受 `+冲击%` Mod？
  按第一轮字面（物理基数 = 自身面板值）应该享受；按元素那一侧（基数不含物理%）又说不通。
  **这一轮给了统一答案**：两边的基数都取「玄骸加成后的新面板」，即：
  ```
  新面板 = 面板伤害 × (1 + 玄骸比例)        ← 玄骸并入面板（D-017）
  物理 %Mod 加量 = 该物理类型在新面板里的值 × Σ物理Mod%
  元素 %Mod 加量 = 新面板总伤 × Σ元素Mod%
  ```
- **由此推出**：玄骸若是**冲击**，它的那份会并入新面板的冲击里，
  再被 `+冲击%` Mod 放大 —— 这与 §4.4「冲击类型：与面板冲击合并为同一类型，
  并享受物理% Mod 增幅（与面板冲击同待遇）」**完全一致**，是文档本来的意思。
- **对校验例 1 的影响**：`100 冲 + 100 切，+100% 冲、+100% 毒`（**无玄骸**）：
  新面板总伤 = 200，物理加量 **不**进元素基数 ⇒ 毒 = 200 × 100% = **200**（表 4.1 原文）。
  → **表 4.1 的「毒 200」与「统一基于新面板」并不矛盾**：那条校验例没有玄骸，
  物理 %Mod 是"从面板出发"的加量，只放大自身类型，不是玄骸份额。
- **结论**：实现改为"物理与元素都基于玄骸加成后的新面板取值"，
  物理加量只作用于该类型（不进元素基数），元素加量取新面板总伤。

  > 最多叠加 y 次」。假设目标此时身上具有 **a 种**异常状态，则增加 **x% × a × y** 的镀层类伤害乘区。

  ```
  镀层类加量 = x% × a × y
  ```

  所以数据层 `conditions` 为空、没有 `maxStacks` 是**正常的**，`y` 恒为 1。
  已写进 `adapter.ts` 的 `conditionOverloadMaxStacks()`（常驻型返回 1）并补了数据层测试。

  已记入 `data-todo/README.md` 第 4c 节。
- **UI（已实现）**：`a`（目标异常状态种类数）做成下拉框，默认 **0**（无异常时镀层不生效）；
  `y`（叠层层数）做成下拉框，选项 0..maxStacks，**默认取最大值**。

  - B. `镀层% = x% × a`（忽略增益层数）——与"最多叠加 y 次"的描述矛盾。
  - C. `a` 取异常状态**总层数**——与 "per Status Type"（每种类型）矛盾。
- **风险 / 不这么改的后果**：带镀层 Mod 的配置基伤会差 `2~3` 倍（x×a×y 的乘数很大）。
- **结论**：需求方 2026-11-05 确认算法；`core` 的 `overForStacks(contribs, coStacks, statusTypes)`

### D-036 异常状态层数单位错误（bug，已修）

### D-037 装填 / 弹匣 Mod 属于「影响伤害」，且内核此前完全没算它们（状态：已确认）

- **日期**：2026-11-05
- **类别**：修 bug + 归类修正
- **需求方原话**：
  > 「装填 mod 被误归类为功能性了，他们影响装填的数值，对持续射击伤害有影响。」
  > 「mod 的收益率好像有问题，我看到了大量负数。」
- **问题一：数据标注**。`mods.json` 里 `reloadSpeed`（装填速度）与 `magazine`（弹匣容量）
  都被标成 `kind: functional` / `bucket: utility`。但持续伤害口径是：
  ```
  持续伤害 = 单次射击 × 弹匣 ÷ (弹匣 ÷ 射速 + 装填时间)
  装填时间 = 面板装填 ÷ (1 + Σ装填速度%)
  ```
  两者**都直接改变持续伤害**，不属于"不影响伤害的功能类"。
- **问题二（更严重）：内核根本没算它们**。`adapter.ts` 的 `toContribStat`

  **即：装填 Mod、弹匣 Mod 的加成一个都没进过计算。**
- **修法**：
  1. `ContribStat` / `BucketableStat` 增加 `magazine`、`reloadSpeed`；
  2. `toContribStat` 补上这两个分支；
  3. `buildOutput` 用 `bucket(面板弹匣, 'magazine')` 与
     `面板装填 ÷ (1 + Σ装填速度%)`；
  4. demo 的 `isExilusMod` 增加 `DAMAGE_AFFECTING_STATS` 黑名单，
     装填/弹匣类**不再能进劣化槽**。
- **验证**：卡拉克 + 爆发装填 → 持续伤害 +5.37%；+ 弹匣增幅 → +5.37%。
- **问题三：备选区增幅出现大量负数**。原因是模拟放置时**直接替换槽位 1**，
  把原本已装备的 Mod 收益一起算掉了。
  改为 `simulateEquip()`：找**第一个空位**装上，8 槽全满则返回 `null`（显示「—」）。
- **结论**：确认并修复。

### D-043 「每层秒伤」= 单层 DoT 的每秒伤害，与层数、射速都无关

- **日期**：2026-11-05
- **类别**：**口径澄清**（此前实现按"每秒叠层 × 每跳"理解，与需求方意图不符）
- **需求方原话**：
  > 「射速怎么会影响 dot 每层秒伤的」
  > 「每层秒伤的意思是单层 dot，他应该是只考虑触发一层的秒伤，跟层数无关。六秒总伤才考虑这部分。」
- **两个口径必须分开**：
  `
  每层秒伤   = 单层 DoT 每秒造成的伤害
             = ② 基础触发值 × ③ 各项加成（元素% × 异常伤害% × 派系% × 爆头）
             **不含**层数、**不含**射速、**不含**多重
  六秒总伤   = Σ 各类型（每秒叠层 × 每层秒伤 × 6 秒）
             这里才乘射速、多重、触发几率
  `
- **此前实现的错误**：dotPerSecond 把两者混在一起 ——
  perSecond = stacksPerShot × 射速 × 每跳，即"每秒叠层 × 每跳"。
  结果**射速会直接影响"每层秒伤"**，不符合"每层"的语义。
- **修正**：
  - 每层秒伤（dotPerSecond / 界面「DoT 每层秒伤」）→ 取**单层值** 	ick 之和，
    与射速、多重、层数无关；
  - 六秒总伤（dot6s）→ 仍按「每秒叠层 × 每层秒伤 × 6」累计。
- **影响**：改完后「DoT 每层秒伤」会大幅下降（不再乘射速与层数），
  但**六秒总伤口径不变**，伤害结论以六秒总伤为准。
- **结论**：确认并实现。

### D-055 配装里没有的元素不触发，DoT 必须为 0（bug）

- **日期**：2026-11-05
- **类别**：修 bug（DoT 结算）
- **需求方原话**：
  > 「异常状态那边，如果配出来的元素里面没有，那他是 0 层，那秒伤也应该是 0，请务必注意这点，
  >   伤害里面的 dot 每秒总伤也应该只计算有的元素。没有的是不会被触发的！虽然他有基础值。」
- **根因**：`dotTick` 的 ① 基础值按 §6.2 取的是**全类型之和**，
  所以即使配装里没有毒/火/电，也能算出一个非零的「每跳伤害」。
  而 `buildOutput` 直接把 `tick.tick` 记成 `dotPerType`，**没有判断该元素是否存在**，
  导致合计虚增。
- **实测（卡拉克 + 仅基伤 Mod，命中只有 冲击/穿刺/切割/火焰）**：

  类型      层数/秒    每层秒伤

  electric  0.000     61.096     ← 同上
  gas       0.000     61.096     ← 同上
  slash     0.949     42.767     ← 存在，正确
  合计      287.153  →  应为 103.864（虚增 183）
  `
- **修正**：新增 `hasDotElement(spread, type)`，判据是**该类型是否出现在命中伤害分布里**。
  不存在时层数与每层秒伤一律记 0，且不计入 `dotPerSecond` / `dot6s`。
  爆炸（blast）同理——配装里没有爆炸元素时 `perStack` / `perSecond` 归 0。
- **口径确认**：这符合 §0.3「触发池由命中伤害里实际存在的类型构成」，
  也与 §6.2 不矛盾：① 的全类型之和只是算 DoT **伤害值**的基数，
  不代表该元素会被触发。
- **验证**：新增 6 项专项回归（只配切割时其余全 0、加火 Mod 后才变非零、

### D-060 「DoT 加权每层秒伤」：按触发占比加权

- **日期**：2026-11-05
- **类别**：**改输出口径**
- **需求方原话**：
  > 「DoT 每层秒伤需要根据触发占比加权，因为是会互相抢触发的。
  >   改成加权 Dot 加权每层秒伤」
- **问题**：原 `dotPerSecond` 把各类型的每层秒伤**直接相加**，
  隐含"每种 DoT 都 100% 会触发"，但实际**触发是互斥的**：
  一次触发只能落在一个类型上，各类型按其在伤害分布里的**占比**分到触发机会。
- **改法**：
  `
  加权每层秒伤 = Σ_t ( 该类型每层秒伤 × 该类型占比 )
  占比_t      = 命中分布中该类型的伤害 ÷ 命中总伤
  `
- **举例**（切割 100 + 火焰 100，各占 50%）：
  `
              每层秒伤   占比    加权
  火焰         100.00    50%    50.00
  切割          35.00    50%    17.50
  合计        135.00           67.50   ← 原来是 135（虚高约 2 倍）
  `
- **命名**：口径标签改为 **`DoT 加权每层秒伤`**。
- **影响范围**：只改「每层秒伤」这一个展示口径；
  **六秒异常状态总伤的算法不变**（那里本来就用 `stacksPerShot` 乘了占比，
  已经是加权的，不存在重复加权问题）。
- **结论**：确认并实现。
**实现记录（D-060）**

- `buildOutput` 里 `dotPerSecond` 的累加改为加权：
  `js
  const shareOfType = spreadTotal(res.finalHit) > 0
    ? (res.finalHit[tick.type] ?? 0) / spreadTotal(res.finalHit) : 0;
  dotPerSecond += perStackPerSecond * shareOfType;
  `
- `dotPerType[t]` 仍存**未加权**的原始每层秒伤，供界面逐类型展示与排查。
- 口径标签：`DoT 每层秒伤` → **`DoT 加权每层秒伤`**（`main.ts` / `analysis.ts` 同步）。
- **六秒异常状态总伤不受影响** —— 那里本来就用 `stacksPerShot`（已含占比）算层数，
  避免重复加权。
- **验证**：新增 7 项回归（各占 50% 时合计减半、单类型占 100% 时不变、
  `dotPerType` 仍为原始值、名称已改）。内核测试 **231 全绿**。

### D-065 确认暴击分档语义（299% = 99% 三级 + 1% 二级）

- **日期**：2026-11-06
- **类别**：确认口径（无需改代码，已有实现即正确）

  `
  k = floor(cc)        → 当前档位
  f = cc − k           → 进入下一档的概率
  第 k 档概率 = 1 − f
  第 k+1 档概率 = f
  档位倍率 = 1 + k × (cd − 1)
  `
  | 暴率 | 分档 |
  |---|---|
  | 99% | 1% 白字（k=0）+ 99% 一级 |
  | 150% | 50% 二级 + 50% 三级 |
  | 200% | 100% 二级 |
  | **299%** | **1% 二级 + 99% 三级** |

- **代码状态**：`critTiers()` 本来就按这个实现，**无需修改**。
  本轮只补断言把语义锁死，防止将来被"优化"成线性公式。
- **补充**：DoT 的爆头倍率走 `expectedHitMultiplier`，它内部用 `critTiers` 分档，

### D-067 装填空窗改用毫秒精度计时（修射速负收益）

- **日期**：2026-11-06
- **类别**：**改结算口径**（六秒曲线的计时精度）
- **需求方原话**：
  > 「观察到一个问题，上了灵敏扳机和撕裂p之后，私发热诚对异常状态总伤是负收益，这不符合逻辑。」
  > 「射速越高总伤越高才对，只是因为弹匣打空可能导致提前装填出现 0 收益或者收益很低
  >   但不可能是负的。你需要正确计入装填的起始时间和装填完毕时间，可以以毫秒为精度计算」
- **复现（卡拉克，膛线 + 灵敏扳机 + 撕裂P）**：
  `
  射速 25.083 → 六秒总伤 4778.08
  射速 30.333 → 六秒总伤 4494.11   ← 加了私法热诚反而 -5.94%
  `
- **根因**：`buildFiringTimeline` 用**整秒**判定开火/装填（取该秒中点 `sec−0.5` 落在
  循环的哪一段），导致开火秒数是**阶梯函数**：
  `
  射速 11.67 → 6 秒全开火
  射速 16.92 → 4 秒开火
  射速 25.08 → 5 秒开火   ← 反常地比 16.92 还多
  射速 30.33 → 4 秒开火   ← 又掉回去，于是"加射速 = 负收益"
  `
- **修正**：改为**毫秒精度的连续时间线**。
  `
  循环 = 打空弹匣(mag ÷ 射速 秒) + 装填(reload 秒)
  对窗口内每一毫秒判定该时刻是否在开火期
  第 t 秒的开火占比 = 该秒内开火毫秒数 ÷ 1000
  叠层按占比折算：实际叠层 = 每秒叠层 × 开火占比
  `
  这样射速单调提升叠层，弹匣打空只会让收益**变小**（甚至趋近 0），不会为负。
- **结论**：已修正。
**实现记录（D-067）**

- 新增 `isFiringAt(mag, fr, reload, t)`：按真实时间判定某时刻是否在开火；
  `buildFiringTimeline` 保留为兼容签名（整秒开关）。
- 新增 `firingFraction(mag, fr, reload, sec)`：把第 sec 秒切成 **1000 毫秒**，
  统计落在开火期内的毫秒数 → 返回 `[0,1]` 的开火占比。
- `dotSixSecondCurve` 的 `firing` 参数改为接收**占比**（0~1）；
  为兼容旧调用方，布尔值 `true/false` 仍按 `1/0` 解释。
- `buildOutput` 改用 `firingFraction`。
- **修复前后对比**（卡拉克 + 膛线 + 灵敏扳机 + 撕裂P）：
  `
                        修复前            修复后
  射速 25.083          4778.08          4295.49
  射速 30.333          4494.11 (-5.94%) 4884.45 (+13.71%)
  `
- **单调性验证**：射速 5 → 60（步长 2.5）共 23 档，总伤**单调不减**；
  「私法热诚 +45% 射速」在基础射速 10/15/20/25/30/40/50 下收益
  分别为 35.72% / 26.14% / 29.31% / 28.24% / 23.06% / 15.37% / 20.16%，**恒为正**。

### D-072 元素 Mod 是否移到暴击之后（状态：待确认）

- **日期**：2026-11-06
- **类别**：改变结算顺序（已确认口径）
- **需求方原话**：
  > 「元素 mod 移到暴击之后似乎更合适，因为 dot 的基础值取的就是没有元素 mod 的那个值。」
- **现状核对（实测）**：`resolveSegment()` 的顺序是
  `① 玄骸 → ② 基伤 → ③④ 元素加量/合成 → ⑤ 暴击`。
  元素 Mod **确实在暴击之前**就并进了命中分布 `finalHit`。
  但 **DoT 基础值 `dotBaseRaw` 走的是另一条分支**（`applyElements(..., 'dotBase')`，
  元素/物理加量被置 0），所以 DoT 基础值里**本来就没有元素 Mod**。

  ⇒ 也就是说：需求方观察到的「DoT 基础值不含元素 Mod」**已经成立**，
  与「元素 Mod 算在暴击之前还是之后」**并不冲突**——两者是不同的东西：
  前者是 `dotBase` 分支的输入，后者是 `finalHit` 分支的顺序。

- **真正会变的数**：如果把元素 Mod 挪到暴击之后（即「先暴击、再按暴击后的值算元素加量」），会改变：
  1. `finalHit` 里元素的**加量基数**。现在是 `tNew = 玄骸+基伤后总伤`；
     挪用后若按暴击后总伤做基数，元素加量会被暴击期望放大 → **命中伤害整体变高**；
  2. 但 `finalHit` 本身是「未暴击的分布」，暴击是在其后乘期望倍率的。
     若元素加量改吃暴击后的基数，等于让元素也吃一次暴击期望，再在 L6 乘一次 → **重复放大**。
- **我的建议**：**不建议移动**。理由：
  - 元素 % 的口径（A-14 / C-04 / D-022）明确是「基数 = 玄骸加成后的新面板总伤」，
    与暴击无关；把它挪到暴击后会让这条已确认口径作废；
  - 若目的是「DoT 基础值不含元素 Mod」，**这一点已经实现**，不需要动顺序。
- **备选方案**：
  - A. 不动（**建议**）：维持 `玄骸 → 基伤 → 元素 → 暴击`；
  - B. 只把「代码结构」重排成暴击在前、但元素加的仍是基伤后基数（纯重构，数值不变）；
  - C. 真的让元素加量吃暴击后基数（会改变数值，需确认预期效果）。
- **风险 / 不这么改的后果**：选 C 会让所有带元素 Mod 的配装命中伤害偏高，
  且与 DoT 基础值的口径进一步不一致（DoT 基础值会显著低于命中伤害的元素部分）。
- **结论**：（待需求方选择 A / B / C）

### D-077 `resolveSegment` 重复计算 + `state` 只覆盖主段（状态：已修）

- **日期**：2026-11-06
- **类别**：bug 修复（D-075 遗留；不改口径）
- **需求方提问**：「`resolveSegment()` 是什么，为什么要再走一遍」
- **`resolveSegment()` 是什么**：结算**一个伤害段**。一个 `AttackMode` 里可以有多个段
  （`impact` 直接命中 / `attack` 飞行体命中 / `explosiveAttack` 爆炸 / `embedDeathAttack`），
  每段是独立伤害向量，各自走 玄骸 → 基伤 → 元素 → 暴击 → DoT。
- **两个问题**：
  1. **重复计算**：`compute()` 先 `mode.segments.map(resolveSegment)` 算一遍，
     又调 `buildState()` 把主段再算一遍；
  2. **覆盖面不足**（更严重）：`state` 只取 `mode.segments[0]`，**其余段完全不在 state 里**。
     实测 Astilla Prime（4 段）：`state.命中分布总伤 = 3.0`（只主段），
     而 `totalSpread = 343.0`（所有段）。**60 把多段武器**受影响。
     —— 上一轮报告里「结果与 state 完全一致」的说法因此不成立：测试只覆盖了单段武器。
- **修复**：
  - `resolveSegment(ctx, seg, upstream?)` 增加可选上游；传了就**直接取 computed**，
    不再重跑玄骸/基伤；不传则自行计算（保持独立调用能力）。
  - `compute()` 先 `mode.segments.map(segmentUpstream)` 得到每段的上游，**只算一次**；
    逐段结算与 state 共用同一份。
  - 新增 `ComputeResult.perSegment: WeaponState[]`，**每段各有完整 computed**。
    `state` 保持为「主段」语义不变。
- **连带发现并修复**：`state` 的 `基伤面板` 只写了 `1 + Σ基伤%`，**漏掉镀层类 `overForStacks`**，
  导致镀层 Mod 在 state 里完全不生效（`verify-co.mjs` 的 `a=1/2/3` 三项当场失败）。
  → 补齐 `基伤系数 = (1+Σ基伤%) + 镀层加量`，且**爆炸段不吃镀层**（与 `applyBaseDamage` 逐字一致）。
  `overForStacks` 随之从 `main.ts` 移到 `weapon-state.ts`（否则 main ↔ weapon-state 循环依赖），
  `main.ts` 原样转出保持导出面不变。
- **验证**：
  - `weapon-state.test.ts` 增至 **14 项**：新增多段武器 4 项（`perSegment` 覆盖、逐段与
    `segments` 一致、多段合计 = `totalSpread`）、镀层 2 项；
  - 镀层测试做过**反向验证**：临时回退修复后该测试确实失败，恢复后通过；
  - 全量 **296 项全绿**，`demo:check` 124 项全过，`build:data` 产出与上一版一致。

### D-080 命中 / 爆炸改为「模式内的独立面板变体」（状态：已确认：实施）

- **日期**：2026-11-06
- **类别**：产出结构变更（`modes[].segments[]` → 模式内的面板变体）
- **需求方原话**：
  > 「而且也不应该作为伤害段计算，应该跟不同模式一样体现为不同面板。
  >  以主武器为例，可以分为主模式直接命中 主模式爆炸，次要模式直接命中，次要模式爆炸，

- **需求方对拆法的裁定**（追问后）：
  > 「各自独立面板，独立查看与配装，否则没有办法解决有的模式触发与暴击不一致，
  >  而且通常对于这种武器，只聚焦于其中一个模式。而且如果都显示在面板上，会很拥挤。」
  > 命名方式：「保留 role，只把命中/爆炸作为子项」
- **问题**：现在 `modes[].segments[]` 把「命中」和「爆炸」放在**同一个模式**里，
  它们共享同一套面板（暴击率 / 触发率 / 射速），但实际上**两段的触发与暴击并不一致**；
  而且界面把两段塞在同一个面板里，看起来很挤。
- **改法**：
  1. `AttackMode` 增加 `variants: ModeVariant[]`，每个变体 = 一个独立面板：
     ```
     interface ModeVariant {
       id: string;            // 'direct' | 'blast'
       label: string;         // '直接命中' | '爆炸'
       segments: DamageSegment[];   // 通常只有 1 段
       override?: {...};      // 该变体自己的面板覆盖（与模式级 override 同一套字段）
     }
     ```
  2. **保留 `role`**（normal / charged / incarnon），变体只是模式内的子项；
  3. 面板取值顺序：**变体 override → 模式 override → 武器级**（新增一层，D-050 的延伸）；
  4. 界面：模式切换栏保持"主模式 / 次要模式 / 灵化模式"，
     模式内部再切换「直接命中 / 爆炸」，**两个变体不同时铺开**（避免拥挤）；
  5. 每个变体**独立配装**：命中与爆炸分别有自己的 Mod 配置。
- **兼容**：只有 1 个段的模式 → 只有 1 个变体，界面不显示变体切换（行为不变）。
- **影响面**：主武器 81 把、副武器 36 把、近战 24 把、Archgun 17 把「含多段模式」。
- **备选方案**：
  - A. **变体（本方案）**：保留 role，模式内切子项 —— 需求方选定；
  - B. 把每段直接拍平成顶层 mode（如 `primary_direct` / `primary_blast`）：
    切换栏会变得很长，且丢失「这两个属于同一个主模式」的信息；
  - C. 维持现状（段）—— 无法解决两段面板不一致。
- **风险**：产出结构变化，读取 `modes[].segments` 的代码需同步；
  demo 的模式切换、`perSegment` 语义要跟着调整。
- **结论**：按 A 实施。`segments` 保留为变体内部的实现细节（单段）。

### D-081 镀层/异况类基伤：每张卡 +80% / 每种异常状态（状态：**已实现**）

- **日期**：2026-11-06
- **类别**：改动已确认的口径（D-024 的「每层百分比 × 叠层上限」算法）
- **需求方原话**：
  > 「镀层步枪才能应该 80% 伤害/异常状态，配置那需要一个框设置怪物身上的异常状态数。其他的镀层基伤 mod 也要修改下。」
- **背景**：
  数据层从 ZKMODS 拿到的 `co` 满级值各不相同：异况超量 80、镀层 步枪才能 20、
  镀层 准确射手 30、镀层 通晓霰弹枪 20；而内核 `overForStacks` 又按
  `加量 = amount/100 × a × y` 乘一次叠层上限，导致同一套「80%」被解释了两次。
- **我的建议**：
  1. 数据层：四张卡的 `co` **满级统一 +80%**，逐级线性（第 r 级 = 80 × r / 等级上限）；
  2. 内核：`加量 = 80% × a`（a = 目标身上异常状态**种类数**），**不乘叠层上限 y**；
  3. 适配层把「每张卡满级值」折算成内核的单层贡献（80 / maxStacks），
     内核再乘回 maxStacks 时恰好等于 80，避免同一口径在两处重复解释；
  4. UI：配置区加「怪物身上异常状态数」输入框（映射到已有的 `CtxOptions.coStatusTypes`）。
- **理由与证据**：
  - 需求方原话点名「镀层步枪才能应该 80%」，且要求「其他的镀层基伤 mod 也要修改」；
  - 旧算法在「两张镀层卡 + 5 种异常」时会出现 80×5×2 + 20×5×2 一类的重复放大，
    与「每张卡 80% / 每种异常」相矛盾。
- **备选方案**：
  - A. 只改数据不改内核（保留 ×y）：仍会出现「每层值 × 层数」的双重解释；
  - B. 改内核、把 y 从公式里拿掉（**本方案**）：每张卡各自 80%，加量 = 80% × a；
  - C. 每张卡分别乘自己的 y：同一套口径下 a 相同、y 不同时「配第二张卡」的边际收益 = 80%，
    单卡时与 B 一致、多卡时 C 更大。**C 目前未采纳**，需求方若想改，
    只需让 `overForStacks` 的 `y` 不再统一相乘即可。
- **风险 / 不这么改的后果**：若按 C 解释，UI 还要给每张卡单独设层数，配置区会变复杂。
- **结论**：（**已被下方「D-081 修订（第二次）」取代**，见 D-083 之后的章节）按 B 实现。数据层 `CO_OVERLOAD_PERCENT = 80`（`stat-map.ts` / `clean-mods.ts` /
  `adapter.ts` 三处同值），测试锁定「单层贡献 × y = 80」。

### D-084 弹药效率建模（状态：**待确认口径写法**，代码已实现）

- **日期**：2026-11-06
- **类别**：新增乘区（`ammoEfficiency`）/ 影响面板展示
- **需求方原话**：
  > 「准星上面还有一个弹药效率词条，这个从现在开始建模。弹药消耗可以出现非整数，
  > 但是为了方便计算，我们把他视为等效增加最大弹药和弹匣数量。假设弹药效率为 x，
  > 则提升的弹匣和弹药 a 为 a/(1-x)。面板上弹匣显示两位小数。」
- **背景**：
  弹药效率此前完全不建模。数据里已有 3 个 Mod 带 `ammoeff`（头脑风暴 / 头颅射击 / 无尽弹雨，
  满级 3~5%），赋能「主要·准星」满层每层 +6% × 10 层 = **60%**。
  但 `arcaneToContributions` 旧实现只取数值槽里的**第一个**数字，
  准星的第二词条（弹药效率）被整个丢掉。
- **实施**：
  1. 新增 `ContribStat: 'ammoEfficiency'`，进 `BucketableStat`（弹匣同属 utility 但不乘进伤害）；
  2. 适配层：Mod 的 `ammoEfficiency` 由 `utility` 放行；赋能的数值槽按**每个带词条名的槽独立成条**
     （`[0].STATUS_CHANCE` / `[0].AMMO_EFF` 各算一条），裸 `.val` 无词条名则忽略
     （否则无情的装填速度会被当成基伤再加一遍）；
  3. 内核：`ammoEfficiencyMultiplier()` = `1/(1-x)`，`等效弹匣 = 面板弹匣 × 倍数`，
     `displayMagazine()` 保留两位小数。
- **⚠ 口径待确认（唯一分歧点）**：
  需求方写的是「提升的弹匣和弹药 a 为 `a/(1-x)`」。按字面，`x = 0.6` 时等效弹匣会变成
  `a × 2.5`；但按"弹药效率 = 每发只消耗 `1-x` 发"的定义，`a/(1-x)` 其实是**能开多少次**，
  额外多出来的部分是 `a · x/(1-x)`（`x = 0.6` 时为 `a × 1.5`）。
  本实现取 **`1/(1-x)`**（即"使用次数倍数"），因为它与常见游戏内表现一致：
  50% 弹药效率 = 弹匣翻倍。
  - 若需求方的本意是 `a/(1-x)` 就直接加到原弹匣上（`x = 1` 趋于无穷），
    只需把 `ammoEfficiencyMultiplier()` 改成 `1 + 1/(1-x)` 即可，改动一处。
- **备选方案**：
  - A. `倍数 = 1/(1-x)`（**本实现**，50% → 翻倍）；
  - B. `倍数 = 1 + 1/(1-x)`（严格按字面 `a + a/(1-x)`）；
  - C. `倍数 = 1/(1-x)` 但 `x` 用"每发消耗 1-x"直接算使用次数（与 A 等价，只是单位不同）。
- **风险 / 不这么改的后果**：若按 B，弹药效率 50% 时弹匣 = 3a，与实际严重不符。
- **结论**：先按 A 实现并测试锁定；**等需求方确认 `x=0.6 → 弹匣 ×2.5` 还是 `×1.5`**。

### D-118 弱点伤害接线；主要·死首改成「基伤 ×3 层 + 弱点伤害（不叠加）」（状态：**已确认 / 已实施**，需求方 2026-11-06）

```
headshotMultiplier = 敌人爆头倍率 × (1 + Σ爆头伤害% + Σ弱点伤害%)     // core/src/crit.ts
```

爆头开关**没勾**时，`damageLine(..., ctx.headshot.enabled, hsMul)` 整段不用这个倍率——
与之前"爆头是开关"的口径一致（D-012 / D-020 不变）。

**界面**：「爆头倍率」勾选框的标题改为「**弱点/爆头倍率**」，悬停提示「目前版本弱点伤害等同于爆头」。

**② 主要·死首**

| 词条 | 数据（每层） | 层数 | 之前 | 现在 |
|---|---|---|---|---|
| 基伤 | 120% | **3**（描述 *Stacks up to 3x*） | +360% ✅ | +360%（不变） |
| 弱点伤害 | 30% | **1**（不随层数叠加） | 无（被忽略） | **+30%** |
| 后坐力 | -50% | — | 忽略 | 忽略（无对应乘区） |

`ARCANE_EFFECT_CAPS` 新增 `PrimaryDamageOnNoMelee: { VAL: 30 }`，`arcaneDisplayStats()`

### D-135 派系伤害对命中伤害生效（状态：**已修复**，需求方 2026-11-06）

- **需求方原话**：「派系伤害未对命中伤害生效，目前只对dot生效了。」

**根因**：`resolveSegment()` 里算出了 `factionPct`（`factionFor(ctx.faction, contribs)`），
但它**只传给了 `dotTick()`**；`damageLine(v, cc, cd, hitHead, hsMul)` 根本没有派系参数。
于是上「对 Grineer +30%」这类卡：DoT 每层秒伤 / 六秒总伤 ×1.3，而
单弹头 / 单次射击 / 爆发伤害 / 持续伤害**全都不变**。

**改法（\§5.2「命中结算前一次」）**

```ts
// core/src/crit.ts
export function damageLine(v, cc, cd, hitHead, headshotMul, factionMul = 1) {
  const base = (hitHead ? v * headshotMul : v) * factionMul;   // ← 只乘这一次
  const crit = base * cd * (hitHead ? 2 : 1);
  return { nonCrit: base, crit, average: (1-cc)*base + cc*crit, headshotMul: ... };
}

// core/src/segment.ts
const factionPct = factionFor(ctx.faction, contribs);
const factionMul = 1 + factionPct;
const line = damageLine(vTotal, cc, cd, ctx.headshot.enabled, hsMul, factionMul);
```

派系乘在 **v 上**（合成后总伤），之后的暴击 / 爆头照常乘——与 §5.2 的顺序一致；
**不**额外乘到 `average` 上（否则会变成平方）。DoT 端仍各自乘一次（原来是**正确的**，不改）。

**验证**（新增 `checks/faction-hit.mjs`，12 项）

```
膛线 + 对 Grineer +30%：
  单弹头 76.370 → 99.281（×1.3）
  单次射击 / 爆发 / 持续 全部 ×1.3
  DoT 每层秒伤 / 六秒总伤 ×1.3（原本就对）
  打 Corpus：全部不变（异派系不加成）
  面板总伤不随派系变化（派系只作用于命中结算）
  单弹头 = 合成总伤 × 1.3 × 暴击期望（证明只乘一次）
```

**回归**：16 个页面校对脚本 + `faction-hit` 全绿；单元测试 424 全绿；
`verify-karak` / `verify-co` / `verify-dot-per-stack` / `verify-elements` 均无失败项。
