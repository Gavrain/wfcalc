### D-029 武器专属 Mod 不得出现在其它武器上（状态：已确认）

- **日期**：2026-11-05
- **类别**：数据取舍（筛选规则）
- **需求方原话**：「有的武器限定 mod 不应该在这把武器上出现」。
- **现状问题**：demo 只按 `slotKind ∈ {rifle, primary}` 过滤，得到 122 张，
  其中混有**专属 Mod**（如某武器专用、Prime 专用、灵化专用）。
- **判据（用数据，不靠名字猜）**：`mods.json` 每条带 `official.compatName` / `compatibilityTags`，
  且 `weapon-slots.json` 里每把武器列了 `broad` / `specific`。
  规则：
  ```
  若 Mod 的 compatibilityTags 含该武器 id / 名称 → 专属，允许
  若 Mod 的 compatibilityTags 非空且不含该武器 → 排除
  compatibilityTags 为空 → 通用，允许
  ```
- **结论**：确认，改为按上面的兼容性数据过滤。

### D-044 开发态武器编辑器：面板 / 伤害分布 / trigger 可视化编辑并写回 manual

- **日期**：2026-11-05
- **类别**：新增产出结构（工具，不改计算口径）
- **需求方原话**：
  > 「映射可能不准这个问题，我建议增加一个编辑按钮，把面板跟伤害分布还有发射器类型都放到编辑页，
  > 我可以直接编辑这个武器的面板并保存修改到文件里，不然还每次要打字给你。这是否可行？」
  追问确认：
  > · 保存方式：**直接写** `packages/data/src/manual/weapon-overrides.json`；
  > · 「另外要有已修改提示，然后支持覆盖到 manual，另外这个修改功能**只在开发阶段生效**。
  >   因为部署成静态页的时候不支持编辑。」
  > · 范围：「只改现有字段的值，但是支持**增删伤害类型**，其他类型属性不支持增删。」
  > · 校验：「**面板总伤应该由分布加起来得到。不需要手动编辑**，其他非初级属性也不应该可以编辑。」
- **可行性结论**：可行，且与现有工作流不冲突。
  数据层本来就是「`generated/` 是流水线产物 / `manual/` 是人工层」两层结构
  （见 `CLAUDE.md`）。编辑结果写进 `manual/` 而非 `generated/`，
  重新抓取不会覆盖。
- **可编辑字段（白名单，其余一律只读）**：
  `
  武器级：critChance / critMultiplier / statusChance / fireRate / magazineSize / reloadTime
  模式级：trigger / role
  分段级：damage 分布（可增删伤害类型）、procChance
  `
  **面板总伤不可编辑** —— 它恒等于 `Σ damage`，UI 上只读显示，由分布自动算出。
- **仅开发态**：
  - 静态部署时没有后端，编辑器按钮**不渲染**（靠 `/__dev` 探针判断）；
  - 本地 `npm run demo` 起的是自带 HTTP 服务，才有 `POST /__save-weapon`。
- **写回格式**：`packages/data/src/manual/weapon-overrides.json`，
  结构 `{ "<weaponId>": { ...WeaponOverride } }`，带 `_manual: true` 与 `note`。
- **已修改提示**：加载时若该武器在 overrides 里有记录，标题旁显示「已修改」标记。
- **结论**：确认并实现。

### D-046 编辑器「保存后自动生效」的合并规则

- **日期**：2026-11-05
- **类别**：数据取舍（overrides 如何合并进武器数据）
- **需求方原话**：「「保存后自动生效」接上」
- **合并规则（逐条）**：
  `
  1. 只有「武器级 6 个数值字段」按 **标量覆盖**：
     critChance / critMultiplier / statusChance / fireRate / magazineSize / reloadTime
  2. 模式按 **id 匹配**（不是按数组下标），避免抓取后模式顺序变化导致错位：
     匹配到 → 覆盖 trigger / role / procChance；
     匹配不到 → **忽略**该条 override，并在 console 警告（不凭空创建模式）
  3. 分段（segments）按 **下标** 依次覆盖 damage 与 procChance。
     条目数不一致时以 override 为准截断/补空，并在 console 警告
  4. **未出现在 override 里的字段一律保留 generated 的原值**（部分覆盖语义）
  5. **damage 整体替换**（不是逐键合并）——
     因为编辑器支持"删除某个伤害类型"，逐键合并会让删掉键又冒回来
  6. 面板总伤不写、不合并：它永远由 Σ damage 现算
  `
- **生效时机**：`boot()` 读到 overrides → 合进 `DATA.weapon` → 首屏就是修正后的数据；
  编辑器保存成功后**立即重新合并 + 重渲染**，不需要刷新页面。
- **优先级**：`generated` < `manual/weapon-overrides.json`。
  重新抓取 `generated` 后 overrides 依然生效。
- **结论**：确认并实现。

### D-048 触发几率去重；发射器类型加中文与括号说明

- **日期**：2026-11-05
- **类别**：UI（编辑器字段归位）
- **需求方原话**：
  > 「触发几率有两个，重复了，在面板数值里面有就行了，然后发射器类型加上中文，加括号解释一下他的特点。」
- **问题**：`statusChance`（触发几率）既出现在「面板数值」，
  又出现在每个「模式」的元信息行 —— 两处都能改，容易改出不一致。
- **修改**：
  1. **删掉模式里的触发几率输入框**，只保留「面板数值」里那一处；
  2. 发射器类型下拉改为 **`中文名（特点）`**，`value` 仍存英文原值：
     `
     auto    → 全自动（按住持续射击）
     semi    → 半自动（每点一次打一发）
     burst   → 点射（一次扣扳机打出多连发）
     charged → 蓄力（按住蓄力后释放，伤害通常更高）
     active  → 主动（需手动触发，如次要开火）
     held    → 持续引导（按住持续输出，如光束类）
     duplex  → 双发（扣扳机与松开各打一发）
     none    → 无（武器本身不直接射击）
     unknown → 未标注（数据未给出，待人工确认）
     `
- **⚠ 连带修复（否则会静默失效）**：内核读的是**分段**上的 `procChance`，
  而「面板数值」只改得到武器级 `statusChance`。删除重复输入框后，
  改触发几率**不会**影响结算。
  现在在输入时与保存前两处都做同步：`modes[].procChance` 与
  `segments[].procChance` 一律跟随 `statusChance`。
- **验证**：新增 `verify-status-sync.mjs`（7 项），确认改 0.31 → 0.5 后
  文件里武器级、模式级、分段级三处都是 0.5。
- **结论**：已实现。

### D-090 已安装 Mod / 赋能显示「贡献幅度」（状态：**待确认口径**，已实现）

- **日期**：2026-11-06
- **类别**：界面展示（不改计算）
- **需求方原话**：
  > 「已安装的 mod 也展示自身提供的贡献百分比，即为相对于不上这张 mod 的提升数值。」
- **实施**：
  在 Mod 槽 / 劣化槽 / 赋能槽的卡片上新增一行「贡献」，内容形如
  ```
  +165.0%
  相对不上这张 · 单次射击
  ```
  计算方式：
  ```
  提升 = 当前指标 ÷ 拿掉这一件后的指标 − 1
  ```
  拿掉这一件 = 从贡献列表里剔除 `source === 该装备 id` 的条目后重算一次（复用 `compute()`）。
- **验证（真实数据，Kuva Karak / 单次射击）**：

| 场景 | 数值 | 边际提升 |
|---|---|---|
| 不装 | 28.82 | — |
| 装膛线（+165% 基伤） | 76.37 | **+165.00%** ✅ 与面板加成一致 |
| 膛线 + 分裂膛室 | 145.10 | 膛线 +165.00% / 分裂膛室 +90.00% |

- **口径说明：这是「边际提升」，不是可加和的份额**。
  上例中两张卡的边际提升之和（+255%）大于两者合计提升（+403.5% 的分解也不相等），
  因为每一张都是"在其它卡已存在的前提下再拿掉它"。
  需求方要的就是"相对于不上这张"，所以按边际口径实现。
- **边界处理**：
  - 该装备没产出任何贡献（纯功能卡）→ 显示「对『单次射击』无影响」；
  - 拿掉后指标为 0 → 比例无意义，也显示为无影响；
  - 指标切换（单次射击 / 持续伤害 …）时全部重算，标签同步显示当前指标名。
- **性能**：`renderAll` 时对每件已装装备各跑一次 `compute`（最多 10 次），
  纯函数、无 I/O，实测无卡顿。
- **待确认**：若需求方希望百分比相对某个**固定指标**（例如恒按"单次射击"而非当前选中的指标），
  或希望额外给一个"占总伤害多少"的口径，需要再确认。

- **修订（同日）**：需求方「去掉本卡提升后面的提示，并在工作流里面提示不需要这种莫名其妙的提示」。
  → 卡片上现在**只显示百分比**（`+165.0%`），删掉了「相对不上这张 · 单次射击」的说明，
  纯功能卡也不再显示"对…无影响"。计算口径不变。
  同时把「界面文案不要自造解释性提示」写进 `docs/决策确认规范.md` 作为长期规则。

### D-097 武器选单的选中一致性（状态：**已实现**）

- **日期**：2026-11-06
- **类别**：修 bug（界面状态与计算状态脱节）
- **需求方反馈**：
  > 「切换武器类型选单的时候武器名字选单会变，此时无法选中第一个目标，
  > 但是后面的武器名字没有更新。搜索时也是，我觉得改为可以选中第一个，
  > 但是与当前武器是同一个的时候不切换。如果你有更好的方案可以提出来」

- **根因**（三点叠加）：
  1. `switchWeapon()` 第一行 `if (当前 === 目标) return` —— 选到第一项（往往就是当前武器）
     时直接返回，**选单没有回写**，界面停在"显示 A、实际在算 B"的状态；
  2. `renderTypeOptions()` 重建类型后默认渲染第一类的武器，
     但**没有触发切换**，选单值与 `DATA.weapon` 脱节；
  3. 搜索分支重建武器选单后同样没回写选中值。

- **采纳方案**（比"允许选第一个、相同就不切"更彻底）：
  > **选单只是选择器，真实状态是 `DATA.weapon`；任何重建选单之后都必须
  > 调用 `syncWeaponSelect()` 把选中值回写成当前武器。**

  这样从根上杜绝"选单显示 A、实际在算 B"，而不只是修"选中第一个"这一个场景。

  具体行为：
  - **切类型** → 真的切到该类型下第一把枪（若与当前武器相同则不重算，符合需求方口径）；
  - **选单重建** → `syncWeaponSelect()` 把选中值设为 `DATA.weapon.id`；
    当前武器不在本列表里（如切到别的类型）→ 补一项「<名字>（当前）」并选中，
    用户随时能看到自己在哪把枪上；
  - **搜索** → 结果里不含当前武器时同样补「（当前）」项；
  - **默认类型** → 切回大类时停在当前武器所属的类型，而不是跳回第一类。

- **测试桩的连带修复**：`dom-interact.mjs` 的事件桩只对 `click` 触发 `onclick`，
  对 `change` / `input` **不触发** `onchange` / `oninput`。真实 DOM 里
  `el.onchange = fn` 等价于注册 change 监听器，所以这是桩的缺陷，
  已补上（否则"切类型"这条路径根本跑不到）。

- **验证**：`dom-interact.mjs` 新增第 44 节（14 项），覆盖
  大类禁用状态、类型切换、切回类型、重复选中当前武器、搜索、清空搜索；
  `packages/demo/test/weapon-select-sync.test.ts`（6 项）覆盖纯逻辑与源码级约束。
  合计 138 项 DOM 检查全通过。

### D-114 编辑器保存报「武器字段「name」不可编辑」（状态：**已修复**；白名单取舍**已确认：不放行**，需求方 2026-11-06）

- **日期**：2026-11-06
- **类别**：bug（前端发的载荷与后端白名单不一致）—— **不改口径、不改公式、不改数据**
- **需求方原话**：「保修修改的武器面板时，会提示保存失败：武器字段「name」不可编辑；武器字段「nameZh」不可编辑。
  请确认流程是否有误」

**根因**

`ui-editor.js` 的 `openEditor()` 在造草稿时把**只读**的武器名一起拷了进去：

```js
editorDraft = { weaponId, name, nameZh, critChance, …, modes };
```

而 `server.mjs` 的 `validateEdit()` 按 D-044「只改现有字段的值」用白名单校验**载荷的顶层键**
（`EDITABLE_WEAPON_FIELDS` = 六个面板数值字段），`name` / `nameZh` 不在其中
→ 每一次点「保存」都返回 400，**任何编辑都存不进去**（不只是改名——编辑器本来就不让改名）。

**为什么校对脚本没拦住**

`checks/editor-save.mjs` 的载荷是**手写的**（`:47`），只有 `weaponId` + 六个面板字段 + `modes`，
从未发过真实草稿的形状；也没有任何脚本走「点开编辑器 → 点保存」这条真实路径
（`editor-layout.mjs` 只点开看渲染）。**测试与实现脱节**，与 D-103 修掉的那批 bug 同类。

**改法（只动前端）**

| 文件 | 改动 |

### D-120 单变体结算：`compute(..., variantIndex)`（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **日期**：2026-11-06
- **类别**：内核结算范围（结果里哪些段的数字）——**不改任何乘区公式**

**现象（需求方原话）**

> 「巴兹火枪……基础面板不知道为什么加了爆炸。其中当前面板是对的。」

实测两列：

```
伤害类型   基础      当前
冲击       90.00    90.00
穿刺       35.25    35.25
切割       9.75     9.75
爆炸       40.00    0.00      ← 基础列多出来的
合计      175.00   135.00
```

**根因**

D-096 修过一次"当前列"（`spreadByVariant` 按变体取），但**基础列**还在读
`res.segments` —— 而 `compute()` 的 `segments` 是 `allSegments(mode)`，
即**所有变体**（直接命中 + 爆炸）的段平铺。于是基础列 = 直接命中 + 爆炸，
当前列 = 只当前变体 → 两列必然对不上。

**改法**

`compute()` 新增可选第 6 参 `variantIndex`：传了就只把 `mode.variants[variantIndex]`
交给上下文与段展开，`segments` / `totalSpread` / `spreadByVariant` 都只含这一个变体。
`runCompute()`（demo 计算层薄壳）统一传 `store.ui.variantIndex`。不传时行为不变（兼容旧调用）。

**顺带修的一个 bug**：`switchWeapon()` 只改了「大类」下拉，没有调 `renderKuvaVisibility()`，
所以从选单换枪时玄骸区块的显隐停在上一把武器（`renderKuvaVisibility` 里
`previousElementSibling` 在 DOM shim 下也为空，补了一条按 id 设置标题的兜底）。

**全库扫描结果**（`checks/weapon-switch-editor.mjs` ③）：107 把多变体武器里，
只有「空刃 CrpBEQuanta」的 电/火 → 辐射 两列不同——那是 D-107 元素后移后
「基础列不合成元素」的既有口径，**不是混同**。其余全部一致。

### D-122 换枪后重置编辑器与「已修改」标记；编辑器只提交改过的字段（状态：**已确认 / 已实施**，需求方 2026-11-06）

### D-126 撤回「换口径顶数」的赋能收益（状态：**已确认 / 已实施**，需求方 2026-11-06 纠正）

### D-128 拆解跟随输出变化重算（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「其他地方有变化导致输出变动的时候也要触发拆解，检查下这些收益变动监听是不是绑在太上游了。」

**根因：拆解根本不是"监听"，是"点一下算一次"**

`showDetail(row)` 只在卡片 `click` 时执行一次，结果直接写进 `#detail`；之后：

```
调敌人异况层数 / 叠加层数 → renderAll() → 拆解不动
切玄骸元素 / 拉滑条         → renderAll() → 拆解不动
切增幅基准 / 开爆头          → renderAll() → 拆解不动
装/拖别的 Mod、换武器        → renderAll() → 拆解不动，甚至留着上一把枪的卡
```

而且它拿的是**点击那一刻的 `row` 快照**——`row.mod` 是当时的对象引用，换枪后就失效了。

**改法：拆解挂到「渲染末尾」，只记住"拆解谁"**

| 之前 | 现在 |
|---|---|
| `showDetail(row)`：算一次，写死 DOM | `selectDetail({kind, id/key, exilus})`：只记"拆解谁" |
| — | `renderDetail()`：按**当前** `store.data` 重新取 Mod/赋能，按**当前**贡献重算 |
| — | `renderAll()` 的最后一行调用 `renderDetail()` |

`renderAll()` 已经是**所有状态变化的唯一汇合点**（异况、叠层、玄骸、派系、爆头、基准、
拖拽、换枪、编辑器保存……全部走它），把拆解挂在这里等于"输出一变就重算"，
不需要给每个控件单独挂监听（那样才会漏）。换枪后 `resolveDetailTarget()` 取不到那张卡时，
自动清空拆解并回到提示文案。

**回归**：新增 `checks/detail-refresh.mjs`（12 项）：

| 改的上游 | 断言 |
|---|---|
| 增幅基准切换 | 拆解重画 / 高亮切到新口径 |
| 爆头开关 | 拆解里的数变化 |
| 换到多模式武器 + 切模式 | 拆解里的数变化 |
| 装上另一张 Mod | 赋能拆解的数变化 |
| 换武器 | 拆解清空并回到「点击备选 Mod 或赋能查看拆解」 |

全量：16 个页面校对脚本全绿；单元测试 424 全绿。
