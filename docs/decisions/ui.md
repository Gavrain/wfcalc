### D-177 N 秒总伤：按"当前 ÷ 分母 − 1"，分母按卡的性质构造（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方原话（择要）**：
  > 「他的计算方式还是应该算现在的 n 秒总伤 / 掉的 n 秒总伤 − 1」
  > 「只是对于我说的不形成 dot 的元素 mod，异常部分按他的元素词条还在计算，如有触发率就去掉触发率。
  >   即（。。。60冰冻60触发率）/（。。。60冰冻）」
  > 「元素没形成 DoT 的元素卡这个计算逻辑在计算 n 秒总伤时，只对 dot 部分生效，直伤部分还是正常视为拿掉了 mod」
  > 「这个是 bug：六秒异常总伤这两张 mod 逻辑上等价，怎么收益一个这么低呢」

**定案公式**

```
总伤增幅 = 当前 N 秒总伤 ÷ 分母 − 1
分母 = 拿掉整张卡后的「续航秒伤」× N + DoT 部分
DoT 部分：

  元素形成了 DoT（火、裂罅上的毒气…）→ 拿掉整张卡后的 N 秒异常总伤
  元素没形成 DoT 的元素卡（冰 / 毒）   → 只去掉触发率词条后的 N 秒异常总伤（"…60 冰冻"）
  其它所有卡（基伤 / 多重 / 触发率 / 元素师…）→ 拿掉整张卡后的 N 秒异常总伤
```

- 占比加权（D-175 的 w1/w2）**整个撤掉**：直伤与 DoT 都由总伤比值直接包含。
- "元素没形成 DoT"这一判定**固定按 N 秒异常总伤的口径**判断（总伤口径下 `dotMetricRoleOf` 直接返回 normal，必须先切口径）。
- 备选卡同样用这套分母构造（直伤取"不带这张卡"，DoT 取"只带元素"）。

**验证**（信条·冷冻光束步枪 + 白霜弹头 / 致命火力 / 铝热焊弹，6 秒窗口）

| 卡 | 整卡拿掉 | 只去触发率（分母"…60 冰冻"） | 显示 |
|---|---|---|---|
| 白霜弹头 | +35.28% | +5.26% | **+27.27%** |
| 致命火力 | +44.07% | +5.26% | **+27.27%** |
| 铝热焊弹（火，形成 DoT） | +65.96% | — | **+65.96%** |

- 冰与毒去掉触发率后的分母**逐位相同**（+5.26%），所以两张卡必然显示同一个数。
- 病毒火完整配装：N 秒总伤下白霜 / 致命同为 +20.8%；异常总伤下同为 +27.3%；续航下同为 +18.7%。

### D-178 裂罅待选词条搜索与排序（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方原话**：
  > 「排序那边加个负面优先。还有为什么输入-搜不到负面词条」
  > 「裂罅 mod 的待选词条收益好像不太对，爆伤射速异常状态暴击率，这几个怎么会负收益」

**搜索为什么失效**

`packages/data/src/manual/riven.ts` 里元素 / 物理词条是直接拼进词条表的：

```js
{ key: 'element_cold', stat: 'elemental:cold', label: '冰冻' }   // 没有 labelEn
```

`renderRivenCandidates()` 里 `d.labelEn.toLowerCase()` 对它们抛错，**整块待选区渲染中断**，
表现就是"搜什么都出不来"。

**修复**

| 问题 | 改法 |
|---|---|
| `labelEn` 缺失 | 统一 `String(d.labelEn \|\| '')`，不再假定一定存在 |
| 搜不到负面 | 查询以 `-` / `−` 开头 → **只搜负面词条**（`-` 单独输入即列出全部负面） |
| 排序 | 新增 **「负面优先」**：先列全部负面（负面内按增幅降序），正面跟在后面 |

**同时同步的 D-177（裂罅收益）**

裂罅待选词条 / 已选词条在 N 秒总伤下原本还是 D-175 的加权拼法，与已装卡的 D-177 不一致，
显示成负收益。现在三处共用 `windowRatioOf()`：

```
增幅 = 当前总伤 ÷ 分母 − 1
分母 = 去掉这一条后的续航秒伤 × N + DoT 部分（元素没形成 DoT 的元素词条只去掉触发率）
```

| 异常状态伤害 +101.3% | −19.92% | **+30.54%** |
| 暴击几率 +168.7% | −19.53% | **+24.27%** |

### D-179 / D-180 / D-181 窗口直击、稳态秒伤、暴率下限（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方的发现与决定**：
  > 「负弹匣对续航秒伤有负收益，他对 n 秒异常总伤的生效是怎么样的。这两者不一致导致在算 6 秒总伤的时候逻辑不一样？」
  > 「需要把 n 秒总伤的直击部分也一样改为计算装填窗口，射击窗口使用爆发伤害，这样更能正确体现短射击窗口内装填跟弹匣的影响。」
  > 「然后加一个你说的稳态秒伤……用来体现连续射击下弹匣装填的影响」
  > 「其他的也按循环算」「全部按一个循环」
  > 「暴击率最低为 0，不会负」

**D-179 N 秒总伤的直击部分**

```
旧：N 秒总伤 = 续航秒伤 × N + N 秒异常总伤
新：N 秒总伤 = 窗口内直击 + N 秒异常总伤
窗口内直击 = 连发秒伤 × Σ_{秒=1..N} 开火占比        （与异常同一条 firingFraction 时间线）
```

- 发射即命中，装填期间不产生新伤害（需求方：「我们现在不都假设发射即命中吗」）。
- 弹匣比窗口长 → 直击不扣装填；弹匣比窗口短 → 两边同时扣。

**D-180 稳态秒伤（新增口径）**

```
稳态秒伤 = 续航秒伤 + 各异常类型的稳态贡献
每种 DoT 稳态 = 每跳 × min(一个循环内能叠的层数) ÷ 循环时长
一个循环内能叠的层数 = 层/秒 × (弹匣 ÷ 射速)      毒气再按 10 层封顶
```

- 全部类型都按「一个循环」：装填期间不叠层，长期平均只跟一个循环能叠多少有关。
- **不用固定 N 秒窗口**：会随窗口长度产生假亏损（弹匣比窗口长时火还没叠满就被截断）。
  实测火：弹匣 80 时 6 秒口径 342/秒、循环口径 276/秒；弹匣 44 时 209/秒 vs 238/秒 —— 方向相反。
- 增幅规则与 D-177 一致（直击拿掉整张卡；元素没形成 DoT 的元素卡在异常那侧只去掉触发率）。

**D-181 暴击率下限**

```ts
export function critChanceTotal(...) { return Math.max(0, critChanceRaw(...)); }
```

- 负暴率没有物理意义，而且会让期望倍率 < 1（白字反而打折）。
- 实测：−150% 暴率贡献 → 暴率 0、期望 1.000。

### D-016 曲线 / 爆炸的展示口径（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径（展示层）
- **背景**：
  表 0.2 定了 DoT 用 0~6 秒逐秒曲线，爆炸「按每秒平均伤害给出」。但没写：
  1. 爆炸的"每秒平均"是否叠加进 0~6 秒曲线（它不属 DoT，且只在 1.5 秒节点结算）；
  2. 曲线是**期望值**还是**单次模拟**——2.4 说"不做随机模拟"，所以只能是期望；
  3. 连续射击时 DoT 的"逐秒叠层"用什么步长（射速 8.75 发/秒，每秒不到 9 发但逐秒一步）。
- **我的建议**：
  曲线严格是**期望逐秒值**（每秒叠层数 = `期望层数/发 × 射速` 累加，按各元素叠层规则封顶/独立计时）；
  爆炸作为**独立的每秒平均事件行**展示，不叠加进 DoT 曲线；两者都给"0~6 秒"同一横轴便于对比。
- **理由与证据**：与表 2.4「只算期望」和 0.2「爆炸按每秒平均」都不冲突，且实现最简单。
- **备选方案**：
  - A. 爆炸独立成行（**本方案**）。
  - B. 叠进曲线：横轴语义会变（混合 DoT 与瞬时结算）。
  - C. 只给 6 秒稳态单值：与已确认的 0.2 冲突，不建议。
- **风险 / 不这么改的后果**：只影响展示，不影响单发伤害；但会让人误以为爆炸是持续伤害。
- **结论**：需求方 2026-11-05 选择「**曲线是期望逐秒值；爆炸独立成一行，不叠进曲线**」。

### D-134 赋能槽的处理方式对齐 Mod 槽 / 劣化槽（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「赋能槽有赋能的时候，其他赋能装不上去的，应该跟mod槽位还有劣化槽一个处理方式」

**为什么会装不上**：D-115 给劣化槽 / 赋能槽都写了"已占用就互换"，但 `makeDropTarget()` 的
`dropHappened` 标志是**全局单一变量**——它只能表示"最近一次 drop 处理过"。
在同一个事件循环里连发两次 `dragstart → drop` 时，第二次的 `dropHappened` 接着有效，
`dragend` 就不再触发"拖出即卸下"的兜底，于是旧的赋能留在槽里、新的没进去。

> 顺带说明：真实浏览器里 dragstart/drop/dragend 是分散在不同事件循环里的，所以手动拖一般没症状；
> 但"处理方式与 Mod 槽 / 劣化槽保持一致"是对的要求，这一轮把它改成同一套：

**改法**

1. `dropHappened` 改成**每次 dragstart 重新初始化**，并在 `drop` 处理完成后**立即复位**，
   不再依赖"下一次解析/第二次事件循环"来清掉；
2. 赋能槽补上与 Mod 相同的**可装判定**：只接受**本武器大类**的赋能
   （`arcaneSlotAccepts()` / `dropOnArcane()`，与 Mod 的 `isModAllowedOnWeapon()` 同一层意思），
   别的大类的赋能进来显示**禁止符号**、不改变槽内容（以前只看 `kind === 'arcane'`，
   会把槽里那张顶掉并换上一个不属于本武器的赋能）；

### D-159 六个输出口径统一改名（状态：**已确认 / 已实施**，需求方 2026-11-12）

- **日期**：2026-11-12
- **类别**：界面（措辞）——只改名字与说明文字，**数值、算法、单位一律不动**
- **需求方原话**：
  > 「把持续伤害这个口径容易跟 dot 搞混。改成什么称呼好，其他几个称呼我也想统一一下风格」
  > 「A 组，但是每层那个要叫异常加权单层秒伤，跟实现逻辑要统一」
  > 「单弹头跟单次射击就行了，加伤害太长了塞不下。」

原因：Warframe 里「持续伤害」通常指中毒/着火那类掉血效果，而这个口径算的是**含换弹的每秒输出**，
跟“异常状态”完全是两回事；「爆发伤害」字面像“一次打出去的总伤”，实际是“不换弹时的每秒输出”。

| 项 | 原（D-033 时期） | 现（D-159） | 单位 | 算法（没变） |
|---|---|---|---|---|
| 命中步 | 单弹头 | **单弹头**（不动） | /弹头 | 合成总伤 × 暴击期望 × 爆头开关 |
| 命中步 | 单次射击 | **单次射击**（不动） | /发 | 单弹头 × 多重 |
| 时间窗 | 爆发伤害（原名「每秒命中」） | **连发秒伤** | /秒 | 单次射击 × 射速，**不含装填** |
| 时间窗 | 持续伤害（原名「持续射击」） | **续航秒伤** | /秒 | 单次 × 弹匣 ÷ (弹匣÷射速 + 装填) |
| 异常 | DoT 加权每层秒伤（原名「DoT 每层秒伤」） | **异常加权单层秒伤** | /层/秒 | Σ 各类型（单层每跳 × 该类型触发占比），爆炸不计入 |
| 异常 | 六秒异常状态总伤 | **六秒异常总伤** | — | 六秒逐秒曲线累加，含爆炸 |

命名规则（需求方本条定下的风格）：

- **统一以「秒伤 / 总伤 / 伤害」结尾**，六个名字一个句式，单选切换时一眼能横向比；
- 两个“每秒”的口径用 **连发（不换弹）/ 续航（含换弹）** 区分，不再抢“持续伤害”这个词；
- 两个异常口径统一说 **「异常」**，与 D-158 的「伤害型异常 / 非伤害型异常」同一套词，
  不再用 `DoT` 这个英文缩写；

**布局**

```
Mod 配置（8 槽 + 劣化槽 + 赋能槽）
──────────────────────────────
裂罅 Mod  ▾  [可折叠，默认收起]
  组合 [2+][2+1−][3+][3+1−]    待选数值 [最低][平均][最高]
  ┌─────────────────┬─────────────────────────┐
  │ 这张裂罅（整卡）  │  待选词条（按当前口径）    │
  │ +1 [词条 ▾] ▬▬▬ │  基础伤害   +196.0%  +36% │
  │    [范围][本条]  │  暴击几率   +178.2%  +25% │
  │ +2 [词条 ▾] ...  │  …                        │
  └─────────────────┴─────────────────────────┘
备选 Mod（原样）
```

- 裂罅区**放在「备选 Mod」上方**，折叠条与备选区标题同级。
- **左栏**是这张裂罅本身：一张整卡（显示整卡收益、可拖进槽位）+ 每条词条的「词条下拉 + 滑杆 + 数字输入 + 取值范围 + 本条收益」。
- **右栏**是待选词条：按当前组合与取值口径显示一条一条的「词条名 · 数值 · 收益」，点一下就填进左栏第一个同类空槽。
- 顶部两个按钮组：组合（2+/2+1−/3+/3+1−）与待选数值口径（最低/平均/最高）。

**数值交互**

- 默认取**平均值**；滑杆范围就是这条词条理论上能洗出的范围（均值 ±10%），也可以直接输入。
- 切换「最低 / 平均 / 最高」会把**已经选好的词条**一起按新口径重填（需求方：「统一设置」）。
- 派系词条显示成 `+53.5%`（内部按 `1 + 值/100` 存，见 `data.md` D-162）；滑杆也按百分比走。
- 词条上显示 `范围 +176.4% ~ +215.6%` 与本条的收益。

**收益口径**

| 显示位置 | 含义 |
|---|---|
| 左栏「整卡」 | 这张裂罅整个装上 vs 不上它 |
| 左栏「本条」 | 只有这一条词条时的提升（与其他条互不干扰） |
| 右栏每行 | 把这条填进这张裂罅后 vs 当前 |
| Mod 槽里的紫色卡 | 整卡收益（与左栏「整卡」同一个数） |

**槽位规则**

- 裂罅在槽位里用占位 id `__riven__` 表示，真实词条在 `store.riven` 里；**同一个实体**，左栏改数值 / 改条数，槽位里的卡立即跟着变。
- **每把武器只能装一张**：
  - 已经装在槽里时，下方裂罅区那张**不能再拖上去**（拖拽时显示禁止符号）；
  - 普通 Mod 可以把裂罅顶掉（裂罅回到下方，仍可再拖上去）；
  - 槽位间的裂罅可以在槽位之间挪动。
- 把裂罅拖出槽位 = 卸下，裂罅与其词条仍留在下方裂罅区。

**组合切换**

- 3+ → 2+ 时多出来的那条正面词条**不会删掉**（暂时收起），切回 3+ 会拿回来。

### D-167 裂罅词条槽：去掉下拉、拖拽手柄收窄、修复待选区消失（状态：已确认 / 已实施）

**二、拖拽手柄收窄到槽顶那一行**

- 原因：整张卡片 `draggable = true` 时，浏览器会抢夺卡片内的鼠标按下事件，

- 原因：`placeRivenEntry()` 清空槽位时写入 `null`；重绘时 `previewWithEntry()`

### D-169 收益算法改为「装进当前配装」（状态：已确认 / 已实施）

- **日期**：2026-11-12
- **需求方发现**：冰凇 Prime 配「病毒 + 火」时，致命火力、地狱火显示没收益；裂罅的一条火显示 **−47.4%**，
  但装上去反而变正。需求方追问：「是不是可以把算收益的假设安装位置放后面」，并选定 **1A（如实算）+ 2A（临时额外槽位）**。

**原因**

元素是**成组生效**的（冰+毒=病毒、火+冰=爆炸、毒+电=腐蚀）。旧算法：

| 对象 | 旧算法 | 为什么错 |
|---|---|---|
| 裂罅单条词条 | **只保留这一条** vs 什么都不上 | 单独一条火只是把面板冰顶掉，显示负的；装进实际配装却是正的 |
| 备选 Mod | 塞进**第一个空槽** | 新卡排在已有卡**前面**，会抢走配对对象；8 槽全满直接显示「—」 |

**新口径**

```
裂罅单条增幅 = (配装 + 这张裂罅全部词条) / (配装 + 这张裂罅去掉这一条) − 1
备选 Mod 增幅 = (配装 + 新卡） / 配装 − 1        ← 新卡临时占「第 9 个槽位」
```

- **如实计算**（1A）：新卡如果打乱现有元素组合（例如这条火把病毒打散），就**如实显示负数**；
  不做「先换掉配装里同类那张」的假设。
- **临时额外槽位**（2A）：不改动用户的 8 个槽；额外槽位号排在所有已有槽之后
  （元素合成按槽位号从小到大配对），所以新卡**不会抢走已有卡的配对对象**，与用户真正装上它一致。
- 8 槽全满时也能算出增幅，不再显示「—」。
- 劣化槽仍只有一格：已占用时该功能 Mod 显示「—」（它确实装不上）。

**验证**（Verglas Prime，8 卡配装 + 裂罅 3+1− 第一条火）

| 项 | 旧 | 新 |
|---|---|---|
| 裂罅第 1 条（火）增幅 | ≈ −47.4% | **+32.6%**（与整卡增幅一致，因为只有这一条） |
| 8 槽全满时备选区 80 张卡的增幅 | 全部「—」 | **全部有值** |

**实现位置**

| 文件 | 改动 |
|---|---|
| `packages/demo/public/app-compute.js` | `rivenEntryGain()` 改为「其它词条全在，只加减这一条」；`currentContributions()` 遍历到 `store.modSlots.length`（含临时第 9 槽） |
| `packages/demo/public/app.js` | `simulateEquip()` 普通卡改为**临时占第 9 个槽位**，不再找空槽、满槽也不返回 null |

### D-171 DoT 口径下的增幅规则（状态：已确认 / 已实施）

- **日期**：2026-11-12
- **需求方发现**：配「病毒 + 火」时，地狱火在**异常加权单层秒伤**下不显示（分母为 0）；
  **六秒异常总伤**下致命活力的收益又特别高，不能真实体现 Mod 对异常的贡献。
- **需求方原话（择要）**：
  > 「在计算 dot 相关口径的元素 mod 收益时，用这个规则」
  > 「毒冰元素乘区在 dot 相关的统计口径下就是 0 贡献，显示 0%。当然你可以后面加上 to dot 小字」
  > 「在单层口径下，触发率无贡献，所以白霜弹头显示 0，而对于 n 秒异常总伤来说，元素部分贡献 0，触发率有贡献」
  > 「在单火 mod 下，他对异常的贡献就是 +∞。包括加权单层跟六秒异常总伤」
  > 「hover提示就不要了，一样改成 to dot 小字」

**每跳的计算链**（`dot.ts` 的 `dotTick`）：

```
每跳 = dotBase(全类型之和) × 系数 × (1 + 该元素%) × (1 + 异常状态伤害%) × (1 + 派系%)
层数 = 触发率 × 该类型占比 × 多重
```

所以「元素 %」和「触发率」分别作用在不同环节，两个 DoT 口径对它们的敏感度不同。

**规则**

| 卡的类型 | 异常加权单层秒伤 | 六秒异常总伤 |
|---|---|---|
| 形成伤害 DoT 的元素（火 / 电 / 毒 / 毒气 / 切割） | 拿掉后分母为 0 → **`∞`** | 同左 |
| 冰 / 毒这类被合成掉、**不形成 DoT** 的元素 | **0%** | **0%** |
| 触发几率 % | **0%**（不影响每跳） | 正常算（影响层数） |
| 异常状态伤害 % | 正常算 | 正常算 |
| 其他（基伤 / 暴击…） | 走普通算法 | 走普通算法 |

- `∞` 用 `Number.POSITIVE_INFINITY` 表示，界面显示为 **`∞`**。
- 所有 DoT 口径的增幅数值旁加 **`to dot`** 小字（不用 hover 提示）。
- 普通 Mod 槽位卡、备选区卡、裂罅词条**同一套规则**。

**曾经的错误做法（已撤掉）**：用 ε（0.0001%）元素充当分母，人为造出「火 DoT 存在但加成≈0」的状态，
让地狱火显示 +90%。这个对比状态现实中不存在，需求方指出正确结果就是 **+∞**。

**验证**（Verglas Prime：膛线 / 分裂膛室 / 致命火力 / 白霜弹头 / 地狱火 / 步枪元素师）

| 卡 | 单层秒伤 | 六秒总伤 | 单次射击 |
|---|---|---|---|
| 地狱火（火） | **∞** | **∞** | +40.9% |
| 致命火力（毒） | **0%** | **0%** | +24.0% |
| 白霜弹头（冰） | **0%** | **0%** | +24.0% |
| 步枪元素师（异常伤害） | +90.0% | +90.0% | ±0.0% |
| 步枪才能（纯触发几率） | **0%** | **+40.9%** | ±0.0% |

**另测「毒气 + 火」**（Dual Viciss，自带毒气 153）：火 Mod 在六秒总伤下是**有限值 +102.1%**
（分母是毒气那份，不为 0），单层 +31.3% —— 证明「∞ 只出现在配装里没有其它伤害型 DoT 时」。

**实现位置**

| 文件 | 改动 |
|---|---|
| `packages/demo/public/app-compute.js` | 新增 `isDotMetric()` / `isPerStackMetric()` / `dotMetricRoleOf()` / `feedsDamageDot()` / `INFINITE_GAIN`；`marginalGainOf()` 分母为 0 时返回 ∞；`gainOf` / `rivenEntryGain` 接入规则 |

### D-172 待选区词条增幅：裂罅一律视为已装（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方原话**：
  > 「我发现往裂罅里面加词条会提升待选区词条的收益，这不符合设计。如果裂罅未安装，那么应该没影响。
  > 因为始终算的是当前词条对伤害口径的增量。如果裂罅已安装，那么同类词条之间应该会互相降低贡献。
  > 当然为了防止跳变，我觉得始终视为裂罅安装上去了的情况下计算更合理。」

**旧做法的问题**

```
旧：增幅 = (配装 + 拼进这条的整张裂罅) / (当前配装) − 1
```

裂罅**未安装**时，`当前配装` 里根本没有裂罅，于是组合区每加一条词条，"整张裂罅"就变强一点，
**待选区所有词条的增幅跟着一起涨**——与这条词条本身无关，纯属结构噪声。

**新口径**

```
增幅 = (配装 + 这张裂罅 + 待选词条) / (配装 + 这张裂罅) − 1
```

- 裂罅**一律视为已装**（占虚位槽 `RIVEN_SLOT_COUNT = 8`，排在 8 个 Mod 槽之后），
  装没装都算一样的数，**不跳变**；
- 分子/分母共用同一张"装好的裂罅"，所以衡量的是**这一条的增量**；
- 分母里已有组合区填的同类词条 → 同类乘区相加，**同类词条互相稀释**。

**验证**（Verglas Prime + 膛线，单次射击口径，3+ 组合）

| 组合区状态 | 暴击几率 | 暴击伤害 | 多重 |
|---|---|---|---|
| 空 | 19.40% | 28.48% | 81.00% |
| 已有暴击伤害 | 45.01% | **22.17%**（同类稀释） | 81.00% |
| 已有基础伤害 | 19.40% | — | 81.00% |

- 「已有暴击伤害时暴击几率从 19.40% 升到 45.01%」是**真实的乘区互动**（暴伤放大暴率的边际价值），不是跳变；
- 「已有基础伤害时暴击几率仍是 19.40%」也正确：基础伤害是纯乘数，不影响比值（数学上可证）。

**实现位置**

| 文件 | 改动 |
|---|---|
| `packages/demo/public/app-compute.js` | 新增 `RIVEN_SLOT_COUNT`、`buildOneContribution()`；重写 `rivenCandidateGain()` |

### D-173 已选词条在两处必须是同一个数（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方报告**：「火焰裂罅还是有问题，在待选区是正的，进入裂罅mod以后就变成负的了。」

  > 右边不就是去掉这一条火焰吗。」

**正确理解**

```
左栏：(当前裂罅) / (当前裂罅去掉这条) − 1
右栏：(当前裂罅) / (当前裂罅去掉这条) − 1
```

**修法**

`rivenCandidateGain(def)` 开头先查这条词条**是否已在裂罅里**；在的话**直接返回 `rivenEntryGain(index)`**。
同一个函数算出来的，一定是同一个数，不存在两条路径各自跑一遍的余地。

**验证**（Verglas Prime：膛线 + 致命火力，3+ 组合，火焰在第 1 条）

- `rivenEntryGain(0)` = **50.6250%**
- `rivenCandidateGain(火焰)` = **50.6250%**
- 两处严格相等；未选中的暴击几率仍按增量公式算（+19.40%）

### D-174 裂罅未装时的试算槽位（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方提问**（承接 D-173）：「也就是说，如果放进裂罅但还未安装，你使用的是 undefined 的槽位号？这会导致什么问题。」
- **需求方定案**：
  > 「原来是 0-7，那放 8 是对的，我以为从 1 开始呢，不存在那个备选 mod 模拟槽位。
  > 备选mod跟裂罅未安装的时候是一个逻辑，他们不会冲突的。」
- **需求方关于内部编号**：「裂罅mod内部多元素，使用同一个标号不影响吧」→ 答：**不行**，见下。

**问题**

`rivenToContributions(undefined)` 会把槽位号退化成 **0、1、2**，跟真实 Mod 槽撞号。
内核按 `slot` 升序做元素两两配对，撞号就改写了配对顺序。

实测（Braton，Mod 火@0 + 电@1，裂罅一条冰）：

| 情况 | 合成结果 |
|---|---|
| 旧代码：未装（`undefined` → 槽位 0） | **爆炸** |
| 修好后：未装（试算槽 8） | **辐射 + 冰** |
| 装上：真实槽 2 | **辐射 + 冰** |

**槽位号分区（定案）**

| 槽位号 | 用途 |
|---|---|
| 0 ~ 7 | 8 个真实的 Mod 槽 |
| **8** | **试算槽**：「假装装进去」时用。备选 Mod 与未安装的裂罅**共用**——两者不同时试算，不冲突 |
| 9 ~ 12 | 武器自带元素 / 玄骸元素（**保持原样，不顺延**） |

- 装了就用**真实槽位号**（需求方：「装上的时候按实际位置」）。

**裂罅内部：必须各占一个号，不能用同一个标号**

实测（裂罅内部 火/冰/电，Mod 槽0=毒）：

| 内部编号 | 合成结果 |
|---|---|
| **从下到上各占一号** | **腐蚀 + 爆炸** ✓（电先配） |
| **全部同号** | **毒气 + 磁力** ✗（退化成插入顺序 = 从上到下） |
| 从上到下各占一号 | 毒气 + 磁力 |

`mergePairwise` 用 `sort((a,b) => a.order - b.order)`，同号时依赖**插入顺序**，
而插入顺序就是界面从上到下——**正好和"从下到上"相反**。所以保持各占一号。

**验证**

- 用试算槽 8 时裂罅槽位号 = 8；装上（真实槽 2）后 = 2；**两者 `rivenEntryGain` 完全相等**（28.93%）；
- 裂罅同一张（火/冰/电），试算槽与多个真实槽位下**合成结果一致**；
- 全仓测试 **579 项全部通过**。

| 文件 | 改动 |
|---|---|
| `packages/demo/public/app-compute.js` | 常量 `RIVEN_TRIAL_SLOT = SLOT_COUNT`（= 8）；`rivenEntryGain()` 未装时传 8 而不是 `undefined` |
| `packages/core/src/elements.ts` | 仅补注释说明 8 是试算槽；**自带元素仍从 9 开始，未改动** |

### D-175 N 秒总伤下的增幅：续航 / 异常加权拼（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方发现**（赤毒·邪眼 病毒火 + 裂罅配装，1 秒窗口）：

  | 卡 | 续航秒伤 | 1 秒异常总伤 | 1 秒总伤（改前） |
  |---|---|---|---|
  | 致命火力 | +15.7% | **±0.0%** | **+51.2%** |
  | 白霜弹头 | +15.7% | **±0.0%** | **+12.4%** |

  两张卡在续航和异常里都是**同一个数**，到总伤里却差 4 倍。
- **需求方原话**：
  > 「显然是三啊，不然我这个 n 秒异常状态总伤的口径不就白搞了吗。」
  > 「只影响增幅这里的显示，1秒总伤统计那边还是照常算。」

**问题根因**

N 秒总伤下的增幅原来是「拿掉这张卡重算总伤」，**绕开了** D-171 的异常口径规则：
拿掉致命火力以后病毒散架、火被释放出来叠层翻倍 → 总伤增幅被凭空放大；
而白霜弹头拿掉冰只是病毒变弱 → 两卡在总伤里不再对称。

**定案算法**

```
总伤增幅 = w1 × 续航秒伤增幅 + w2 × N 秒异常总伤增幅
w1 = 续航秒伤 × N ÷ N 秒总伤     w2 = N 秒异常总伤 ÷ N 秒总伤     （w1 + w2 = 1，取当前配装）
```

|---|---|
| 续航 | `当前 ÷ 拿掉后 − 1`（命中伤害，普通边际增幅） |
| 异常 | **仍是 D-171 那套规则**：元素被合成掉、不形成伤害型 DoT → **0%**；否则 `当前 ÷ 拿掉后 − 1`；拿掉后归 0 → **`∞`** |

- 已装卡 / 劣化槽 / 赋能 / 备选卡 / 裂罅整卡 / 裂罅词条（左右两栏）**一律同一套**。
- 总伤下卡上的增幅旁标 **`to total`**（与 DoT 口径的 `to dot` 区分）。

**验证**（赤毒·邪眼 + 膛线 / 分裂膛室 / 白霜弹头 / 致命火力 / 铝热焊弹 / 野火 / 裂罅 / 步枪元素师，1 秒窗口）

| 卡 | 续航秒伤 | 1 秒异常总伤 | 1 秒总伤（改后） |
|---|---|---|---|
| 致命火力 | +15.7% | ±0.0% | **+10.8%** |
| 白霜弹头 | +15.7% | ±0.0% | **+10.8%** |
| 铝热焊弹（火） | +15.7% | +75.3% | **+34.3%** |

### D-176 N 秒异常总伤：元素卡按「元素 × 触发率」拆开（状态：已确认 / 已实施）

- **日期**：2026-11-13
- **需求方发现**：1 秒异常总伤里，白霜弹头、致命火力显示 ±0.0%——
  > 「白霜弹头跟致命火力变成 0 收益了，你是不是忘了他们还提供触发率。」
- **需求方原话（择要）**：
  > 「触发率就按触发率mod的收益来算。其他不管，这个事情只涉及到元素对dot收益问题」
  > 「我指的是 (1+0)*(1+x)」（元素增益 × 触发率增益）
  > 「参考裂罅mod，三个词条的收益相加并不等于整卡收益，实际上是相乘」
  > 「按内核链算，不应该有特殊的处理逻辑」

**问题**

D-171 原文是「元素部分贡献 0，**触发率有贡献**」，但实现里 `dotMetricRoleOf()` 对
"元素不形成 DoT"的卡**整卡**返回 `zero`，把同一张卡上的 +60 触发率一起抹掉了。

**定案算法（N 秒异常总伤下）**

```
元素增益 = 0                                  （元素没形成 DoT 时；D-171）
触发率增益 = 只留触发率 ÷ 当前 − 1            （= 内核层数链里 (1+Σ触发率) 的比值）
异常增幅 = (1 + 元素增益) × (1 + 触发率增益) − 1
```

**按「卡是什么卡」分流（需求方 2026-11-13）**

| 情形 | 走哪条 |
|---|---|
| **待选区**的元素 mod（假设装到 8 号位） | 原来的逻辑：装上 vs 当前 |
| **已装**、元素**形成** DoT（病毒火里的火、裂罅上的毒气…） | 正常拿掉重算（分母为 0 → `∞`） |
| **已装**、元素**没形成** DoT（病毒火里的冰 / 毒） | 元素部分 0；触发率部分按内核层数链算，**两者相乘**；没触发率词条 → 0 |
| 其它所有卡（基伤 / 多重 / 暴击 / 射速 / 元素师…） | 不动：仍按原来的边际算法 |

**N 秒总伤**：直伤与 DoT **拆开各自算**，不要混同——
续航部分走续航秒伤增幅、异常部分走 N 秒异常总伤增幅，再按当前占比加权（D-175）。

**之前的两处错误（已修）**

1. 量反了方向：元素增益用了「只留元素 ÷ 当前」，在病毒火里会得出负数，连带把触发率翻成负的。
   两个增益都必须是「装上 ÷ 当前」。
2. 把「元素卡拆法」套到了**所有卡**上：膛线 / 分裂膛室 / 元素师在 N 秒总伤里被拆得面目全非。
   只有"已装且元素没形成 DoT 的元素卡"才走特殊拆法，其它卡保持原样。

**验证**（赤毒·邪眼，1 秒窗口；膛线 / 分裂膛室 / 白霜弹头 / 致命火力 / 空槽 / 铝热焊弹 / 裂罅 / 步枪元素师）

| 卡 | 1 秒异常总伤 |
|---|---|
| 白霜弹头 | **+27.27%**（元素 0 × 触发率） |
| 致命火力 | **+27.27%**（同上） |
| 膛线 | +57.77%（原样） |
| 分裂膛室 | +44.73%（原样） |

### D-196 稳态秒伤的卡面增幅对齐 N 秒总伤；「形成 DoT」按独立单元素判（状态：**已确认 / 已实施**，需求方 2026-11-14）

- **日期**：2026-11-14
- **类别**：界面显示（卡面增幅），不改口径表里的任何数值
- **需求方原话**：
  > 「你需要参考 n 秒总伤那边的做法。」
  > 「A」（选"稳态的判定复用 `dotRoleForWindow`"）
  > 「铝热当然是错了，火是不会被合成进病毒的，病毒是冰和毒。他组成 dot，所以应该走整张拿掉。
  >   注意不是特制这张应该走拿掉，而是按台账口径，形成 dot 的走这个。」

**问题一：稳态的 DoT 侧判定恒为 normal**

`windowGainForSource()` 的稳态分支直接调 `dotMetricRoleOf()` 判断 split，但稳态**不属于 DoT 口径**
（`isDotMetric()` 只认 `dotPerSecond` / `dot6s`），`dotMetricRoleOf()` 在非 DoT 口径下第一时间就
`return { kind: 'normal' }`。于是「元素没形成 DoT 的元素卡只去掉触发率」这条 D-177 的构造
在稳态里**永远走不到**，白霜弹头 / 致命火力只能拿到触发率的边际（**+0.74%**）。

**问题二：`feedsDamageDot()` 把"火被写进病毒"误判**

判据看的是合成后的 `elementDetail.v`。实测本配装（冰凇 Prime + 白霜 / 致命 / 铝热 / 污染）：

```
elementDetail.v      = { heat: 19.2, viral: 99.2 }
elementDetail.singles = [ heat 19.2（铝热焊弹） ]
elementDetail.compounds= [ viral 99.2（冰 19.2 + 毒 48，面板冰 32 作单元素留下） ]
```

旧逻辑拿**该卡自己的元素类型**去 `v` 里找，多数情况下结果其实是对的（冰 / 毒在 `v` 里确实没有），
但判据本身站不住：`v` 是"合成后的伤害分布"，**复合元素会把源元素的份额合并掉**，
它回答不了"这个元素还在不在面板上"。
按需求方口径：**病毒是冰 + 毒合成的，不会把火吃进去**；「形成 DoT」= 这个元素
**还在面板上、能触发它自己的 DoT**，所以判据改为 `elementDetail.singles`
（拿不到 `singles` 时才退回 `v`）。

**定案**

```
分裂判定（split）= 这张卡是元素卡 + 带触发率 + 它贡献的元素不在 elementDetail.singles 里
稳态秒伤的 DoT 侧：固定按「N 秒异常总伤」口径判 split（复用 dotRoleForWindow），与 D-177 逐条一致
形成 DoT 的卡（铝热焊弹 → 火）→ 走"整张拿掉"，不是特例，就是台账口径
```

**验证**（冰凇 Prime，四张卡：白霜 / 致命 / 铝热 / 污染，稳态秒伤当前值 1385.60）

| 卡 | 形成 DoT | split（改后） | 稳态秒伤增幅 | 参考：6 秒总伤 |
|---|---|---|---|---|
| 白霜弹头（冰） | 否 | 是 | **+19.61%**（原 +0.74%） | +20.18% |
| 致命火力（毒） | 否 | 是 | **+19.61%**（原 +0.74%） | +20.18% |
| 铝热焊弹（火） | **是** | 否（原误判为是） | **+23.57%**（原 +19.61%） | 走整张拿掉 |
| 污染弹匣（毒 90，无触发率） | 否 | 否 | +28.86% | +22.11% |

- 冰与毒的分母逐位相同（和 D-177 一样），所以两张卡必然显示同一个数。
