### D-016 曲线 / 爆炸的展示口径（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的口径（展示层）
- **背景**：
  表 0.2 定了 DoT 用 0~6 秒逐秒曲线，爆炸「按每秒平均伤害给出」。但没写：
  1. 爆炸的"每秒平均"是否叠加进 0~6 秒曲线（它不属 DoT，且只在 1.5 秒节点结算）；
  2. 曲线是**期望值**还是**单次模拟**——2.4 说"不做随机模拟"，所以只能是期望；
  3. 连续射击时 DoT 的"逐秒叠层"用什么步长（射速 8.75 发/秒，每秒不到 9 发但逐秒一步）。
- **我的建议**：
  曲线严格是**期望逐秒值**（每秒叠层数 = `期望层数/发 × 射速` 累加，按各元素叠层规则封顶/独立计时）；
  爆炸作为**独立的每秒平均事件行**展示，不叠加进 DoT 曲线；两者都给"0~6 秒"同一横轴便于对比。
- **理由与证据**：与表 2.4「只算期望」和 0.2「爆炸按每秒平均」都不冲突，且实现最简单。
- **备选方案**：
  - A. 爆炸独立成行（**本方案**）。
  - B. 叠进曲线：横轴语义会变（混合 DoT 与瞬时结算）。
  - C. 只给 6 秒稳态单值：与已确认的 0.2 冲突，不建议。
- **风险 / 不这么改的后果**：只影响展示，不影响单发伤害；但会让人误以为爆炸是持续伤害。
- **结论**：需求方 2026-11-05 选择「**曲线是期望逐秒值；爆炸独立成一行，不叠进曲线**」。

### D-021 demo 的显示形态与交互（状态：已确认）

- **日期**：2026-11-05
- **类别**：结构变化（demo 页面形态）
- **背景**：需求方要一个能本地跑的计算内核 demo，并给出了具体布局。
- **我的建议（已实现）**：
  1. **示例武器**：赤毒·卡拉克（`KuvaKarak`）单模式步枪，**不考虑灵化**；
  2. **左侧**：武器名、基础面板、Mod 加成后面板（**随 Mod 实时更新**）、玄骸元素/加成、
     输出口径列表（单选）与 DoT 明细；
  3. **右侧上方**：两行四列 Mod 槽位；旁侧**劣化槽**（只能放功能类 Mod），劣化槽上方**赋能槽**；
  4. **右侧下方·备选区**：当前武器可装的全部 Mod（步枪 = `rifle` + `primary` 共 122 张），
     长方形卡片显示**名字 + 词条数值 + 对当前配置的伤害增幅**；
  5. **增幅口径**用单选按钮切换（单弹头 / 单次射击 / 每秒命中 / 持续射击 / DoT 每秒 / DoT 0~6 秒），
     默认「单次射击」；
  6. **拖拽**放置；劣化槽只收功能类（`kind` ∈ functional/special/skip 或 `bucket = utility`），
     功能类也不能进普通槽。
- **判定「功能类」的依据**：数据层 `stats[].kind` 与 `bucket`。
  ⚠ 数据层没有"这是不是劣化槽 Mod"的字段（游戏内另有 `EXILUS` 标记未抓取），
  所以这里用"**是否改变伤害**"反推：不改变伤害的才允许进劣化槽。
  这是**实现近似**，若以后抓到官方 `EXILUS` 标记，应改为读那个字段（记入 data-todo）。
- **风险**：某些游戏内禁止进劣化槽的 Mod（如部分 `special` 类）会被允许；反之亦然。
  只影响"能否放进劣化槽"的便利性，不影响伤害数值。
- **结论**：需求方 2026-11-05 确认布局；实现细节按上。

### D-035 槽位不再自动紧凑；筛选改单选按钮组；词条汉化（状态：已确认）

- **日期**：2026-11-05
- **类别**：改动已确认的行为（D-034 的槽位语义被推翻）+ 产出结构
- **需求方原话**：
  > 「mod 配置不要自动紧凑，放在哪个位置就是哪个位置。」
  > 「筛选改成单选框，ui 改好看点，多个 button 有一个高亮那种，触发里面少了带触发的元素卡。」
  > 「然后英文词条记得汉化一下。穿透装填速度什么的。」
- **槽位语义（修订 D-034）**：
  ```
  · 从备选区拖入 → 直接占据目标槽；目标槽原有 Mod 退回备选区；**其余槽一律不动**。
  · 槽位之间移动 → **两个位置直接交换**，不做整体平移、不做自动紧凑。
  · 空出来的槽**保持空着**，后面的 Mod 不自动前移。
  ```
- **为什么改**：D-034 当时按「前移填洞」实现，需求方实际期望的是"位置由玩家手动决定"。
  自动紧凑会让玩家摆好的顺序被打乱。
- **筛选**：`<select>` 改为**按钮组**，当前项高亮（单选语义）。
- **「触发」漏卡（bug）**：`filterKeyOf` 只把主归类为 `status` 的卡放进「触发」，
  而**带 `+触发几率` 词条的元素卡**主归类是「元素」，于是从「触发」里消失。
  改为：`matchesFilter` 对「触发」额外收**任何带触发类词条**的卡（触发几率/异常伤害/异常持续）。
- **词条汉化**：新增 `STAT_LABEL` 表，覆盖 `穿透 / 装填速度 / 弹匣容量 / 精准度 / 后坐力 /
  弹速 / 爆炸范围 / 变焦 / 弹药上限 / 弹药效率 / 弱点伤害` 等；元素与物理走 `ELEMENT_LABEL`。
  界面不再直接显示英文 key。
- **结论**：全部确认并实现。

### D-045 面板高亮的位置错了：应只高亮「当前」列

- **日期**：2026-11-05
- **类别**：修 bug（UI）
- **需求方原话**：
  > 「武器面板那边的高亮不对，伤害分布也是，只高亮有变动的当前面板」
- **根因**：`fillRows` 里写的是 `c === 1 && isChanged(row)` 时加 `changed` 类。
  但第 2 列（索引 1）是**「基础」列**，「当前」列是**索引 2**。
  于是高亮跑到了不会变的基础值上，看着像"高亮不对"。
- **修正**：改为 `c === 2 && changed` —— 只高亮「当前」列；
  「基础」列永远不高亮；「合计」行也不高亮。
- **验证**：实测高亮前的基础列 23.00% / ×2.10 / 1.00 被标红，
  修正后变成当前列 57.50% / ×4.62 / 2.500 被标蓝，且触发几率/射速（未变）不高亮。
  新增断言：两张表的 `changed` **只能出现在索引 2**。
- **结论**：已修复。

### D-117 镀层「0 层」可选；推演小字改到镀层 Mod 卡上（状态：**已确认 / 已实施**，需求方 2026-11-06）

**改法**：

|---|---|
| `app-compute.js` `computeOptions()` | `opts.coStacks = Math.max(0, store.ui.coStacks)`（不再把 0 换成上限） |

### D-129 拆解里的「等效弹匣」改成与输出口径同样的表（状态：**已确认 / 已实施**，需求方 2026-11-06）

### D-130 拆解的措辞与结构整理（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「面板变动这个是什么时候加进去的，之前没有吧？……弹匣（按弹药效率折算）……这个也不需要写括号里
  那些啊，直接写等效弹匣就行了。然后差异统一用增幅这个表述，不要用变化。暴击变动这个也很冗余，
  拆解本身就是表示变动，写暴击就行了。」

### D-131 修复：Mod 配置区被 6 列网格挤成一坨（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「mod配置那边你改崩了，挤成一坨了」

**我上一轮（D-127）改崩了两处 CSS**

1. **`.slot` 的基础样式整块丢了**：为了加 `position: relative`（放槽名标签），
   我把原来的 `.slot { background / border / padding / min-height / display:flex … }`
   替换成了只有一行 `position: relative` —— 所有槽位（包括 8 个普通 Mod 槽）失去背景、边框、
   内边距与最小高度，内容直接贴在一起。**这是"挤成一坨"的主因**。
2. **`.slot-wrap` 改成 `repeat(6, 1fr)` 网格 + `.slot-grid { display: contents }`**：
   本意是让侧栏两张槽和 Mod 槽同宽，但 `contents` 把 8 个 Mod 槽 + 2 个侧槽全部摊进
   **同一个网格的换行流**，侧槽被挤到第二行末尾，整个区域成了一排乱格子。

**改法（恢复结构 + 保持"侧槽与 Mod 槽同宽"）**

```css
.slot {                      /* 恢复原有样式，只多一行 position: relative */
  position: relative; background: var(--panel-2); border: 1px dashed var(--line);
  border-radius: 5px; padding: 6px; min-height: 84px;
  display: flex; flex-direction: column; gap: 4px; …
}
.slot-wrap   { display: flex; gap: 8px; align-items: stretch; }
.slot-grid   { display: grid; grid-template-columns: repeat(4, 1fr); flex: 1; min-width: 0; }
.side-column { display: grid; grid-template-columns: repeat(2, minmax(0, 1fr)); flex: 1; min-width: 0; }
.arcane-slots, .side-slots { display: contents; }   /* 两张侧槽直接落进侧栏自己的 2 格 */
```

侧栏与 Mod 槽区等宽（都 `flex: 1`），侧栏里 2 格 → 每格与普通 Mod 槽同宽；
Mod 槽区仍是原来的 4 列网格。**没有用 `contents` 把 Mod 槽摊出去**。

**教训**：改"有多个 div 包裹层"的布局时，`display: contents` 会把包裹层的子元素提升到父容器的
布局流里更上层——层级一旦算错，整个区域的排布就全乱；这类改动要小步改、改完对一眼。

### D-134 赋能槽的处理方式对齐 Mod 槽 / 劣化槽（状态：**已确认 / 已实施**，需求方 2026-11-06）

- **需求方原话**：「赋能槽有赋能的时候，其他赋能装不上去的，应该跟mod槽位还有劣化槽一个处理方式」

**为什么会装不上**：D-115 给劣化槽 / 赋能槽都写了"已占用就互换"，但 `makeDropTarget()` 的
`dropHappened` 标志是**全局单一变量**——它只能表示"最近一次 drop 处理过"。
在同一个事件循环里连发两次 `dragstart → drop` 时，第二次的 `dropHappened` 接着有效，
`dragend` 就不再触发"拖出即卸下"的兜底，于是旧的赋能留在槽里、新的没进去。

> 顺带说明：真实浏览器里 dragstart/drop/dragend 是分散在不同事件循环里的，所以手动拖一般没症状；
> 但"处理方式与 Mod 槽 / 劣化槽保持一致"是对的要求，这一轮把它改成同一套：

**改法**

1. `dropHappened` 改成**每次 dragstart 重新初始化**，并在 `drop` 处理完成后**立即复位**，
   不再依赖"下一次解析/第二次事件循环"来清掉；
2. 赋能槽补上与 Mod 相同的**可装判定**：只接受**本武器大类**的赋能
   （`arcaneSlotAccepts()` / `dropOnArcane()`，与 Mod 的 `isModAllowedOnWeapon()` 同一层意思），
   别的大类的赋能进来显示**禁止符号**、不改变槽内容（以前只看 `kind === 'arcane'`，
   会把槽里那张顶掉并换上一个不属于本武器的赋能）；
3. 赋能槽之间的互换（拖到备选区的某张赋能卡）也加了大类校验（`candidateCardAccepts`）。

**回归**：`arcane-detail.mjs` 扩到 30 项（+ 槽里已有赋能时拖入别的赋能 = 互换、被换下的回列表、
别的大类赋能不能进当前槽、拖进来不改变槽内容；另加"侧栏是单列窄栏"的结构断言）。
全量：16 个页面校对脚本全绿；单元测试 424 全绿。
