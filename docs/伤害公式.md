## 0. 为什么要把乘区表转成伪代码

乘区表是给人看的，同一个词在不同实现里能长出不同的结果。表里已经有两个这样的地方：

| 表里的原文 | 容易被理解成 | 实际口径 |
|---|---|---|
| 「DoT 基础值 = 剔除元素/物理 Mod 加量的命中伤」 | 先算完含 Mod 的命中伤，再减回去 | 从"基础伤害项"出发，**根本不走元素加量那一步**（第 5 节 `L2(side='dotBase')`） |
| 「元素 %Mod 先加总；各元素加量按该元素归属」 | 所有元素 % 加起来乘一次总伤 | **每个元素类型各自一个变量**，物理不参与放大（第 5 节 `L2` ③） |

写成函数后，有争议的地方会从"文字怎么理解"变成"这两行代码为什么不同"，确认起来快得多。

## 1. 单位与数据字段（对齐数据层实际字段名）

### 1.1 单位约定

```
百分比：内核一律用 0~1 小数（0.45 = 45%），ΣMod% 求和后落在这一口径
倍率  ：不带百分号的倍数（暴伤 2.0 = 2 倍）
```

两种来源口径不同，**只在读取入口归一化一次**，内核内部不再混用：

| 来源 | `critChance` / `statusChance` | `critMultiplier` | 伤害分布 / `levelValues` |
|---|---|---|---|
| `generated/weapons/*.json` | 0~1 小数（0.12 = 12%） | 倍数（1.6） | 绝对值 / — |
| `generated/mods/*.json` 的 `levelValues` | 0~100 百分数 | 0~100 百分数 | — |

### 1.2 字段名对照（类型名 ↔ 数据层实际字段名）

`packages/core/src/weapon.ts` 的类型名与数据层实际输出**不一致**（见下表）。本文一律用**数据层实际字段名**，
是否把 `weapon.ts` 直接对齐到数据层，见 D-011。

| `weapon.ts` 类型字段 | 数据层实际字段 | 说明 |
|---|---|---|
| `name: {en, zh}` | `name` / `nameZh` | 武器是扁平两字段 |
| `isAoe` | `aoe` | |
| `languageKey` | 同左 | 数据层有，类型里声明为可选 |
| `baseMultishot` | `multishot` | `emit.ts` 第 62 行 `multishot: m.baseMultishot` |
| `bullets` | `bullets` | = 导出 `fireIterations`，与 `multishot` **经常不等** |

## 2. 两条基础规则（后面所有乘区都建立在它们上）

### 2.1 通用乘区骨架（乘区归属表 2.0）

```
BUCKET(panel, id) = ( panel × (1 + Σ_pct(id)) + Σ_flat(id) ) × (1 + arcaneMul?) × Π_mul(id)
```

- `Σ_pct`：该乘区内 `form='pct'` 的贡献相加；
- `Σ_flat`：`form='flat'` 的固定加算值——表里**只给暴率、暴伤各设一个**（私法套装入暴率这一项）；
- `Π_mul`：`form='mul'` 的独立额外乘区——表里只给射速设了一个。

### 2.2 元素 / 物理贡献的语义（A-02 已确认）

- `elemental:heat = 0.9` 表示「+90% 火伤」的**加成百分比**：加量 = 新面板总伤 × 0.9；
- `physical:impact = 1.0` 表示「+100% 冲击」：加量 = 该物理类型自身面板值 × 1.0；
- 同类型的多条 Mod **先加总成一个槽位**再参与合成（D-006），不同元素类型是各自独立的槽位。

## 3. 结算链总览（对应乘区归属表第 1 节；玄骸顺序已按 D-017 修正）

```
[入口] buildContext(武器, 模式, Mod/赋能/灵化/自定义) → Ctx
   │
   ├─ L0 面板切段：每个 segment 一个伤害向量 v
   ├─ L2① 玄骸加成 → 改面板基伤（与面板基伤同等待遇，吃基伤加成）   ← D-017
   ├─ L1 基伤（双基本值）/ 多重（独立乘区）
   ├─ L2② 元素加量 + 物理加量 + 复合合成                   ← 唯一处理"元素"的地方
   ├─ L3 暴击（平均线 / 分档上下限线） + 爆头
   ├─ L4 触发状态机：总触发率 → 元素占比 → 期望层数 → DoT 每跳
   ├─ L5 目标结算：超宏 → 护盾 → 护甲/削甲 → 生命；派系乘区
   └─ L6 输出口径：单弹头 / 单次射击 / 每秒命中 / 每秒 DoT（0~6 秒曲线）/ 持续射击 DPS
```

每个 L 函数都返回 `{ value, detail }`：`detail` 记录"哪条贡献、落在哪个乘区、贡献了多少"，
直接喂给 UI 的拆解展示（CLAUDE.md 的"每个乘区都能复算"）。

> 编号沿用乘区表的 L1~L6，**执行顺序**以本节箭头为准：玄骸（L2 前置）先于基伤（L1）。

## 5. L2：玄骸 → 基伤 → 元素加量 → 复合合成（**最容易写错，全部逻辑集中在三个函数里**）

> **顺序修正（2026-11-05 需求方确认）**：玄骸加成**在基伤之前**结算，它体现在武器面板基伤内，
> 因此它**吃全部基伤加成**（基伤 Mod%、镀层%）。这推翻了表 4.4 旧写法里"玄骸加成自身不会被再乘一次"。
> 台账 D-007、D-017。定稿顺序：

```
面板伤害分布
  → ① 玄骸加成（L2 前置，改"面板基伤"）
  → ② 基伤（双基本值：(含玄骸的基伤 + 灵化基伤) × (1+Σ基伤Mod%+镀层%)）
  → ③ 物理 %Mod / ④ 元素 %Mod（基数 = ② 的新面板总伤）
  → ⑤ 两两合成 → ⑥ 汇总
```

### 5.1 前置：玄骸加成改面板基伤（`applyKuvaBonus`）

```ts
// 「玄骸加成体现在面板基伤内」= 玄骸那一份与面板基伤同等待遇：
//   吃 (1 + Σ基伤Mod% + 镀层%)，不吃灵化基伤那一路。
// 表 4.4 校验例 2 的 24 在代数上必然成立（例中基伤 G=0）：
//   玄骸加量 = 面板总伤 × 比例 = 40 × 0.6 = 24；随后被基伤 (1+G) 放大 —— 这就是 D-017 的"在基伤之前"。
//   两种写法（金额按总额算 / 与面板同乘再减回）代数等价，区别只在"玄骸进不进元素 % 的基数"。
function applyKuvaBonus(panel: Vec, ctx: Ctx): Vec {
  if (!ctx.kuva) return { ...panel }
  const augment = panelTotal(panel) × ctx.kuva.ratio          // 未加基伤的玄骸金额
  if (isPhysical(ctx.kuva.type))
    return { ...panel, [ctx.kuva.type]: panel[ctx.kuva.type] + augment }  // 冲击与面板冲击合并（4.4）
  return { ...panel, [ctx.kuva.type]: augment }               // 其它类型是独立的一份
}
```

### 5.2 基伤与多重（`applyBaseDamage` + `multishot`）

```ts
function applyBaseDamage(panelWithKuva: Vec, seg: Segment, ctx: Ctx): Vec {
  const g       = 1 + sumPct('baseDamage')             // 基伤 Mod 总和
  const isAoe   = seg.kind === 'explosiveAttack'       // = seg.aoe
  // 2.1 双基本值：基伤项 = 面板基伤 × (1 + Σ基伤Mod% + 镀层%) + 灵化基伤 × (1 + Σ基伤Mod%)
  //   镀层类（'co'）不吃灵化基伤、不吃 AoE；玄骸那一份位于面板基伤内，因此同样被放大（D-017）
  const k       = isAoe ? g
                        : (1 + sumPct('baseDamage') + overForStacks(ctx))   // 镀层实际层数 ⚠ A-03
  const kInnate = g                                                 // 灵化基伤只吃 (1+Σ基伤Mod%)
  return scaleSpread(panelWithKuva, isInnate(seg) ? kInnate : k)
}

function multishot(ctx): number {
  return 1 + sumPct('multishot')                  // 2.2：与基伤相乘，绝不相加
}
```

- **按 D-017，玄骸进入元素 % 的基数**：它在 ② 已被基伤放大，所以元素 % 的基数 = 含玄骸的总伤（见 §5.4）。
  `spreadTotalAfterMods` 只负责"不含玄骸加成"的那一步，玄骸由 `applyKuvaBonus` 并在基伤前加进面板。

### 5.3 元素 / 物理加量 + 两两合成（`applyElements`）

```ts
type Vec  = Partial<Record<DamageType, number>>
type Side = 'hit' | 'dotBase'        // dotBase = 6.2 的"剔除元素/物理加量"情形

function applyElements(base: Vec, ctx: Ctx, side: Side): { v: Vec; detail: Slot[] } {
  // base = ② 的结果（已含基伤、已含被放大的玄骸）；函数内部不再乘玄骸
  const Tnew = total(base)                              // 新面板总伤（元素 % 的基数）
  const out: Vec = {}

  // ───── ③ 物理 %Mod（4.1 ③）：基数 = 该物理类型自身面板值 ─────
  for (const t of PHYSICAL) {
    const m = side === 'hit' ? sumPct(`physical:${t}`) : 0        // dotBase 剔除
    out[t] = base[t] × (1 + m)
  }

  // ───── ④ 元素 %Mod（4.1 ②）：基数 = 新面板总伤；物理不放大 ─────
  interface Slot { type: DamageType; amount: number; order: number; src: string; fromMod: boolean }
  const slots: Slot[] = []

  // 4.1 【已确认】同类型元素 Mod 先加总成一个槽位（D-006 例 C ⟹ 毒气 370）
  for (const [t, group] of groupByType(elementalContribs(ctx.mods, side)))
    slots.push({ type: t, amount: Tnew × Σ(group), order: min(group.slot), src: 'mod', fromMod: true })

  // 4.2 底座里已有的元素（面板自带 / 已被基伤放大的玄骸 / 灵化基伤）→ 各占一个槽位
  //     玄骸若是复合元素（磁力等），它在配对时天然不参与（isCompound）
  for (const [t, amount] of entries(base))
    if (!isPhysical(t)) slots.push({ type: t, amount, order: panelSlot(t), src: 'panel', fromMod: false })

  // ───── ⑤ 两两合成（4.3）：槽位从小到大；合成即整体、不再参与配对 ─────
  const { singles, compounds } = mergePairwise(slots)

  // ───── ⑥ 汇总：单元素 + 复合元素（同类型相加） ─────
  for (const s of singles)   out[s.type] = (out[s.type] ?? 0) + s.amount
  for (const c of compounds) out[c.type] = (out[c.type] ?? 0) + c.amount
  return { v: out, detail: [...slots, ...compounds] }
}

function mergePairwise(slots: Slot[]) {
  const queue = slots.slice().sort(byOrder)      // 稳定排序
  const singles: Slot[] = []; const compounds: Slot[] = []
  while (queue.length) {
    const a = queue.shift()
    if (isCompound(a.type)) { compounds.push(a); continue }        // 复合元素不参与配对
    const b = queue.find(s => !isCompound(s.type) && pairOf(a.type, s.type))
    if (!b) { singles.push(a); continue }                          // 配不上 → 留作单元素
    queue.splice(queue.indexOf(b), 1)
    compounds.push({ type: pairOf(a.type, b.type), amount: a.amount + b.amount,
                     fromMod: a.fromMod || b.fromMod })            // 合成即整体
  }
  return { singles, compounds }
}

const PAIRS = {
  'heat+cold':'blast', 'heat+toxin':'gas', 'heat+electric':'radiation',
  'cold+toxin':'viral', 'cold+electric':'magnetic', 'toxin+electric':'corrosive',
}
```

**DoT 基础值（6.2）就是 `side='dotBase'`**：③④ 全部置 0 ⇒ 只剩 ①+② 的效果（玄骸 + 基伤 + 多重 + 暴击）。
这不是"事后减法"，而是**从根上不放进去**——表里最容易抄错的一条。

### 5.4 已确认的合成顺序（例 C → 毒气 370）

```
面板 10 火（武器自带），槽 1 = +90% 火，槽 2 = +90% 毒；新面板总伤 Tnew = 200（题意）
  ④ 同类型先加总：火Mod 180 并成一个槽位；毒Mod 180 另一个槽位；面板火 10 一个槽位
  ⑤ 配对（面板元素先入队）：面板火 10 + 火Mod 180 → 火 190
                          火 190 再与 毒Mod 180 配对 → 毒气 370 ✅
     （若"按槽位不先加总"，结果会是 火 190 + 毒 180，即不复合 —— 需求方已否决）
  ⑥ 汇总：毒气 370、无残余火/毒
```

**⚠ A-02 已确认**：同类型 Mod 元素**先加总成一个槽位**再参与合成。
剩下两个细问仍未定，但不影响本条已确认的语义：
① 面板自带单元素与 Mod 单元素谁先入队（例 2 中"毒(Mod) 与 面板火"能配上，说明**面板元素先入队**是可行做法）；
② 两个**不同**基础元素的 Mod 卡（火卡 + 毒卡）在"先加总"之后，靠什么定跨类型配对顺序（默认按槽位号最小者优先）。

**⚠ A-14（已确认为口径 A）**：元素加量 = `新面板总伤 × 元素%`，
其中「新面板总伤」= **①玄骸 + ②基伤**（表 4.1 校验例 1 → 200）。物理 %Mod **不计入**该基数，
见 `decisions.md` D-022（待需求方最终确认）。
若被驳回，改 `applyElements` 与 `spreadTotalAfterMods` 两处。

## 6. L3：暴击与爆头

```ts
// 3.1 两条线，务必分开
function critChanceTotal(ctx) { return BUCKET(weapon.critChance, 'critChance') }          // 固定加算 = 私法
function critDamageTotal(ctx) { return BUCKET(weapon.critMultiplier, 'critMultiplier') }

function critAverage(v: number, cc: number, cd: number): number {
  return (cc × (cd − 1) + 1) × v              // 平均伤害：−1 项永远是总爆伤，不出现"实际倍率"
}

function critTiers(cc: number, cd: number) {  // 上下限：分档实际倍率 + 各档概率
  const k = Math.floor(cc)                    // 暴率 150% → k=1
  const f = cc - k
  return [
    { k,     prob: 1 − f, mul: 1 + k       × (cd − 1) },
    { k: k+1, prob: f,     mul: 1 + (k + 1) × (cd − 1) },
  ]
}

// 3.2 爆头（需求方 2026-11-05 裁定：爆头是「开关」，且爆头倍率与暴击倍率是两件事）
//   D-020 补正：×2 只作用于"爆头且暴击"，未暴击不乘；未开爆头整项不存在。**与暴击分档线无关**。
//   爆头倍率 = 敌人配置的 headshotMultiplier（默认 3.0）× (1 + Σ爆头Mod%)
function headshotMultiplier(ctx: Ctx): number {
  return (enemy.headshotMultiplier ?? 3.0) × (1 + sumPct('headshotDamage'))
}

function damageLine(v: number, cc: number, cd: number, hitHead: boolean, ctx: Ctx) {
  const base = v × (hitHead ? headshotMultiplier(ctx) : 1)
  const critRow = base × cd × (hitHead ? 2 : 1)        // D-012 + D-020：只有爆头 ∧ 暴击才 ×2
  return {
    不暴击: base,                                      // 爆头但不暴击：只乘爆头倍率，不乘 2
    暴击  : critRow,
    平均  : (1 − cc) × base + cc × critRow,            // = base × [(1−cc) + cc × cd × (hitHead?2:1)]
  }
}
```

- **口径来源（D-012 原文）**：「爆头倍率跟这个不是一个事情，爆头有自己的倍率，爆头且暴击的时候需要乘爆头倍率乘暴击倍率再乘 2」。
  → 推翻了表 3.2 的"等效于总爆伤翻倍"写法。爆头是**开关**（不勾选时完全没有爆头项），
   **爆头但未暴击时不额外乘 2**，只有"爆头 且 暴击"才 `× 2`。
- **与平均伤害的关系**：平均伤害仍然是 `cc(cd−1)+1` 的期望（3.1），爆头 ×2 只在"命中弱点且暴击"时出现；
  上式的 `平均` 行把这一点并进了一个式子，便于直接对比"勾/不勾爆头"。
- **⚠ 待补充确认**：分档上下限（k 级）里的 `×2` —— **D-020 已确认：与分档线无关**。
  分档给出的是"暴击等级 k 对应的倍率"，`×2` 只是"该档是否发生暴击"的标记，不随 k 变化；
  平均线用 `(1−cc)·base + cc·critRow`，两条线在 `cc ≥ 1` 与 `cc = 0` 两端必须一致（已写成测试）。
- **弱点暴率**（`weakcc`，敏锐主武 / 手枪敏锐等）：表里没给落点，属第 7 节范围，随 D-014 暂缓。
- **近战连击（`br` 急进猛突 / `scc`）与角斗士套装**：同样未定义"连击倍率"的来源，随 D-014 暂缓。

## 7. L4：触发与 DoT

```ts
// 0.3 ①：单弹头总触发率（全体元素合计）
function totalProcChance(seg: Segment, ctx: Ctx): number {
  const base = seg.procChance                                   // 0~1
  const m = 1 + sumPct('statusChance')
  return ctx.beam ? base × m × (1 + sumPct('multishot')) : base × m   // 2.3：射线再乘一次多重，实弹不乘
}

// 0.3 ②：某元素在触发池里的份额
function share(t: DamageType, v: Vec): number { return (v[t] ?? 0) / total(v) }

// 0.3 ③④：期望层数
function stacksPerShot(t: DamageType, v: Vec, seg: Segment, ctx: Ctx): number {
  return totalProcChance(seg, ctx) × share(t, v) × (ctx.beam ? 1 : multishot(ctx))
}

// 6.2：DoT 完整结算链
//   需求方 2026-11-05（D-008）：① 玄骸是固有的 → 保留在基础值里；② 爆头是开关 → 不进①，
//   而是每跳时作为独立的爆头开关乘在 ③ 之后（与射线合并跳同一处理）。
function dotTick(dotBase: Vec, t: DoTType, ctx: Ctx): number {
  const b = dotBase[t] × DOT_COEF[t]                          // ② 基础触发值 = ① × 系数
  // ① 里的 dotBase 已含：玄骸加成（D-017）、基伤、多重、暴击；不含元素/物理 Mod 加量
  return b
    × (1 + sumPct(`elemental:${t}`))                          // ③ 该类型元素%：毒气只吃毒气（6.3）
    × (1 + sumPct('statusDamage'))                            // 6.3 异常状态伤害 +X%
    × (1 + factionFor(enemy.faction))                         // ③ 派系第二次（5.3 / D-013）
    × (ctx.manual?.headshot ? headshotMultiplier(ctx) : 1)    // 爆头开关（D-008）
}

const DOT_COEF = { heat: 0.5, toxin: 0.5, electric: 0.5, gas: 0.5, slash: 0.35 }

// 6.3 / 表 4.1：dotBase 侧的元素加量口径（A-14 已定：口径 A）。
// DoT 基础值剔除的是"加量部分"，不是剔掉元素本身：面板自带元素（如 50 火）仍留在 dotBase 里，
// 只是不含 +90% 火 Mod 的加量。因此 dotBase 的元素值 = 面板自带元素值 × 基伤系数（不含 Mod 加量）。
//   例：面板 100 冲 + 50 火，+100% 基伤、+90% 火 → dotBase = { impact: 200, heat: 100 }（热 DoT 看 100，不看 190）
const DOT_DURATION = { heat: 6, toxin: 6, electric: 6, gas: 6, slash: 6 }     // 爆炸不在此表（见 §9）
```

- **DoT 基础值（①）**：`side='dotBase'` 的结果 ⇒ 含玄骸 ± 基伤 ± 多重 ± 暴击，**不含**元素/物理 Mod 加量。
  玄骸是武器固有属性，**保留**（D-008；与 D-017「玄骸在基伤之前」一致）。
- **爆头对 DoT**：表 3.2 说"适用"，需求方把它定为**开关**，因此放在每跳的独立乘区（不进①，避免被派系加成二次放大）。
- **爆炸**：需求方明确「爆炸是异常状态，跟 DoT 不是同一个类型」（D-008）→ **单列结算**，不进本节汇总，见 §9。
- **射线多重**：实弹 `stacksPerShot` 乘多重、射线不乘；射线那 `(1+Σ射线多重%)` 只进触发率不进伤害（2.3）。
  射线标记走人工表 `manual/beam-weapons.ts`（D-010，进 `data-todo` 人工确认）。

```ts
// 每秒叠层 = 每发期望层数 × 射速，按各元素叠层规则累加（火焰无上限并累加基础值、毒气 10 层、其余独立计时）
function dotCurveSeconds(dotBase: Vec, seg: Segment, ctx: Ctx): number[][] {   // [t][doTType]，t = 0..6
  return Array.from({ length: 7 }, (_, t) => DoT_TYPES.map(x => stacksAt(t, x) × dotTick(dotBase, x, ctx)))
}
```

**爆炸（6.4 / D-008 / D-016）：单列一行，不进 DoT 曲线。**

```ts
// 需求方 D-008：「爆炸是异常状态，跟 DoT 不是一个类型」→ 独立结算、独立展示
function blastLine(dotBase: Vec, seg: Segment, ctx: Ctx) {
  const sps    = stacksPerShot('blast', dotBase, seg, ctx) × fireRateFinal   // 期望每秒叠层
  const fills  = sps × 1.5 ≥ 10                                              // 1.5 秒内能否叠满 10 层
  const single = total(dotBase) × 0.30                                       // 单体：每层 30%
  // 范围仅在「满 10 层立即结算」时产生：300% / 层 = 单体的 10 倍（6.4）
  return fills ? { 每秒平均: (single × 10 + single × 10) / 1.5, 结算方式: '满10层立即结算（含范围）' }
               : { 每秒平均: single × sps,                     结算方式: '满时长结算（无范围）' }
}
```

- **爆炸的「基础伤害」**：D-008 已确认爆炸与 DoT 不是同一类型，本版以 `dotBase` 作为爆炸的伤害基数
  （与 DoT 基础值同源，含玄骸 + 基伤 + 多重 + 暴击）。若后续希望爆炸单独定义基数，再单列。
- **曲线是期望值**：与 2.4「只算期望、不做随机模拟」一致（D-016）。

### 12.1 A-14 元素加量载体（**已确认：口径 A**）

场景一（与校验例 1 相同）：面板 = 100 冲击 + 100 切割，Mod = +100% 冲击、+100% 毒素。无玄骸、无基伤 Mod。

```
口径 A（「加量加到该类型上」，即表 4.1 原文 单类型最终_t = 面板伤害_t + 加量_t）
  物理：冲 = 100 × (1+100%) = 200；切 = 100
  元素：基数 Tnew = 200 + 100 = 300；毒加量 = 300 × 100% = 300
  汇总：冲击 200 / 切割 100 / 毒素 300        ← 与归属表校验例 1 一致

口径 B（「底座已经含物理 %，元素加量只记一份」）
  物理：冲 = 200；切 = 100
  元素：毒 = Tnew × 100% = 300（毒素原本无面板值）
  汇总：冲击 200 / 切割 100 / 毒素 300        ← 本例与 A 完全相同
```

**真正的分叉只出现在「面板本身已有同类型元素」时**：

```
面板 = 50 火 + 50 切，Mod = +100% 火
  口径 A：Tnew = 150（= 50 火 + 50 切，无物理 %）
          火 = 面板 50 + 加量 150×100% = 200；切 = 50       → 总伤 250
  口径 B：把「已放大的火」当作新的面板再乘一次
          火 = 150 × (1+100%) = 300；切 = 50                → 总伤 350
```

> **需求方 2026-11-05 选择口径 A**：元素加量**加到该类型上**（表 4.1 原文的直接翻译）。
> 口径 B（把已放大的元素当新面板再乘一次）已否决——它会让元素 % 随面板自带元素量非线性放大。
> 校验例 1 的结果以**算式**为准：`新面板总伤`（= 玄骸 + 基伤）= **200**，
> 毒素加量 = 200 × 100% = **200** ⇒ 汇总 `冲击 200 / 切割 100 / 毒素 200`，与表 4.1 原文一致。
> （旧写法"300"把物理 %Mod 算进了基数，已修正；取舍见 `decisions.md` D-022。）

### 12.2 A-03 镀层类伤害乘区（**已定案**：`decisions.md` D-024）

**规则原文**：「目标每具有 1 种异常状态 +x% 伤害，最多叠加 y 次」⇒

```
镀层类加量 = x% × a × y        （进基伤括号：面板基伤 × (1 + Σ基伤Mod% + 镀层%)）
  x = 每层百分比（Mod 的 +X%，数据层 stats[levelValues 满级]）
  y = 叠加上限（击杀后获得的 buff 层数；数据层 conditions[].maxStacks，UI 下拉框默认取最大值）
  a = 目标身上的异常状态**种类数**（不是层数：中毒 5 层只算 1 种），UI 下拉框，默认 0
```

- **落点**：只进基伤括号，**不吃**灵化基伤那一项、**不吃** AoE 段（表 2.1 已确认）。
- **数据层可直接驱动**（本次核对，共 4 个带 `key: 'co'` 的 Mod）：

  | Mod | 槽位 | x（每层） | y（maxStacks） | a=1 时 |
  |---|---|---|---|---|
  | 镀层 步枪才能 `galvanized_aptitude` | rifle | 20% | 2 | +40% |
  | 镀层 准确射手 `galvanized_shot` | pistol | 30% | 3 | +90% |
  | 镀层 通晓霰弹枪 `galvanized_savvy` | shotgun | 20% | 2 | +40% |
  | 异况超量 `condition_overload` | melee | 80% | **无 maxStacks** ⚠ | 按 y=1 计，待补 |

- **`a` 的可用范围**：0..10（对应 15 种伤害类型里"目标身上有的种类数"）。
- **类镀层被动的武器**：`packages/data/src/manual/weapon-effects.ts` 仍是空表，
  本次**不按名字猜**哪把武器有类镀层被动（D-000 教训）；需求方点到哪把、录哪把。
- **校验**（`verify-co.mjs`，赤毒·卡拉克 + 膛线 + 镀层步枪才能，玄骸火 50%）：
  面板 23 → 玄骸 11.5 → 面板 34.5；a=3 时镀层 = 20%×3×2 = +120%，基伤系数 3.85
  ⇒ 加成后总伤 34.5 × 3.85 = **132.825**（a=0/1/2 分别是 91.425 / 105.225 / 119.025，全部对上）。
