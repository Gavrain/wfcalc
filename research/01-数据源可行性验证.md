# 数据源与武器面板可行性验证（PoC）

> 结论先行：**武器面板数据完全可获取且结构完整**，足以支撑"自定义武器面板 + 全武器内置库"。
> 但**AoE 半径、灵化加成、赋能/紫卡描述、Mod 数值**不在武器导出里，必须从独立数据源或人工维护层补齐。
>
> 验证环境：Windows / Node v24.10.0 / git 2.55.0。验证日期：2026-11-04。

## 1. 网络环境（重要，影响所有后续脚本）

- 本机直连 HTTPS 失败：`Invoke-WebRequest` 与 `curl.exe` 均返回
  `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`（TLS 客户端凭据异常）；
  注册表显示代理 `127.0.0.1:10809`，但该端口**没有进程监听**（代理软件未运行）。
- 因此**抓取脚本不要依赖本机 TLS 栈**。本地脚本验证时使用了 harness 的 `web_fetch` 工具取回数据。
- 工程落地时建议：抓取脚本走 Node 的 `fetch`/`undici`，并在 CI（GitHub Actions，Linux）里跑，
  避开本机 TLS/代理问题；本地只在需要时配合代理软件运行。

## 2. 数据源实测

| 数据源 | 地址 | 实测结果 | 说明 |
|---|---|---|---|
| Public Export Plus | `https://browse.wf/warframe-public-export-plus/ExportWeapons.json` | HTTP 200 | DE 官方导出（社区镜像），**最权威**，字段见第 3 节 |
| 同上 | `.../ExportUpgrades.json` | HTTP 200 | Mod / 紫卡词条 / 赋能级别的原始数据 |
| 同上 | `.../ExportRecipes.json` | HTTP 200 | 配方表，可用于筛选"可获取武器" |
| WFCD/warframe-items | `raw.githubusercontent.com/WFCD/warframe-items/master/data/json/Weapons.json` | 未测（本机 TLS 阻断） | 社区聚合，已做本地化名称与字段整理 |
| WARFRAME Wiki | `https://wiki.warframe.com/w/Damage/Calculation` | 可读 | 公式口径的核对来源 |

> 本次快照只取到导出文件的开头部分（约 10 万字符、43 把武器），用于**结构验证**，不代表全量。
> 全量抓取需在真实网络下由脚本完成。

## 3. 武器导出的字段结构（已验证）

单个武器对象（`ExportWeapons.json` 的 value）顶层字段：

```
name, parentName, icon, codexSecret, description, introducedAt, tradable,
productCategory, holsterCategory, slot, variantType, compatibilityTags,
damagePerShot[20], totalDamage, criticalChance, criticalMultiplier, procChance,
fireRate, trigger, accuracy, noise, magazineSize, reloadTime, multishot,
masteryReq, omegaAttenuation,              // omegaAttenuation = 紫卡倾向
// 近战专有
range, followThrough, comboDuration, blockingAngle, windUp,
slamAttack, slamRadialDamage, slamRadius,
slideAttack, heavyAttackDamage,
heavySlamAttack, heavySlamRadialDamage, heavySlamRadius,
// 模式与细节
behaviours[]
```

`behaviours[]` 每一项即一个**攻击模式 / 弹头段**，是本项目最关键的建模输入：

```
stateName,            // 触发方式：TriggerAuto / TriggerSemiAuto / TriggerBurst / TriggerActivated ...
fireIterations,       // 该段的弹头数（霰弹枪 = 弹丸数）
burst: { count, delay },  // 点射
impact:   { DT_*: 数, procChance },   // 命中直接伤害
projectile: {
  attack:            { DT_*: 数, procChance },   // 飞行体命中
  explosiveAttack:   { DT_*: 数, procChance },   // 爆炸（AoE）
  embedDeathAttack:  { DT_*: 数, procChance }    // 嵌入/滞留后死亡伤害
}
```

伤害类型键：`DT_IMPACT / DT_PUNCTURE / DT_SLASH / DT_FIRE / DT_FREEZE / DT_ELECTRICITY /
DT_POISON / DT_EXPLOSION / DT_RADIATION ...`。

**已实测到的、直接影响建模的结论：**

1. **多攻击模式是普遍现象**：43 把武器里 31 把有 >1 个 behaviour（占位模式会被过滤，见第 6 节）。
2. **弹头命中与范围伤害在结构上是分开的**：11 把武器带 `explosiveAttack`，4 把带 `embedDeathAttack`。
   这正好对应你说的"弹头命中 vs 范围伤害"两类伤害口径。
3. **`fireIterations` 与顶层 `multishot` 可能不一致**：例如 Strun Vandal 顶层 `multishot: 10`，
   而 behaviour 里 `fireIterations: 10`；但 Soma 的第二个 behaviour 是 `fireIterations: 8` 的
   特殊状态、而不是"8 连发"。**不能简单把 behaviours 条数当模式数，也不能把 fireIterations 全部当多重。**
4. **`stateName` 缺失的 behaviour 是占位符**：大量武器有 `fireIterations: 1, impact: { DT_IMPACT: 40, procChance: 0.1 }`
   的裸条目，没有任何 `stateName`，实测约 40 点伤害——这是数据里的残留，清洗时按"无 stateName 且
   数值为 40/3.333"丢弃。
5. **顶层 `damagePerShot` 只反映主模式**：`HeavyRifle`(Gorgon) 的 20 元素数组是子弹伤害，
   但 behaviour 里 `projectile.embedDeathAttack.DT_FIRE = 725`（Gorgon 蓄力爆炸）**完全不在数组里**。
   → **必须用 behaviours 建模，`damagePerShot` 只能当交叉校验。**
6. `0.9999` 级别的浮点误差普遍存在（如 `18.999991`），规范化时统一 round 到 4~6 位小数。

## 4. 导出数据**缺失**的字段（必须另找来源或人工维护）

| 缺失项 | 影响 | 建议来源 |
|---|---|---|
| **AoE 半径（explosion radius）** | 无法把范围伤害分摊到多个敌人 | Wiki `Module:Weapons/data` 的 `ExplosionRadius`，或人工表 |
| **灵化（Incarnon）加成** | 灵化是多攻击模式里最特殊的一类 | 人工维护结构化表（等级 1~5 加成、激活条件、灵化形态面板） |
| **赋能（Arcane）数值** | 武器赋能槽 | `ExportUpgrades` + 人工核对 |
| **紫卡（Riven）词条基准值** | 紫卡配置 | 已存于工作区 `20261031紫卡模拟器V10.html`（`ZKDATA`/`ZKNAMES`/`ZKPRICE`） |
| **Mod 数值与乘区归属** | 公式里每个 Mod 影响哪个乘区 | 导出只有 `baseDrain/rarity/compat`，**没有数值**；数值要么人工表，要么用现有 HTML 里的 `ZKMODS` |
| 中文名 / 本地化 | UI 显示 | 现有 HTML 的 `ZKNAMES`，或 DE 语言包 |

> 关键判断：**现有紫卡模拟器里的 `ZKMODS`、`ZKARCS`、`ZKSTORE` 恰好补上了导出数据缺失的那部分**，
> 可以把它们当作"人工维护层"的起点（需核对许可与准确性）。

## 5. 可用的现成素材（工作区内的紫卡模拟器）

单文件 15.4 MB HTML，纯原生 JS、零外部依赖，内部模块：

- 数据：`ZKDATA` / `ZKNAMES`（名称、紫卡词条）、`BASEDATA` / `RULES`、`ZKMODS`（11.6 万字符 Mod 表）、
  `ZKARCS`（赋能）、`ZKSETS`（套装）、`ZKSTANCE`（架势）、`ZKASM`（天工造武 / 组合枪）、
  `ZKPRICE`（1.37 MB 紫卡价格）、`WEAPON_DB`（加密的武器库）。
- 计算：`RIVEN_ROUTER` 内含 `typeCoef / compCoef / typedSum / critExpect / effectiveArmor /
  armorDR / DOT_COEF / PROC`，以及按目标档（普通图 Lv40 / 钢铁 Lv140）的护甲缩放。
- UI：`<main>` + 标签页 + 卡片式，暗/亮双主题、中英双语（`tx(cn,en)`、`ZKLANGI`）、localStorage 记忆。
- 体积构成：`ORT_EMBED` 4.9 MB + `ONNX_MODELS` 7.6 MB（紫卡 OCR 模型）≈ **占总体积 80%**——
  计算与数据本体只有约 1.6 MB。**新工程不包含 OCR，不会有体积问题。**

## 6. 清洗规则草案（写进 `packages/data-build`）

1. 丢弃无 `stateName` 的占位 behaviour（第 3 节第 4 条）。
2. 每个 behaviour 归一化为 `AttackMode { trigger, shots, bullets, segments: ImpactSegment[] }`。
3. `impact / attack / explosiveAttack / embedDeathAttack` 每个都归一化为独立的 `DamageSegment`，
   带 `kind: 'hit' | 'aoe' | 'embed'`，并**保持其对多重、元素、暴击的不同响应**（这是核心乘区差异）。
4. 保留 `multishot`、`fireRate`、`trigger`、`magazineSize`、`reloadTime` 等 DPS 相关字段。
5. 输出 JSON Schema 校验 + 变更 diff，任何上游字段变动都要在 CI 里报出来，避免静默错漏。

## 7. 对"自定义武器面板"的支持度

导出字段覆盖了自定义武器需要的全部基础量（伤害分布、暴率、暴伤、触发、多重、射速、弹匣、换弹、
模式结构、近战专项数值），**自定义武器 = 同一份 Schema 的手填实例**，无需额外建模。
缺的只有 AoE 半径与灵化加成，这两项在自定义面板里同样需要单独输入框。
